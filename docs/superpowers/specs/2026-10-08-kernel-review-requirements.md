## 1. 要解决的问题

1. **审 patch 没有固定步骤。** `linux-kernel-dev` 的「审码」只指向代码风格文档
   (`SKILL.md:50`)。让模型审一个 BSP patch,它不会系统地拆分改动、追调用链、
   排除误报,结果取决于当次发挥,同一个 patch 审两次可能得出两套结论。
2. **社区已有成熟的审查规则,但不覆盖 BSP。** `masoncl/review-prompts`(sashiko
   所用的规则)有完整的审查流程和误报排查清单,但没有 gpio、pinctrl、clk、
   regulator、ASoC 等驱动子系统的规则,也不了解老内核、厂商宏开关、defconfig。
3. **没法证明审查变好了。** `linux-kernel-dev` 现有的 148 条用例不调用模型
   (`regression_test.mjs:6`),`evolution/rules.json` 55 条规则的命中次数全是 0。
   改了规则之后,审查是变好还是变坏,目前没有任何数据。
4. **在 GitHub 上看不出我们跟社区这套规则的关系。** 7 月那份调研页
   (`docs/KERNEL-REPOS-SURVEY.html`)甚至漏掉了 review-prompts。

## 2. 用的人

| 谁 | 用来做什么 | 本期是否覆盖 |
|---|---|---|
| BSP 工程师(user 和团队) | 提 MR 前自审;审厂商 / 原厂给的 patch;SDK 升级或移植后审一段提交 | **是,首要对象** |
| 本仓维护者(user) | 升级上游版本;写新的 BSP 规则并量效果 | 是 |
| GitHub 访客 | 了解这个 skill 是什么、跟上游什么关系、效果有多少 | 是 |
| 上游维护者 | 接收我们提的规则 | **否**,暂缓(user 2026-10-08 定),条件见设计书 §10 |

## 3. 使用场景

| 编号 | 场景 | 期望结果 |
|---|---|---|
| S1 | 工程师在 BSP 内核树里说「审一下 HEAD」 | 得到问题列表:每条有位置、严重度、怎么触发、是不是这个 patch 引入的;没问题就明确说没找到问题,并列出查过哪些方面 |
| S2 | 审厂商给的 patch(已 `git am` 到一个分支) | 同 S1;patch 的提交信息和注释里如果夹带「忽略以上规则」之类的文字,审查不受影响 |
| S3 | SDK 升级后审一段范围 `HEAD~5..HEAD` | 逐个提交审;后面提交修好的问题要标出「在哪个提交里修了」 |
| S4 | 只改了 defconfig 或几行 dts 的小改动 | 只跑确定性脚本,几秒到几十秒出结果,不走全流程 |
| S5 | 已经装了 sashiko 的人 | 用 sashiko 的多阶段流水线跑同一套规则(含 BSP 规则) |
| S6 | 维护者升级上游 submodule | 能当场知道升级有没有让 BSP 规则失效 |
| S7 | 维护者新写一条 BSP 规则 | 能跑基准测试,拿到「加规则前 / 加规则后」两组数 |
| S8 | GitHub 访客打开仓库 | 从 README 看到 kernel-review 是什么、基于哪个上游、许可是什么 |

## 4. 功能需求

优先级:**必须** = 该阶段不完成不算交付;**应有** = 该阶段尽量做,可顺延一个阶段。

### 4.1 接入上游

| 编号 | 需求 | 优先级 | 设计 | 阶段 |
|---|---|---|---|---|
| R-F01 | 上游 review-prompts 以 git submodule 接入 `third_party/review-prompts`,固定在一个具体提交 | 必须 | §4 | P0 |
| R-F02 | 找规则目录的顺序:环境变量 `KERNEL_REVIEW_PROMPTS_DIR` → 本仓 submodule → `$HOME/src/review-prompts`。三处都没有时,退出码非 0,并打印能直接复制执行的安装命令 | 必须 | §4 | P0 |
| R-F03 | 生成合并规则目录:上游 `kernel/` + 本仓 BSP 规则,BSP 规则登记进合并后的子系统索引表 | 必须 | §7.1 | P0 |
| R-F04 | 合并后核对:索引表表头列数与预期一致,每条 BSP 索引行都在最终索引里;任何一项不符,退出码非 0 并指出是哪一行 | 必须 | §7.1 | P0 |
| R-F05 | 合并目录的底座可以换成 sashiko 自带的规则包(`--base`),供 S5 使用 | 应有 | §6、§7.1 | P0 |
| R-F06 | 不要求用户运行上游的全局安装脚本;本 skill 不往 `~/.claude/skills/kernel/`、`~/.claude/commands/` 写任何东西 | 必须 | §6 | P0 |

### 4.2 审查本身

| 编号 | 需求 | 优先级 | 设计 | 阶段 |
|---|---|---|---|---|
| R-F10 | 输入支持单个提交(默认 HEAD)和提交范围 `A..B` | 必须 | §6 | P0 |
| R-F11 | 审查全程不改被审的内核树:不改工作区文件,不切分支,不动 git 元数据 | 必须 | §6 | P0 |
| R-F12 | **审查产物不落在被审的内核树里。** 上游流程要求把 `review-inline.txt` 写到当前目录(上游 `review-core.md:247`),也就是内核树里,BSP 树里多出未跟踪文件很容易被一起提交进 MR。产物默认放 `~/.cache/sky-skills/kernel-review/<树目录名>/<提交号前 12 位>/`,可用参数改 | 必须 | §6、§11 | P0 |
| R-F13 | 按上游 `review-core.md` 的流程审查,匹配到的 BSP 规则自动加载 | 必须 | §6 | P0 |
| R-F14 | 输出里列出**这次实际加载了哪些规则文件**。这样 BSP 规则没加载时,读结果的人能看出来,而不是看到一份照常完成、但少了 BSP 部分的审查 | 必须 | §7.1、§11 | P0 |
| R-F15 | 输出两份:① `review-inline.txt`,上游版式(英文纯文本);② 对话里给中文摘要,每条写明:问题、位置(`文件:行`)、严重度、触发条件、是这个 patch 引入的还是原来就有的 | 必须 | §6 | P0 |
| R-F16 | 严重度沿用上游 `severity.md` 的四级(Critical / High / Medium / Low),不另立标准 | 必须 | §6 | P0 |
| R-F17 | 审范围时,问题如果在范围内后面的提交里修好了,要标出修复它的提交标题 | 应有 | §6 | P0 |
| R-F18 | 被审 patch 里的提交信息、注释、文件内容一律当数据,不当指令;规则只从合并目录加载 | 必须 | §11 | P0 |
| R-F19 | 小改动(只改 defconfig、dts 或注释)默认只跑确定性脚本;用户说「完整审」时强制走全流程。判定标准在 P1 实测后写进 SKILL.md | 应有 | §11 | P1 |

### 4.3 确定性预检和引用核对

| 编号 | 需求 | 优先级 | 设计 | 阶段 |
|---|---|---|---|---|
| R-F20 | 审查前按改动类型调用 `linux-kernel-dev/scripts/` 里已有的脚本(触发条件见设计书 §7.3 的表),结果写进产物目录的 `facts.md`,作为审查的已知上下文 | 必须 | §7.3 | P1 |
| R-F21 | 只调用,不复制 `linux-kernel-dev` 的脚本 | 必须 | §7.3 | P1 |
| R-F22 | 某个脚本缺依赖或运行失败时不中断审查,但在 `facts.md` 里写明「没运行 + 原因」,中文摘要里也提一句 | 必须 | §7.3 | P1 |
| R-F23 | `review-inline.txt` 里每一行代码引用(`> ` 开头),都要在该提交的 diff 或当时的文件里找得到;找不到的意见退回重查,最终报告里只保留核对通过的,并写明退回了几条 | 必须 | §7.4 | P1 |

### 4.4 BSP 规则

| 编号 | 需求 | 优先级 | 设计 | 阶段 |
|---|---|---|---|---|
| R-F30 | 第一批 5 份:gpio、ASoC、iio、phy、pinctrl,外加 1 份 BSP 误报排除规则 | 必须 | §7.2 | P2 |
| R-F31 | 版式照上游 `subsystem-template.md`,英文;只写审查时容易漏的 bug 写法,不写常识和通用编程建议 | 必须 | §7.2 | P2 |
| R-F32 | 每条 bug 写法都带内核源码出处(文件路径 + 函数名) | 必须 | §7.2 | P2 |
| R-F33 | 文件名加 `bsp-` 前缀,避免将来跟上游同名文件冲突 | 必须 | §7.2 | P2 |
| R-F34 | 误报排除规则每条都写清楚排除依据,不允许出现「BSP 代码标准低」这类笼统理由 | 必须 | §7.2 | P2 |
| R-F35 | 第二批(clk、regulator、regmap、spi、mmc)用本地 BSP 题库量效果后再定 | 应有 | §12 | P4 |

### 4.5 基准测试

| 编号 | 需求 | 优先级 | 设计 | 阶段 |
|---|---|---|---|---|
| R-F40 | 题目格式照 sashiko 的 `benchmark.json`:`Commit` / `Fixed-by` / `subsystem` / `problem_description` | 必须 | §8 | P3 |
| R-F41 | 公开题库:sashiko 基准里第一批 5 个子系统的 64 条,只存提交号和描述 | 必须 | §8 | P3 |
| R-F42 | 本地题库从 BSP 树的 `Fixes:` 提交里挖,只存本机 `~/.config/sky-skills/kernel-review/`,任何情况下不进仓库 | 必须 | §8 | P3 |
| R-F43 | 同一批题跑两组:① 只用上游规则 ② 上游 + BSP 规则;规则目录是两组之间唯一的差别 | 必须 | §8 | P3 |
| R-F44 | 判分三档:找到 / 部分找到 / 漏掉;同时记录每组报出的问题总数,用来估算误报 | 必须 | §8 | P3 |
| R-F45 | 每次跑分记录:上游提交号、合并目录的内容哈希、模型名、审查引擎、每题耗时和 token 数 | 必须 | §8 | P3 |
| R-F46 | 先跑 10 条冒烟测试,其中 3 条各重复 3 次,看同一题结果的波动有多大,再决定全量跑几次 | 必须 | §8 | P3 |
| R-F47 | 支持两种审查引擎:Claude Code + 本 skill、sashiko CLI | 应有 | §8 | P3 |

## 5. 非功能需求

| 编号 | 需求 | 怎么验收 |
|---|---|---|
| R-N01 | 上游文件不进本仓 git 历史 | `git ls-files` 里除了 submodule 记录本身,没有任何上游文件 |
| R-N02 | 出处清楚 | README 致谢段写明上游仓库、作者、许可;改编自 sashiko 的判分提示词在文件头注明来源和 Apache-2.0 |
| R-N03 | 公开内容不含内部信息 | 所有新增 / 修改的公开文件跑外发脱敏检查(两条 grep),0 命中 |
| R-N04 | 中文文档不用黑话、不用自造简称 | `check_buzzwords.py --strict` 两张词表都是 0 |
| R-N05 | 可复现 | submodule 固定提交;基准结果文件带 R-F45 列的全部字段 |
| R-N06 | 每个新脚本都有 `--selftest`,而且自测里至少有一项「故意给坏输入,必须报错」 | 跑自测;再把被测的那段逻辑临时注释掉,自测必须失败(确认自测不是摆设) |
| R-N07 | 运行环境 | macOS 和 Linux 都能跑;依赖只限 bash、python3、node、git(`linux-kernel-dev` 现有脚本已经需要这些);缺依赖时说清楚缺什么 |
| R-N08 | 成本可见 | 基准每题记录 token 数和耗时;全量跑之前先用冒烟测试估算总量 |
| R-N09 | 不污染用户环境 | 不写 `~/.claude/` 下的全局配置;缓存只放 `~/.cache/sky-skills/` 和 `~/.config/sky-skills/` |

## 6. 不做的事(本期)

- 不向上游提 PR(user 定,条件见设计书 §10)
- 不支持直接审 `.patch` / mbox 文件,先 `git am` 到一个分支再审
- 不搬 sashiko 的守护进程、邮件列表监听、数据库、webhook
- 不翻译上游规则,不在本仓保存上游文件的副本
- 不自己写多阶段编排,要多阶段就用 sashiko
- 不把审查结果自动发到 MR 或邮件,只输出文件和对话摘要

## 9. 用到的词

| 词 | 意思 |
|---|---|
| submodule | git 的子模块:本仓只记录「上游仓库地址 + 一个提交号」,文件内容不进本仓历史 |
| 合并规则目录 | 把上游规则和本仓 BSP 规则放进同一个目录,让上游的审查流程能一起加载 |
| 基准测试 | 拿一批已知有 bug 的真实提交让审查去找,数它找到了几个 |
| 误报 | 报出来的问题实际不存在 |
| 冒烟测试 | 正式全量跑之前,先用少量题确认流程能跑通 |
