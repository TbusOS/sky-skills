1 · What a struct actually occupies1 · 结构体到底占了多少

The fields you wrote are on the left, what the compiler laid out is on the right — and the padding is drawn as sunken gaps, because that is what it is: nothing. Two holes here cost 15 of 56 bytes. The dashed line is the cache line boundary, which is the reason this matters beyond tidiness.你写的字段在左边，编译器排出来的在右边 —— 而填充画成凹陷的空格，因为它就是这个：什么都没有。这里两个空洞吃掉了 56 字节里的 15 个。那条虚线是 cache line 边界，也是这件事不只是「整不整齐」的原因。

2 · Three relations that look alike in code2 · 代码里长得像的三种关系

struct B b, struct B *b and struct list_head n are one character apart in the source and three different lifetimes in reality. Embedding is drawn as containment, a pointer as a hop out to somewhere else, and a list_head as neither — because the list holds the head, not your struct.struct B b、struct B *b、struct list_head n 在源码里差一个字符，在现实里是三条不同的生命周期。嵌入画成包含，指针画成跳到别处，而 list_head 两者都不是 —— 因为链表串的是那个 head，不是你的结构体。

Two allocations, two lifetimes. This is the one that produces use-after-free: A can outlive B, or hold a pointer to something already freed.两次分配，两条生命周期。 释放后使用就出在这一种：A 可能活得比 B 久，也可能手里攥着一个已经被释放的东西。

The list holds the list_head, not A. That is why you need container_of(pos, struct A, n) to get back to A — and why the offset of n is what makes it work.链表串起来的是 list_head，不是 A。 所以才需要 container_of(pos, struct A, n) 才能拿回 A —— 而让它成立的，正是 n 在结构体里的偏移。

3 · Where your private pointer is parked3 · 你的私有指针存在哪

Four lines of probe, drawn. The kernel hands you a struct device; you allocate your own struct and then park a pointer to it on the kernel’s side so that every later callback can get it back. The chain is short — what makes it worth a figure is that it is walked from memory every single time.probe 里的四行，画出来。内核给你一个 struct device；你分配自己的结构体，然后把指向它的指针寄存在内核那边，让之后每一次回调都能取回来。链很短 —— 值得画成图，是因为它每次都是凭记忆走的。

device → client → yoursdevice → client → 你的get the direction backwards and you get a pointer that is valid, wrong, and silent方向弄反，你得到的是一个合法的、错的、而且不报错的指针
/* probe 里这四行，就是下面那张图 */ static int tp_probe(struct i2c_client *cl) { struct tp_data *tp; tp = devm_kzalloc(&cl->dev, sizeof(*tp), GFP_KERNEL); tp->client = cl; /* 往下记 */ i2c_set_clientdata(cl, tp); /* 往上挂 */ ... } /* 别处要拿回来: */ struct tp_data *tp = i2c_get_clientdata(cl);
The two orange lines are the round trip: set_clientdata stores your struct on the kernel’s side, get_clientdata takes it back. Everything else in the chain the kernel already built for you.橙色那两行就是这一来一回：set_clientdata 把你的结构体存到内核那边，get_clientdata 再取回来。链上其余的部分，内核早就替你搭好了。

4 · From a device tree property to a struct field4 · 从设备树属性到结构体字段

Each row is one property and the field it becomes, with the function that does the conversion named on the row itself — because that name is what you actually go looking for. The last row is sunken on purpose: compatible never becomes a field at all.每一行是一个属性和它变成的那个字段，而且做这次转换的函数就写在这一行上 —— 因为你真正要找的就是那个函数名。最后一行故意是凹的：compatible 根本不会变成任何字段。

ONE NODE, THREE PROPERTIES一个节点，三个属性a typo in compatible is silent; a typo in quartz,lanes gives you a zero — two very different bugscompatible 写错是一片安静，quartz,lanes 写错给你一个 0 —— 两种完全不同的 bug
/* arch/arm64/boot/dts/... */ touch@38 { compatible = "quartz,tp-q1"; reg = <0x38>; quartz,lanes = <4>; reset-gpios = <&gpio4 18 GPIO_ACTIVE_LOW>; }; /* probe 里读出来 */ of_property_read_u32(np, "quartz,lanes", &tp->lanes); tp->rst = devm_gpiod_get(dev, "reset", GPIOD_OUT_HIGH);
