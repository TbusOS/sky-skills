# primer · 技术图画法

位域、时序、总线、数据通路、调用路径、算法、互连与地址带、协议分层、纵向地址映射 ——
这九类图和 primer 原有的科普插画差在一件事上:
**它们要同时对得起小白和工程师。**

一张位序画反的寄存器图、一张采样沿和协议相反的时序图,比没有图更糟:它教了一句假话,
而读者会拿着这句假话去读真的 datasheet。

画法的规矩仍然是 `illustration-craft.md`(线宽、viewBox 换算、`fill="none"`、SVG 文字 ≥13px)
和 `dos-and-donts.md`(黄单档、比喻卡必有、不幼稚化);这份文件只加一层:
**技术上不许说错的那些格子在哪。**

## §0 总规则:简化随便,说错不行

> 该省的都可以省。**但不许在图上放一句工程师必须来纠正的话。**

技术图解的全部难处是这条规则的两半互相拉扯。下面五种是最常犯的,每一种都不是"画得糙",
是**在教假话**:

| 画错了什么 | 读者学到的假话 |
|---|---|
| **位序反了** —— bit 0 画在左端,却按"最高位在左"标注 | 他照这张图去读 datasheet,每个字段都落在镜像位置 |
| **采样沿和协议相反** —— 写着 SPI mode 0,黄点画在下降沿 | 他按图接线,采到的是上一位 |
| **总线画成点对点** —— CPU 各拉一根线到每个外设 | "为什么不能人人直连"那一节的结论正好反了过来 |
| **握手只画一个箭头** —— valid 有箭头,ready 没有 | 他以为一方发就成交,而 valid/ready 的全部意义是两边都同意 |
| **跨带箭头跳层** —— 用户态直接连到寄存器 | 这页要纠正的正是这个误解,图替他确认了一遍(特权口子另说,见 §5) |

五条的共同点:**四道机械检查一条都不会报。** verify.py 数 class,visual-audit 量像素和字号,
axe 查对比度,截图只是把画面存下来 —— 没有一道知道 mode 0 在哪个沿采样。
这一格只有这份文件和 §10 的自查。

### 可以省的 / 不许歪的

| 放心省 | 一歪就是假话 |
|---|---|
| 流水线、预取、缓存一致性 | **位序与位宽** |
| 总线仲裁的细节、突发传输长度 | **哪个沿采样、谁在驱动这根线** |
| 时钟偏斜、抖动、上升时间的具体数 | **信号方向**(谁指向谁) |
| 错误路径、中断、超时 | **谁和谁真的连在一起** |
| 电平转换、上拉电阻的阻值 | **层与层的先后次序** |
| 多余的信号线(只画这一节要用的) | **数量级**(位宽、时钟数、砍几次) |

两条配套的纪律:

- **省掉的东西在 figcaption 里说一句。** "这里只画了片选和时钟两根线" 比画一根不存在的线好。
  一句话的成本远低于读者第二天在真手册上撞见第三根线时的困惑。
- **别拿真型号盖章。** 图和某颗真芯片的实际布局不一致时,不要在图上写它的型号和寄存器名。
  要么照真的画,要么用明显通用的名字(`DIR` / "方向寄存器")。一张看着像手册截图、内容却是编的图,
  是这九类图最坏的结局 —— 它会被人当事实引用。

## §1 位域图(bitfield)

一排格子,每格一位。这是硬件主题最常出现的一张图,也是最容易画反的一张。

### 必须画

- **位号方向标出来,而且两端都标。** 寄存器表的通行习惯是 **MSB 左 / LSB 右**:左端写 `31`,
  右端写 `0`。只标一端等于没标 —— 读者无法判断中间的字段是从哪头数的。
- **字段宽度和真实位宽成比例。** 格距固定,字段宽度 = 位数 × 格距。16 位的保留段必须是
  8 位字段的两倍宽。
- **字段跨度一律写 `[高位:低位]`。** 一个占 bit 8 到 bit 15 的字段写成 `[15:8]`,不是 `[8:15]` ——
  datasheet 和 Verilog 都是这个顺序,反着写的括注会让人把字段读成镜像的。
  **bit 0 是最低位**,也就是个位:`[15:8]` 这个字段的值 = 寄存器值 >> 8。
- **正在讲的那个字段用 `--primer-violet` 平涂**,其余字段留白或纸白底。一张图一个主体
  (`illustration-craft.md` §1 与 §9),所以一张位域图只讲一个字段。
- **保留位用 hair 斜线**(1.8 线,45°,间距 10 单位)+ 一处"保留 / Reserved"标签,不是每位一个标签。
- **位号字号 ≥13px**(源尺寸),和图内其它标签一样受 `illustration-craft.md` §6 管。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 32 位标 32 个位号 | 不是错,是装不下 —— 双语页的标签预算见 §8 第 2 条。压小字号来塞满,正是 `dense-diagram-labels-small` 这条检查存在的理由 |
| 字段等宽排列(4 个格子代表 16/8/4/4 位) | 读者数格子会得出错的位宽,而位宽决定这个字段能装多大的数 |
| 保留位画成和可用字段一样的实色块 | 读者会以为它是个能用的字段。保留位的规矩是"读回来是什么就写回什么"(有的手册要求写 0,按手册来),它必须一眼就和可用字段不一样 |
| 格线抖动(手绘感) | 格线的位置**就是**位的位置。抖一格线 = 位错位。抖动只许留给寄存器的外框(§8 第 1 条) |
| 同一页混用两套位号习惯 | 报文图(RFC 风格)是另一套:位从 0 起、从左往右数。画报文就按报文的习惯,但**一页只许一套**,而且要在 caption 里点明是哪套 |

### 违例 → 改写

❌ 位号从左往右 0、1、2 … 31,caption 却写"最高位在左":

```svg
<text x="38"  y="52" font-size="13" fill="#243244">0</text>
<text x="922" y="52" font-size="13" fill="#243244">31</text>
```

图和字说了两件事。读者要么信图要么信字,两条路都通向错的位置。

✅ 位号方向和习惯一致,两端都标,中间只标字段边界:

```svg
<!-- MSB 左 / LSB 右;只标两端与字段边界,不标 32 个 -->
<!-- x 从格距算出来:x = 24 + 28.5 × (格序 + 0.5),格序从左端 0 起,格距见下面的 viewBox 一节 -->
<g text-anchor="middle">
  <text x="38"  y="52" font-size="13" fill="#243244">31</text>  <!-- 格序 0  -->
  <text x="694" y="52" font-size="13" fill="#243244">8</text>   <!-- 格序 23 -->
  <text x="722" y="52" font-size="13" fill="#243244">7</text>   <!-- 格序 24 -->
  <text x="922" y="52" font-size="13" fill="#243244">0</text>   <!-- 格序 31 -->
</g>
```

每 8 位可以给一条 hair 竖线当刻度,**不给数字** —— 刻度让人数得清,数字会把预算吃光。

### viewBox

**格距的下限由"格子里真的放了什么标签"定,不由位宽定。** 判据一句话:

```
格距 ≥ 格内最宽标签的宽度 + 两侧各 7 单位   （格内没有标签 → 这条不设下限）
```

**32 位、而且每格里都要放一个标签** → `viewBox="0 0 960 300"`,挂在
`.primer-container primer-container--wide` 上。13px 的两位数连两侧边距要
14.3 + 7 × 2 = **28.3 单位**(下面第三条给了这两个数的来处),而 32 个格子挤进 900 宽只剩
(900 − 48) / 32 = **26.6 单位** —— 差 1.7,装不下,所以要 960。**960 是这一种画法算出来的数,
不是位域图的通行下限**(§9 一览表里那一行给的就是这一种)。
格内标签这里指值(0/1)、字段名一类的东西 —— **不是 32 个位号**:标满 32 个位号这件事
本身就被下面的 ❌ 表第一行挡着,不管 viewBox 多宽。

⚠ **升 wide 的理由是横向分辨率,不是标签数,也不是列数。** `design-tokens.md` §6 给的两条
(≥16 个标签 / ≥3 列)这张图都不满足 —— 位号只标四个。技术图在那两条之外多的这条理由,
是上面那个格距下限;升档换来的是横向的地方,不是标签额度。

**只在格排外标几个位号的图不受 960 管。** 位号写在格排**上方**、只标两端和正在讲的那个字段时,
格子里没有东西可碰,26.6 单位的格距撞不到任何标签 —— 这种 32 位图留在 `900` 宽是对的,
省下来的横向预算可以换给同一张图里别的东西(引脚、灯、0/1 图例)。
换宽度就要按 §9 的一般式重算自己的高度上限:900 宽 / 1080 档是 533 单位,不是 480。

- 上限验算:1024 视口下 wide 档渲染 960px,`illustration-craft.md` §3 的上限是 960 × 1.13 = 1084;960 在限内。
- 渲染描边:1440 下 3.4 × 1280 / 960 = **4.53px**;1024 下 3.4 × 960 / 960 = **3.40px**。都过 3px 下限。
- 格距:(960 − 24 × 2) / 32 = 912 / 32 = **28.5 单位**,1440 下渲染 38.0px,1024 下 28.5px。
  13px 的两位数字宽约 14.3 单位(0.55em × 2),两侧各留 7 单位,装得下。
- 900 宽的对照:格距 (900 − 24 × 2) / 32 = **26.625 单位**,1440 下渲染 31.9px。
  格内塞两位数差 1.7 单位、不过;**格内空着(位号在格排上方)就没有下限要过** —— 同一个
  26.625 在两种画法下一个不合格、一个合格,可见这条量的是标签,不是位宽。
- 高度:300 单位 → 1440 下渲染 300 × 1280 / 960 = **400px**,离 640px 的
  `diagram-oversized` 门限还远(wide 档**且 viewBox 宽 960** 时,高度上限是 480 单位;
  这个 480 只对 960 宽成立,一般式见 §9)。
- 铺满(§9 那条):格排占 912 / 960 = 95% 宽;纵向内容要跨 ≥150 单位(50%),
  所以位号行 40、格排 60–130、字段括注 150–210、结论标签 260 —— 跨 220 单位 = 73%。

**8 位 / 16 位** → `viewBox="0 0 900 280"`,`.primer-container` 就够。
格距 (900 − 48) / 8 = **106.5 单位**(16 位时 53.25);描边 1440 下 4.08px / 1024 下 3.63px;
渲染高 280 × 1.2 = 336px。

## §2 时序波形(timing)

两根线上的先后次序。这张图的每一个横坐标都是一句工程断言。

### 必须画

- **时钟是方波,边沿竖直。** 一个周期 = 一段低 + 一段高,转换段 `dx = 0`(圆头描边已经给了
  1.7 单位的圆角)。要画斜边就控制在半周期的 8% 以内。
- **采样沿标出来,而且和协议一致。** 黄点(`#ffd23f`,r ≈ 7 单位)画在真正采样的那个沿上,
  一张图里黄只此一处(`illustration-craft.md` §9)。
- **数据线的有效窗口画成一段平台**,两端各一小段交叉("要变了 / 变完了"),平台正中才是可以采的部分。
- **每一行说清是谁在驱动。** SPI 里主机驱动 SCLK 和 MOSI,从机驱动 MISO ——
  优先在 figcaption 里一句说完(中文标签进图很贵,见下面的标签清单);
  只有一行的小图可以用箭头方向或一个中性缩写(`M→S`)在图里表示。
  **两边共用的那根线**(I²C 的 SDA、单总线)必须在换手的位置画一个交接标记,
  不然图在说一根线有两个主人 —— 而"谁在驱动这根线"是 §0 列进"一歪就是假话"的那一格。
- **建立/保持用一对双箭头 + 标注**:建立时间在采样沿**左边**(数据先稳住),
  保持时间在采样沿**右边**(采完才许变)。跨度 ≥24 单位,不然两个箭头头会叠在一起。
  ⚠ 24 单位在 88 单位的周期上占 **27%**,而真器件的建立时间通常只是周期的百分之几。
  这个放大是为了画得清,**代价是 figcaption 必须说一句"建立/保持的标注不按比例"**。
- **多信号纵向对齐靠一条 hair 竖线贯穿全部信号行。** 同一时刻在所有行上是同一个 x,
  这是"时序"这个词的全部含义。
- **片选/使能的边沿也要画。** 它什么时候拉低、什么时候放开,决定了这一帧从哪开始到哪结束。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 采样沿和声明的模式相反 | SPI mode 0 = CPOL 0(空闲时钟低)+ CPHA 0(每周期**第一个**沿采样),第一个沿就是上升沿。把黄点画在下降沿,读者按图接线会采到上一位 |
| 数据正好在采样沿上跳变 | 采样沿附近是禁止跳变的窗口,画成同时跳变等于告诉读者建立/保持时间不存在 |
| 明显的斜坡边沿(梯形时钟) | 时序图里的明显斜坡表示"这根信号的沿很慢"(模拟量 / 上电斜坡),不是时钟 |
| 时钟边沿抖动(手绘感) | 那就是时钟抖动 —— 一个真实存在、而且是要避免的现象。边沿、采样点一律不抖(§8 第 1 条) |
| 信号行各自为政、没有贯穿的时间线 | 读者拿不到"这两件事同时发生"这个结论,而这是时序图唯一要给的东西 |
| 建立时间画在采样沿右边 | 顺序反了。反了的时序图会让人把"提前准备好"理解成"采完再准备" |

### 违例 → 改写

❌ 标题写"SPI mode 0",MOSI 在上升沿跳变,黄点也落在上升沿:

> 数据和采样同时发生 —— 这在真硬件上是竞态。读者若照此写驱动,读回来的每一位都错一拍。

✅ mode 0 的真实次序,画成三句可以逐句核对的话:

> ① 空闲时钟为低,片选先拉低。② MOSI 在**下降沿**换成下一位,在上升沿之前稳住。
> ③ 黄点画在**上升沿** —— 采的是已经稳住的那一位。

⚠ 第一位是例外:它在**片选拉低时**就摆到线上了,前面没有下降沿可以换。
"每位在下降沿换"从第二位起才成立,压缩过的 figcaption 不许把这一条抹平:
"片选拉低后 8 个时钟,每个上升沿采一位;第一位在片选拉低时就摆好,之后每位在下降沿换。"

### viewBox

`viewBox="0 0 960 400"`,挂 `.primer-container primer-container--wide`。
升档的理由和 §1 一样是**横向分辨率**(8 个周期要 88 单位一个才画得开),
不是 `design-tokens.md` §6 的标签数或列数 —— 这张图只有 12 个标签。

- 描边:1440 下 4.53px,1024 下 3.40px(同 §1 的 960 档)。
- 横向排布:信号名栏 x 24–140;波形区 x 152–936 共 **784 单位** =
  片选先拉低的空拍 48 + 8 个周期 × 88 + 收尾 32。周期 88 单位,1440 下渲染 117px,1024 下 88px;
  半周期 44 单位,斜边上限 44 × 8% = 3.5 单位。
- 纵向排布:4 条信号行(片选 / 时钟 / MOSI / MISO),行距 76 单位,y 60–364;
  顶部 40 留刻度,底部到 382 留建立/保持标注。内容跨 342 / 400 = 86%,过铺满检查。
- 高度:400 → 1440 下渲染 400 × 1280 / 960 = **533px**,在 640px 门限内
  (wide 档、viewBox 宽 960 时的上限是 480 单位;一般式见 §9)。
- 标签清单(元素数,见 §8 第 2 条):4 个信号名(中性,各 1)+ 首末两位的位序号(中性,2)
  + 采样点 1 组双语(2)+ 建立/保持 2 组双语(4)= **12 个 `<text>`**,在 wide 档 18 的预算内。
  想给 8 位每位都写值就是 8 个额外元素 —— 只标首末两位。
- **驱动方写进 figcaption,不进图。** "主机 / 从机"是中文,画进图里每处要 2 个元素、四行就是 8 个,
  预算当场爆。图里只留中性的信号名,一句"SCLK 和 MOSI 由主机驱动,MISO 由从机驱动"放 caption ——
  这条规矩和它零成本的执行方式是一起的。

## §3 总线 / SoC 框图

"芯片里面有什么"。这张图存在的唯一理由是纠正"外设各有一根私线接到 CPU"这个默认想象,
所以总线本身必须是画面上最不像一根线的东西。

**这一节画的是共享总线**(APB 那一类:一条街,一次一笔,靠仲裁排队)。
交叉开关(AXI 那一类:几对主从同时走)是另一张图、另一套结论 ——
这份文件不给它画法,但**不许把这一节的结论套到它头上**,下面的禁止表里单列了一行。

### 必须画

- **主从分区。** 主设备(CPU、DMA)在上排,从设备(内存、UART、SPI)在下排,总线在中间。
  上下一分,"谁发起传输"就不用再写字解释。
- **总线画成一条街,不是一条细线。** 带高 **≥28 单位**(= 8 × 3.4 主线宽),内部平涂或 tint。
  每个设备从街上接一条**短支线**,而不是一根直达对面的长线。
- **figcaption 点明这是哪一种总线。** 一条街的画法画的是**共享总线** —— caption 里就要写
  "这张画的是一条共享总线,像 APB"。这一句是下面"一次只成交一笔"那条禁令能成立的全部前提:
  不写,读者会把共享总线的结论当成所有片上互连的结论。
- **两个方向分开画。** 地址与写数据向下,读数据向上,两条独立箭头,别合成一个双箭头。
- **地址空间画成门牌号段,而且定死一个方向**:这份文件定的是**低地址在下、往上递增**
  (`0x0000_0000` 在最下面),和内存映射表的通行画法一致。不重叠,每段贴一个起始地址。
  **方向要在 figcaption 里说一句** —— 高地址在下的画法同样有人用,
  所以"递增"本身不构成信息,图定了哪一头,字就得说同一头。
- **时钟域 / 电源域用极浅底色的背景区**(`--primer-violet-soft #efe9fc`,或调色板色 + `fill-opacity .12`),
  域边界用 hair 虚线沿区域边缘画出来,区域贴一个域名标签。
- **跨域的每个点都要显式。** 有箭头穿过域边界时,边界上画一个小方块标"同步";
  不想画同步块,就把边界画在没有箭头穿过的位置。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| CPU 各拉一根线到每个外设 | 这是点对点,不是总线。读者会得出"人人直连也行"的结论,而这一节就是要说明它为什么不行 |
| 在**一条共享总线**上同时画两笔传输 | 共享总线一次只成交一笔。画两笔等于说不需要仲裁 —— 而仲裁是这种总线的核心机制。**这条禁令只管共享总线**,见下一行 |
| 把共享总线的结论推广到 crossbar | 现代 SoC 的主干多是**交叉开关**(AXI 那一类):几对主从可以**同时**各走各的,每个从端口自己仲裁。这也正是它比一条街贵的地方 —— 硅面积换的就是这份并发。所以"总线一次只走一笔"是**这张图**的性质,不是片上互连的性质;想画交叉开关就画成网格,别画成街 |
| 把 DMA 画在外设那一排 | DMA 是**主设备**,它自己发起传输。画在下排等于抹掉了"外设也能自己搬数据"这件事 —— 而这正是 DMA 存在的理由。(它自己那组配置寄存器又让它同时是个**从设备**:一块东西可以有两个身份,画在上排指的是它搬数据时那个身份) |
| 从一个从设备画一条主动箭头去另一个从设备 | 从设备不发起传输。真会主动的那个东西,按定义就该画在上排 |
| 地址段重叠或倒序 | 地址空间是门牌号:重叠的号段在真硬件上是配置错误(**刻意做的镜像除外** —— 有的片子把同一块内存映射到两个号段,启动时的重映射也是真事,但那要在 caption 里说明是故意的),不是简化。倒序则是和图里定的方向不一致:定了低地址在下,就一路往上递增 |
| 一根线直接跨过时钟域边界 | 真硬件上那正是要打同步器的地方。画成直连等于说跨域可以随便连 |
| 从"睡着"的电源域里画出一条实线箭头 | 图在说"关了电还在发信号"。域睡着时,跨出它的箭头要断在边界上 |
| 给域区上第二个色相(黄或绿) | `illustration-craft.md` §9 一张图只留一个辅助色。域是背景,不该抢主体的紫 |

### 违例 → 改写

❌ CPU 居中,四根等长的线呈放射状连到四个外设:

> 画面读起来是"CPU 有四个口"。下一节讲"为什么不能人人直连"时,读者已经从图上学会了直连。

## §4 IP core 内部图(数据通路与控制通路)

一块能接上总线的积木,内部分两层:货走哪里、令从哪来。这两层在画面上必须一眼分开。

⚠ **先分清画的是哪一种 IP** —— 这一节后面几条规矩都跟着它变:

- **有独立数据口的 IP**(以太网 MAC、带 DMA 的控制器、视频流水线):货从数据口进出,
  寄存器只发令。下面的两层画法说的就是这一种。
- **数据就是一个寄存器的 IP**(PIO 式的 UART:收发都落在 `THR` / `RBR` 上,SPI 的 `DR` 同理):
  它**没有**独立数据口 —— CPU 每写一个字节就是往一个寄存器地址写一次。
  这种图**必须**把数据画成穿过寄存器,那才是它真实的样子。

### 必须画

- **一个外壳**,接口穿过外壳边框:寄存器接口(面向总线)· 数据口(**有独立数据口的 IP 才有**)
  · 时钟与复位。时钟与复位常被省掉,但它们是这块积木能不能接上去的前提,画一次比解释一句便宜。
- **数据通路是粗的一层**:一条平涂的带(宽 ≥20 单位)或 3.4 主线,从输入口穿过处理块到输出口,
  **一条主线走通**,不断开。
- **控制通路是细虚线的一层**:`class="primer-hair"`(1.8)+ `stroke-dasharray="2 9"`,
  从寄存器块或控制块指向数据通路上每一个被控的点。
- **寄存器块是 CPU 一侧的唯一入口**:CPU 一侧只有一条箭头,落在寄存器块上,不落在数据通路上。
  "唯一"限定在 CPU 那一侧 —— **数据口和 DMA 不经过它**,它们是另外的入口,
  所以上面那条"数据口也穿过外壳边框"才不和这句自相矛盾。
  PIO 式的 IP 只有 CPU 这一侧,那句"唯一"在它身上才是字面的唯一。
- **握手是一对反向箭头 + 状态标注**:valid 从源指向宿,ready 从宿指向源,
  上下错开 **≥22 单位**(渲染 26px),中间一行字写清成交条件。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| valid/ready 画成一个双向箭头 | 框图里的双向箭头意思是"这根线两个方向都走数据"。valid 和 ready 是两根各走一个方向的独立线,**两个同时为高的那一拍**才成交 —— 双箭头把这层意思整个删掉了 |
| **当这块 IP 有独立数据口时**,把数据流画成穿过寄存器块 | 读者会以为吞吐量要经过 CPU 的寄存器读写。数据口和 DMA 存在的全部理由就是不走那条路。**反过来同样是错**:PIO 式的 IP(数据就是 `THR` / `RBR` 那个寄存器)画出一条绕过寄存器的数据口,是凭空发明了一条硬件上不存在的路 —— 那种图必须画成穿过寄存器 |
| 控制通路只靠颜色区分(线宽线型不变) | 印成灰度或对色不敏感的读者眼里两条线就是一条。**线宽和线型要同时变**(3.4 实线 → 1.8 虚线) |
| 画成"valid 要等 ready" | 反了。源端不许因为对方没准备好就不举 valid;宿端可以等看见 valid 再举 ready。图上画出强制次序就把这条规矩说反了 |
| 一个写着 "FSM" 的空框 | 缩写没翻译(`explain-method.md` §1)。要么画出两三个状态圈和它们之间的箭头,要么就叫它"控制板" |
| 数据通路中途断开、靠箭头暗示接续 | 断开的通路在硬件里是另一回事(跨时钟的 FIFO、寄存的一级)。想画那个就画那个,别用断线当省略号 |

### 违例 → 改写

❌ 一条双向箭头,上面写 `valid/ready`:

> 读者拿到的信息是"这里有一根双向的线"。握手真正要教的"两边都同意才交出去",一个字都没传到。

✅ 两条错开的独立箭头 + 一行成交条件:

> 上面一条从左到右:`valid` —— "我这有一件,拿去。"
> 下面一条从右到左:`ready` —— "我这有空,来吧。"
> 中间一行:两个都举手的那一拍,东西才算交出去。

### viewBox

`viewBox="0 0 900 460"`,`.primer-container`。

- 描边:4.08px(1440)/ 3.63px(1024)。
- 高度:460 → 渲染 460 × 1080 / 900 = **552px**,在 640px 门限内,也在 900 宽 / 1080 档那条
  533 单位的上限内(见 §9 的一般式)。
- 排布:外壳 x 120–780 / y 60–400;数据带 y 250 一线横穿(带宽 20 单位,渲染 24px);
  寄存器块在外壳左上;控制虚线从寄存器块下引到数据带上的两个被控点;握手一对在右边框外,
  上下错开 22 单位。内容跨 60→420 = 360 / 460 = 78%,宽向 x 60→850 = 88%,过铺满检查。
- 标签清单:块名 3 个(中性)+ `valid` / `ready`(中性,2)+ 数据通路 / 控制通路 2 组双语(4)
  = **9 个 `<text>`**,在 1080 档 14 的预算内。

## §5 调用路径图

一次操作要穿过几层软件才碰到硬件。这张图靠**带**说话:带的数量就是答案。

### 必须画

- **五条等高的水平带**:用户态 / 系统调用 / 子系统 / 驱动 / 硬件。等高才让"每层花一步"读得出来。
- **每两条带之间一条贯通全宽的分界线** —— 五条带之间是 **4 条**界线,不是 5 条。
  用户态和内核态之间那条用 3.4 主线,**其余 3 条**用 hair ——
  这是全图唯一一条"要陷入内核"的边界,它值一次线宽差别。
- **带名贴左端**,每条一个双语标签。
- **去路箭头实线,每段只跨一条边界线**,箭尾在带 N 里、箭头在带 N+1 里,肉眼能看出它穿过了那条线。
- **返回路径虚线**(`stroke-dasharray="6 8"`),和去路错开,不与去路共用一条线。
- **硬件带里落到具体的东西**:一个寄存器名、一根引脚。落到一个写着"硬件"的空框等于没落。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 跨带箭头两端都在同一条带里,靠位置暗示跨层 | 读者数不出层数,而"要穿几层"是这张图的全部内容 |
| 跳层(用户态直接连到寄存器) | 普通程序走不到寄存器 —— 要走 `/dev/mem`、UIO、VFIO 这类特权口子才行,而这页讲的是普通那条路。别把它说成"用户程序不能直接写寄存器":那条路存在,DPDK 一类的东西天天在走。图上跳一层,正好替读者确认了这页要纠正的那个误解 |
| 返回箭头和去路合成一条双箭头 | 返回值和数据不是同一件事,而且返回发生在后一个时刻。双箭头把时间抹平了 |
| 返回箭头的起点和页面说法不一致 | 缓冲的 tty 在驱动把字节排进队列时就返回了,字节还没出引脚;直接写寄存器的设备才是写到硬件才返回。**两种都真实存在**,但图和字不许说两件事 —— 讲队列就从驱动带起,讲直写就从硬件带起 |
| 带高不等且没有理由 | 高的那条带会被读成"这层更重要 / 更慢",而这不是图想说的 |
| 边界线抖动 | 边界的位置就是层的位置(§8 第 1 条) |

### 违例 → 改写

❌ 一条长箭头从最上面的命令行直插到最下面的寄存器:

> 图在说"敲一行命令就写到了寄存器"。三层内核代码消失了,而这三层正是这页要讲的东西。

✅ 四段箭头,每段只跨一条边界:

> ① 命令 → `write` 进内核(穿过那条加粗的用户态/内核态边界)
> ② `write` → tty 层(子系统带里找到这台设备的驱动)
> ③ tty 层 → 驱动(驱动带)
> ④ 驱动 → 发送寄存器(硬件带,落在一个真的寄存器名上)
> 返回虚线从驱动带起,回到命令那一带 —— 因为这页讲的是"排进队列就返回"。

### viewBox

**工作档是 `viewBox="0 0 960 440"` + `.primer-container primer-container--wide`。**
这是最吃标签预算的几张之一,而且**它吃不进 1080 档** —— 先看清单再看几何。

- 标签清单(按这一节自己要求的东西数,不是按最省的画法数):
  5 条带名双语 = 10 + ✅ 那条路径的 **4** 段步骤号(中性)= 4 +
  硬件带里那个落点(寄存器名或引脚名,中性)= 1 → **最少 15 个 `<text>`**。
  再加上"返回"这一组双语(2)、路径上写出来的调用名(`write` 一类,中性,每个 1),

  (对比一下:`960 470` 渲染 627px,只剩 13px —— 比 §9 那条"只剩 16px 所以不要用"的例子还紧。

- 只讲三步、不写落点名的简版可以留在 1080 档的 `900 480`(渲染 576px,13 个标签)。
  但那就不是这一节要求的图了 —— 硬件带落到空框这条是 §10 第 5 条会问的。

## §6 算法 / 数学图

抽象量的变化。这里的诱惑是把整个过程塞进一张图,然后用箭头把它缝起来。

### 必须画

- **状态快照序列:每步一张小图,并排一行。** 读者看的是"从这张到那张变了什么",
  这个差别只有在两张图挨着时才看得见。
- **被淘汰的部分留在原位、改成 hair 空心**(1.8 描边 + `fill="none"`),不删掉。
- **每张快照下面一个剩余量的数字**,并且这些数字要真的对得上(见下面的算术)。
- **数量给实物参照**(`explain-method.md` §3),而且参照物算得对。
- **前置条件画出来。** 二分查找要求先排好序 —— 排好序这件事要么在图里看得见(卡片是递增的),
  要么单独一节讲。它不是细节,它是这个算法能成立的前提。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 一张大图塞五步,用箭头缝起来 | 箭头会长到跨过半张图,而"每次砍一半"这个节奏在一张静态大图里读不出来 |
| 把淘汰的一半从图上删掉 | 读者看到的是"数据变少了"。真实情况是一行数据都没少,少的是**还要看的范围** |
| 用降低对比度的办法做"淘汰"效果 | 淡化的文字过不了 axe 的对比度检查(`design-tokens.md` §7)。**要淡就淡图形,不淡文字** —— 一个数字要么用 `--primer-mut`(纸上 5.97:1),要么干脆不写 |
| 剩余量的数字凑整 | 一个算错的参照物比裸数字更糟:读者会不再相信这页的其它数字(`explain-method.md` §3) |
| 省掉"必须先排好序" | 没排序时每次比较不给任何关于该去哪一半的信息 —— 算法直接不成立。这不是细节,是前提 |

### 违例 → 改写

❌ 一张图,五个箭头,中间三步的卡片被擦掉:

> 画面在说"数据被删掉了"。而二分查找一行都不删,它只是不再看另一半。

✅ 五张并排快照,淘汰的一半留在原位改成空心:

> 2000 万 → 1000 万 → 500 万 → 250 万 → 125 万,每张下面一个数。
> **第一张是起点,不是一刀** —— 五张之间只有 **4 刀**。
> 五张之后再给一句结论:再这么砍 **21** 次就只剩一张 —— 一共 25 次。

⚠ 这里最容易错一个:**五张快照 = 四次对折**,不是五次。数快照会把总数多算一次。

算术要摆出来才站得住:

- 总次数:2²⁴ = 16 777 216,不到 2000 万;2²⁵ = 33 554 432,够了。所以 **25 次**。
- 四刀之后剩多少:2⁴ = 16,2000 万 / 16 = **125 万**,和第五张快照上的数一致。
- 还要几刀:2²⁰ = 1 048 576 < 125 万 ≤ 2²¹ = 2 097 152,所以还要 **21** 次。
- 对得上:4 + 21 = **25**。

实物参照:一张 0.1mm 的纸对折 25 次,厚度是 0.1mm × 2²⁵ ≈ **3.4 公里** ——
比世界第一高楼叠四座还高(828m × 4 = 3312m)。翻倍这件事有多快,这句话比"指数增长"有用。

### viewBox

`viewBox="0 0 900 320"`,`.primer-container`。

- 描边:4.08px(1440)/ 3.63px(1024)。
- 五格排布:(900 − 24 × 2) / 5 = **170.4 单位**格距 → 面板宽 150 + 间隙 20.4。
  面板渲染宽 150 × 1.2 = 180px(1440)。
- 高度:320 → 渲染 **384px**。内容 y 60→282 = 222 / 320 = 69%,宽向 852 / 900 = 95%,过铺满检查。
- 标签清单:5 个剩余量数字(中性)+ "剩下" 1 组双语(2)+ "已淘汰" 1 组双语(2)
  = **9 个 `<text>`**,在 1080 档 14 的预算内。
- ⚠ 图内标签的字号仍按整张 viewBox 换算,不按小面板换算:13px 源字号在 900 / 1080 档
  渲染 15.6px,和全宽图一样宽裕。**小面板不会让字变小,别因此把字号压下去。**

## §7 两边不是一套门牌号(互连 + 地址带)

这一节回答的是**一个**问题:两块芯片之间有一根线,程序能不能拿一个指针直接读到对面。

答案不在线里,也不在内存里,而在**两边各自的门牌号本**上 —— 而这恰恰是读者默认想错的地方:
线连上了,大多数人就以为"能读了"。所以这张图必须把**线路图**和**门牌号图**画在同一张纸上,
中间用一条箭头把它们缝起来。分成两张图,这一步就要读者自己在脑子里把两半对上,而这一步就是全部难点。

**比喻先行(primer 的硬规矩,`explain-method.md`)**:两个小区各自从 1 号开始编门牌。
修一条路把它们连起来,门牌号并不会因此合并 —— A 小区的 5 号还是 A 的 5 号。
想让 A 的住户直接按自己的门牌本找到 B 的某栋楼,得**在 A 的门牌本上给那栋楼另开一个号段**。
图里那块斜纹,画的就是这个"另开的号段"。比喻卡里就写这一句,别写"地址空间映射"。

### 必须画

- **两条地址带,横着放,上下错开,永不合并成一条。** 每条带贴一个"这是谁的门牌本"的标签
  (`CPU 看到的` / `加速器看到的`)。合成一条带、中间画根竖线隔开 —— 那是在说"同一本册子的两半",
  意思正好反了,而且这恰好是读者本来就有的错误想象。
- **同一块内存在两边写出两个不同的起始地址。** 这是全图唯一必须出现的一对数字,
  也是"两套编号"这句话的证据。只画带、不写数字,读者会以为你只是画了两遍。
  数字用中性标签(`0x8000_0000`),不挂 lang class,占 1 个额度(§8 第 2 条)。
- **"另开的号段"用斜纹平涂,不用新颜色。** 45° 斜线、`--primer-ink` 墨色、`stroke-width 2`、
  间距 6–8 单位。**颜色那一格已经被"这是哪种内存"占掉了**(`illustration-craft.md` §9:
  一张图只留一个辅助色),斜纹是另一条通道,可以叠在任何颜色上而不抢它。
  给窗口段换个鲜艳色,等于把两件事塞进一个通道,读者只能二选一地读。
- **一条箭头,从发起访问的那一块出发,落在带里的某一段上。** 这条箭头是全图的**主体**,
  所以它是紫的(§8 第 3 条:一张图一个主体,主体是紫的)。**落点必须是某一段,不是整条带** ——
  落在整条带上,这句话就退化成"CPU 能访问内存",等于什么都没说。
- **互连线的名字压在线上,做成一颗药丸**(圆角矩形 + 平涂底 + 中性标签)。线会拐弯、会交叉,
  名字写在线**旁边**归属就不确定;压在线**上**,归属由位置定死。
- **figcaption 把箭头的结论说成一句人话**:"CPU 用一条普通的读指令就能读到这一段,
  不用先搬一份"。图上有箭头、字上没有结论 = 读者还是不知道能不能直接递指针。
  段宽不按容量比例时,也在这里说一句(§10 第 12 条)。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 两条带合并成一条 | 在说两边编号是同一套 —— 这正是这张图要纠正的那个误解 |
| 只画拓扑,把地址范围当一行小字写在方块里 | 门牌号是**每边一本**;写进同一个方块等于宣布只有一本 |
| 窗口段换成另一个鲜艳色 | 抢掉了"这是哪种内存"那条通道,两件事都读不出。斜纹和颜色是两条正交的通道 |
| 紫的箭头画两条(两边各一条) | 一张图一个主体。两条紫等于说两件事同等重要,而这一节只回答一个问题 |
| 把两边的门牌号写成同一个数 | 那就没有这张图了。两个不同的起始地址是这张图唯一的证据 |
| 段与段之间的分界画成抖动的手绘线 | 门牌号段的边界是精确的。承载意义的几何不抖(§8 第 1 条) |
| 一张图画三个以上节点 | 标签预算 1080 档 14 个,两个节点 + 两条带就已经用掉 13 个。第三个节点必须拆图 |
| 药丸盖住箭头的落点 | 落点是这张图的结论所在,不许被任何东西压住 |

## §8 九类共通的六条

技术主题不给 primer 的规矩打折。反过来,有六条在技术图上要收得更紧。

1. **承载意义的几何不抖。** `illustration-craft.md` §5 的手绘抖动只许出现在外壳和背景面板上。
   位域格线、时钟边沿、采样点、分层带边界、箭头端点 **一律不抖** ——
   抖动在这些位置上不是手绘感,它本身就是一个工程现象(时钟抖动 / 位错位)。
2. **标签预算数的是 `<text>` 元素,不是"看得见的标签"。** 双语标签是两个元素,一句话占 2。
   canonical 库最密的一张图是 12 个元素(6 组双语),1080 档的上限是 14
   (`illustration-craft.md` §7)。技术图能画得下去全靠一件事:**数字和信号名两种语言同形**
   (`31` / `SCLK` / `valid`),写一个 `<text>`、不挂 lang class,占 1 个额度。
   叙述性标签压到 2–3 组双语,剩下的额度全留给数字和信号名。
   ⚠ **省下来的中文要在 figcaption 里还上。** `valid` / `SCLK` / `THR` 只有英文形,
   图里省掉的那半句得在 caption 的中文里给出对照("`THR` 就是发送保持寄存器,数据从这儿出去")。
   design-copy-critic 查的是整页的中英对等,图里省了、caption 里也没有,那就是真的少了一半。
3. **一张图一个主体,主体是紫的。** 技术图里的"主体" = 正在讲的那个字段 / 那个沿 / 那个模块。
   第二处紫会让读者以为两处同等重要,而这一节只回答一个问题(`explain-method.md` §6)。
4. **黄只圈一处,且不与绿同图。** 技术图的黄归"这里就是要看的那个点":采样点、正在读的那一格。
   **别拿黄去区分字段** —— 那是把马克笔当填充色用,而且立刻违反 §10 的色序。
5. **三层结构照旧:轮廓 3.4 + 平涂 + hair 细节。** 一排空格子是表格不是插画。
   hair 层在技术图里就是刻度、斜线、栅格、引脚、螺丝孔 —— 少了它,图是干净的,也是空的。
6. **`aria-label` 写工程结论,figcaption 复述图里的每个数字。** 屏幕阅读器用户只拿到 `aria-label`
   那一句:"一张时序图"给不了任何东西,"片选拉低后 8 个时钟、每个上升沿采一位"给的是全部内容。
   figcaption 那份复述是给手机读者的 —— 375 视口下栏距降到 20px(`primer.css` Section L),
   内容宽只剩 375 − 20 × 2 = **335px**,13 单位的图内标签渲染 13 × 335 / 900 = **4.8px**
   (960 宽的图 4.5px)。**那已经不是"小",是读不了** —— 数字必须在 caption 里能读到
   (canonical `process` 就是这么做的)。

## §9 viewBox 一览(每格都是算出来的)

`illustration-craft.md` §3 的两条公式,这份文件全部数字都从它们来:

```
渲染描边 = 3.4 × 渲染宽 / viewBox 宽        （下限 3px）
渲染高   = viewBox 高 × 渲染宽 / viewBox 宽  （上限 640px，diagram-oversized）
```

渲染宽取两个审查视口里更窄的那个算描边(1024),取更宽的那个算高度(1440)。
`.primer-container` 在 1440 下渲染 1080 / 1024 下 960;`--wide` 在 1440 下 1280 / 1024 下仍是 960。

把第二条公式反解一下,就是**高度上限的一般式** —— 这份文件里所有"上限 N 单位"都是它的一个取值:

```
viewBox 高 ≤ 640 × viewBox 宽 / 渲染宽
```

**它同时取决于两个数,不是容器档一个。** 所以 533 和 480 都不是档的常数:

| viewBox 宽 | 容器档(渲染宽 @1440) | 高度上限 |
|---|---|---|
| 900 | 1080 档 | 640 × 900 / 1080 = **533 单位** |
| 960 | `--wide`(1280) | 640 × 960 / 1280 = **480 单位** |
| 800 | 1080 档 | 640 × 800 / 1080 = **474 单位** |

第三行就是这份文件最容易踩的坑:一张 800 宽的 viewBox 放进 1080 档,缩放比是 1080 / 800 = 1.35,
533 单位渲染 533 × 1.35 = **720px** —— 早就越线了,而"1080 档上限 533"这句话会说它安全。
**改 viewBox 宽度和改容器档一样,都要重算高度上限。**

(`diagram-oversized` 本身比 640 这条线宽松:它只看 `figure svg` 里带 ≥3 个 `<text>` 的图,
级别是 warn 而不是 error,同一页有 ≥4 张图时还多一条相对臂 —— 高过本页中位数 2.5 倍也报,
`figure` 上加 `data-allow-tall` 还能显式豁免。**640 是自律线,不是它一定会拦住你的那条线** ——
所以别指望机械检查替你发现算错的高度。)

| 图 | 容器档 | viewBox | 描边 @1440 / @1024 | 渲染高 @1440 | `<text>` |
|---|---|---|---|---|---|
| 位域(32 位) | `--wide` | `960 300` | 4.53 / 3.40 | 400px | ≤18 |
| 位域(8/16 位) | 1080 | `900 280` | 4.08 / 3.63 | 336px | ≤14 |
| 时序波形 | `--wide` | `960 400` | 4.53 / 3.40 | 533px | ≤18 |
| 总线 / SoC | 1080 | `900 470` | 4.08 / 3.63 | 564px | ≤14 |
| 互连 + 地址带(2 节点) | 1080 | `900 470` | 4.08 / 3.63 | 564px | ≤14(§7 实算 13,只剩一个额度) |
| IP core 内部 | 1080 | `900 460` | 4.08 / 3.63 | 552px | ≤14 |
| 调用路径(5 带,**工作档**) | `--wide` | `960 440` | 4.53 / 3.40 | 587px | ≤18 |
| 调用路径(简版,只讲三步) | 1080 | `900 480` | 4.08 / 3.63 | 576px | ≤14(§5 的完整画法装不进) |
| 算法快照(5 格) | 1080 | `900 320` | 4.08 / 3.63 | 384px | ≤14 |
| hero(技术页也一样) | hero 右栏 | `500 340` | 3.57 / 3.15 | 357px | ≤4 |
| 协议分层(3 层双侧) | `--wide` | `960 440` | 4.53 / 3.40 | 587px | ≤18(§11 实算 17,只剩一个额度) |
| 纵向地址映射(2 本) | `--wide` | `960 440` | 4.53 / 3.40 | 587px | ≤18(§12 实算 17,只剩一个额度) |
| 比喻卡 | 卡内图栏 | `180 150` | 3.25 / 3.25 | 143px | **0** |

窄视口的描边不用自己管,但**有一个前提**:960 档由 primer.css 的
`svg[viewBox^="0 0 960 "]` 自己认出来,页面什么都不用写;上表之外的宽度
(裁过的 viewBox、936 这种)要在 `<figure>` 上写一次 `style="--primer-vbw: 936"`,
不写的话窄视口那几档会按 900 算,渲染出来细 6.7%,在 481 / 661–695 / 901–911
三段跌破 3px 下限(`illustration-craft.md` §3、`known-bugs.md` §8.2 有实测值)。

四条从这张表读出来的规矩:

- **上限是一对数算出来的,不是一个档的常数。** 上面那张表里的 533(900 宽 / 1080 档)和
  480(960 宽 / wide 档)是这份文件用到的两个取值,别把它们当成档的属性搬去别的宽度。
  canonical 的 `900 520` 渲染 624px,离门限只剩 16px —— 所以工作值取 ≤500。
- **换档要连 viewBox 宽度一起换。** 900 宽的图升到 wide 档,同一个 480 单位从
  480 × 1080 / 900 = 576px 涨到 480 × 1280 / 900 = 682px,也就是 **+18%**,当场越线。
  (42% 是 1280 / 900 这个单位→像素的换算比,**不是**高度的涨幅 —— 两个档的比才是
  1280 / 1080 = 1.185。混用这两个数会让人以为 480 单位在两个档里都安全。)
  宽度提到 960 才把高度按回来:480 × 1280 / 960 = 640px,正好压在线上,所以工作值再收一档。
- **hero 图仍是实物,不是原理图。** 技术页的 hero 画那颗芯片、那两块板子、那根线;
  位域和波形留给节内的全宽图。hero 的 500 宽 viewBox 装不下 32 个格子,
  硬装的结果是格距 14 单位、位号 6px。
- **换了 viewBox 宽度或容器档,描边和高度都要重算,两端都算。** 高度按上面那条一般式;
  描边按 `值 × 内容宽 / 设计宽度`,每一个受影响的断点档两端各算一次。
  "另一个宽度是好的"推不出这个宽度也好 —— 960 掉出下限、900 没掉,就是这么来的。

## §10 画完自查(先过工程,再过工艺)

工程七条 —— 一条不过就是在教假话,机械检查不会替你发现:

1. 位序方向和标注一致?两端都标了位号?字段跨度写成 `[高位:低位]`?字段宽度和位数成比例?
2. 采样沿和声明的模式一致?数据没有在采样沿上跳变?建立时间在沿的左边?
   **每一行是谁在驱动,说清了**(图里或 caption 里)?共用线的换手位置有交接标记?
3. 总线是一条街、设备接短支线?主设备都在上排(DMA 也在)?地址段按图里定的方向递增、不重叠?
   **figcaption 点明了画的是共享总线**(而不是把"一次一笔"推广到交叉开关)、也说了地址的方向?
4. 握手是两条独立反向箭头 + 成交条件?控制通路的线宽**和**线型都和数据通路不同?
   CPU 一侧的箭头只落在寄存器块上?**先确认画的是哪种 IP** —— 有独立数据口的不许让数据穿寄存器,
   PIO 式的(数据就是 `THR` / `RBR`)反过来必须穿。
5. 每条跨带箭头只跨一条边界、肉眼能看出穿过?没有跳层?返回路径的起点和页面的说法一致?
   五条带之间是 4 条界线(只有一条是主线)?硬件带落在一个真的寄存器名或引脚上?
6. 快照的剩余量逐张对得上?总次数和 2 的幂算对了(**快照张数 − 1 = 砍的次数**,别多算一刀)?
   "必须先排好序"画出来了?
7. 两条地址带是分开的两条、中间留着空白?同一块内存在两边**写出了两个不同的起始地址**?
   紫箭头**落在某一段上**而不是整条带?斜纹段没有换成另一个颜色?
   figcaption 里有那句人话结论(能不能直接读)、以及"段宽不按比例"那句?

工艺五条 —— 转去 `illustration-craft.md` §10 走完整版,这里只列技术图特有的:

8. 承载意义的几何(格线 / 边沿 / 边界 / 号段界线 / 采样点)一处没抖?
9. `<text>` 元素数在预算内?数字和信号名都是**中性**标签(没挂 lang class,没写两遍)?
   只有英文形的名字在 caption 里给了中文对照?
10. 紫只有一处主体?黄只有一处、且没有和绿同图?
11. 渲染高度在 640px 以内?**上限按 640 × viewBox 宽 / 渲染宽 重算过**(改了容器档或 viewBox 宽度都要重算)?
12. 省掉的东西在 figcaption 里说了一句(不按比例的标注也算)?没有拿真型号给一张示意图盖章?

## §10.5 为什么 primer 没有 glyphs.svg

anthropic / apple / glass 各有一份 `templates/diagrams/glyphs.svg` 构件片段集
(队列梳齿 / 字节尺 / 插槽排 / 端口贴边 / 器件卡 / AC 耦合 / 同步块 / 斜纹),
**primer 不做这一份**,这是决定不是遗漏:

- 那三家的字形是**示意符号** —— 一个梳齿矩形代表"深度有限的队列",靠约定读。
  primer 的构件是**插画**:三层结构(轮廓 3.4 + 平涂 + hair 细节)画出来的一个真东西,
  靠"它长得就像那样"读。同一个队列,在 primer 里是一排看得见的格子,不是梳齿符号。
- 真要用那套符号,`illustration-craft.md` 的三层结构已经在管它们该长什么样了,
  再出一份片段集只会多一处要同步的地方。
- 需要"这是一个有限队列"这种承诺时,照 §6(算法 / 数学图)画格子阵列 —— 那一节本来就是干这个的。

## §11 协议分层对等图

> 编号接在 §10 之后 —— §1–§7 是先有的七类,§8–§10 是共通规矩,新加的两类顺号排在最后,
> 不打乱文件里既有的十几处交叉引用。

"传输层和对方的传输层通信" —— 教材都这么写,读者据此想象出来的是**两个传输层之间有一条通道**。
于是他去问"传输层的线在哪""为什么示波器抓不到 DLLP"。
真相是:**横向那条线一根都不存在,字节全程只走纵向**,唯一真实的横向连接在最底下那一层。
这张图就是为纠正这一句而存在的。

### 必须画

- **两侧各一摞,层数相同、每层左右两块高度相同、同名层的 y 坐标严格相同。**
  坐标一致就是"对等"的几何表达 —— 两侧错开半格,"对等"在图上就没有依据了。
- **层名放中间那一列的气泡里**(`--primer-violet-soft #efe9fc` 圆角胶囊),不放进两侧的方块里。
  放进方块会被读成"这一层的第一个部件";放中间还顺带**把上面两层的横向虚线截断** ——
  截断本身就在说"这里过不去"。
- **每个方块里要有一个真名**(`TLP` / `DLLP` / `128b/130b`),不是空框。
  空框在说"这层什么都不做"。这三个词都是**同形标识符**,一个 `<text>` 一个额度(§8 第 2 条),
  这也正是这张图能在 18 个额度里画完的原因。
- **上面几层之间画 hair 虚线,而且必须在中间断开**;最底下一层**不画横线**,
  改成从左块底下拉一根**主线宽的实线**,横过去,再升进右块。
  全图唯一一根从左连到右的实线 —— 这就是结论本身。
- **黄只圈那根真线**(§8 第 4 条:黄归"这里就是要看的那个点")。
- **紫箭头顺左边一层层往下、过那根线、顺右边一层层往上。** 主体是紫的(§8 第 3 条),
  而这张图的主体就是"字节实际走的路"。
- **figcaption 必须写出那句人话**:"上面两层的横线是双方说好的规矩,不是线;
  字节是从左边一层层下去、过一次线、再一层层上来的。"

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 上面几层之间画实线(哪怕细) | 直接宣布同层之间真有一根线 —— 这正是本图要纠正的误解 |
| 只画一侧那一摞 | 对等关系没地方画,图退化成"分了三层"的普通框图,全部价值消失 |
| 紫箭头从传输层直接连到最底层 | 分层的全部意义就是不许跳。跳一次,读者就学会了可以跳 |
| 方块里只写层名、不写部件 | 层名已经在中间的气泡里了;方块再写一遍等于这层没内容 |
| 两侧层高不等 | 高的那层会被读成"更重要 / 更慢",而这不是图要说的 |
| 黄圈在层名或某个方块上 | 黄一旦不只一处就不再是"看这里";而这张图要看的是最底下那根线 |

### 违例 → 改写

❌ 三条横线把左右两摞逐层连起来,粗细一样:

> 图在说"每一层都和对面直接连着"。读者会去找传输层的那根线,找不到就以为自己漏了什么。

✅ 上面两层的横线画成 hair 虚线**并且在中间断开**(层名气泡坐在断口里),
最底下一层的两块之间不画横线,改成一根实线从左块底部落下、横过去、升进右块,黄条压在它下面:

> "只有最下面这根是真的"从画面本身出来。紫箭头顺着左边下去、过这根线、再顺着右边上去,
> 读者不用读字就知道字节走了哪条路。

### viewBox

`viewBox="0 0 960 440"` + `.primer-figure primer-fig-wide`。

- 描边:1440 下 3.4 × 1280 / 960 = **4.53px**,1024 下 3.4 × 960 / 960 = **3.40px**。
- 高度:440 → 渲染 440 × 1280 / 960 = **587px**,在 640 门限内(960 / wide 档的上限是 480 单位,§9)。
- 纵向:三层各 92 单位(y 40 / 160 / 280),层间 28 单位的空隙**同时给紫箭头用** ——
  空隙收到 20 以下,箭头就画不出"穿过去"的样子了。真线在 y 398,底部留 42。
- 标签清单:3 个层名双语 = 6 + 6 个部件同形名 = 6 + `PCIe lane` = 1 + 两句注双语 = 4 → **17**,
  wide 档上限 18,只剩一个额度。**要加第四层就得砍一句注**,别指望还能加标签。

## §12 纵向地址映射图

一段内存被 MMIO 空洞盖住之后,BIOS 会把它挪到高处重新露面 —— 同一块 DRAM,两个门牌号。
这件事光靠文字说不清,因为读者脑子里只有一本门牌本;而这里有**两本**。

§7 画的是"互连 + 地址带",要回答"字节走哪根线";**这一张不画拓扑,只画编号本身**,
回答"这个号落在哪儿、在另一本里叫什么"。

### 必须画

- **两本竖着的门牌本,低地址在下**(和 §3 定的方向一致),**方向要在 figcaption 里说一句**。
- **引线指的是分界线,不是某一段。** 这是本图型的签名动作,理由是语义的:
  **分界是一个地址,段是一个范围**。把 `TOLUD` 写在某段中间,读者无法判断它指的是这段的
  起点、终点还是长度 —— 三种读法都讲得通,而只有一种对。引线从分界处水平拉出去,
  标在本子外面的空白列里;段名写在段内居中,两者不在同一列,谁也不占谁的位置。
- **右边那本要比左边短。** 地址空间比内存条大是事实,画成一样高就是在说它们一样大。
- **被盖住的那一段和搬上去的那一段,用一条紫线连起来,写"重映射"。**
  这条线是全图的主体(§8 第 3 条)。
- **空洞用斜纹,不换颜色**(§7 同款规矩:颜色已经在说"这是哪类",斜纹说"这不是内存")。
- **黄只给搬上去的那一段** —— 全图最反直觉的就是它。
- **figcaption 复述每个门牌号**,并说明"段高不按比例"(§8 第 6 条)。

### 禁止

| ❌ 别画 | 它教错了什么 |
|---|---|
| 门牌号写在段的中间 | 起点 / 终点 / 长度三种读法都成立,读者只能猜 |
| 两本画成一本、中间加一条粗线隔开 | 粗线读作"同一本里的两段",而这里是两套编号 —— 意思正好反了 |
| 两本一样高 | 在说地址空间和内存条一样大 |
| 空洞换一个鲜艳颜色 | 颜色在编码"这是哪类内存";换色等于把两件事挤进同一个通道 |
| 黄同时圈住两段(搬走前 + 搬走后) | §8 第 4 条:黄只一处。两段的关系交给那条紫线,不是再点一次黄 |
| 把 `TOLUD` 的引线画到空洞的顶上 | `TOLUD` 是**低端可用内存的顶**,也就是空洞**开始**的地方。画到空洞顶上,读者会照着这个数去算空洞大小,算出来的是负数或者错一个 GiB |

### 违例 → 改写

❌ 一条长带子,中间用一条粗线把"系统看到的"和"内存条上的"隔开:

> 粗线在这里读作"同一本本子的两段"。整张图想说的"两套编号"当场消失。

✅ 两本分开画,中间留出空白,一条紫线从右本的那一段拉到左本的那一段,写"重映射":

> 空白本身就在说"这是两本";紫线落在**某一段上**而不是整本上,才说得出"就是这一段搬上去了"。
> figcaption 收一句:"同一块内存,在内存条上它在 3–4 GiB,在系统眼里它在 TOUUD 上面 —— 换了个号,不是多了一块。"

`viewBox="0 0 960 440"` + `.primer-figure primer-fig-wide`。

- 描边:同 §11,4.53 / 3.40px。
- 高度:440 → 渲染 **587px**,在门限内。
- 横向四列:标号列 0–96 · 左本 150–430 · 映射区 430–620 · 右本 620–900。
  左本 y 40–380,右本 y 120–380(短一截 = 内存比地址空间小)。
- 标签清单:两本标题双语 = 4 + 段名(`DRAM` ×3 同形 + `MMIO` 同形)= 4 +
  两段说明双语 = 4 + `重映射` 双语 = 2 + 三个门牌号同形 = 3 → **17**,只剩一个额度。
  **想再标一条分界就得先砍一句说明。**
