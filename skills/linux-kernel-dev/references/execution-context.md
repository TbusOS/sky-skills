# 执行上下文 — 下结论前先拿到"这行什么时候跑"

> 配套可执行检查:`scripts/show_guard_chain.py <file>:<line>`(或 `--grep <pattern> <path>`)
> 相关:`api-contract-change.md`(改接口前枚举调用点)· `bsp_discipline.md`(改动 4 维度)· `dos-and-donts.md`

何时读本文:**任何"从搜索结果推断系统行为"的场合** —— grep 到一行就要据此判断
"这个功能有没有生效""这条路走不走得通""该往哪改"。

## 1. 病灶:grep 返回的是行,语义住在块里

```
grep 命中一行
  → 「这行存在」
  → 脑子自动补一句「所以它会跑」        ← 这一步没有任何证据
  → 结论
```

那句自动补的话就是全部错误的来源。一行代码是否执行、什么时候执行、执行几次,
**全部由包着它的块头决定**,而块头不在 grep 的输出里。

## 2. 没有这条纪律会怎样

不是"结论略有偏差",是**结论直接反向**:

| 真实情况 | 漏看守卫后的结论 | 后果 |
|---|---|---|
| 事件触发器,每次条件成立都重跑 | 「开机跑一次」 | 以为状态是静态的,据此设计缓存 / 单次初始化 |
| `#ifdef` 未开启,根本没编进去 | 「这功能有」 | 花几天调一段不存在的代码 |
| 被 `if (flags & X)` 挡住,X 从没置位 | 「这行会执行」 | 排查方向整体跑偏 |
| `depends on` 不满足,配置项不可见 | 「配了就生效」 | defconfig 改了没反应,反复怀疑编译系统 |

**架构判断错一次,后面所有设计都建在错前提上。** 这是比编译错误昂贵得多的一类错误 ——
编译错误当场报,前提错误要到板子上才暴露,而且暴露时表现为"功能间歇性失效",最难查。

## 3. 三个必答问题(顺序不能换)

```
① WHO   —— 谁执行它?(哪个进程 / 子系统 / 上下文)
② WHEN  —— 什么条件下执行?一次性?周期?事件驱动?重入吗?
③ ELSE  —— 条件不成立时走哪条路?那条路是不是才是常态?
```

**最常见的失败不是三个都不问,而是拿 ① 的答案当 ② 的答案。**

查清"只有 X 写这个节点"(WHO)之后,很容易顺口说出"所以 X 启动时写一次"(WHEN)——
可 WHO 的证据完全没有覆盖 WHEN。这两个问题的证据来源是**不同的行**:
WHO 在命中行上,WHEN 在块头上。

③ 同样要紧:很多时候 else 分支才是实际走的那条,而它离命中行有几十行远,
不主动去看就永远看不见。

## 4. 块结构语言清单(grep 单行必失真)

BSP 工作天天跨这几层,每一层都是块结构:

| 位置 | 块头长什么样 | 漏看会怎样 |
|---|---|---|
| **Android init `.rc`** | `on <trigger>` / `service <name>` | 事件触发当成开机一次性,或归错触发器 |
| **C / C++** | `#if*` · `if` · `for` · `while` · `switch` | 条件执行当无条件;未编译的代码当活代码 |
| **Kconfig** | `config` + `depends on` · `if` · `menu` | 以为配了就生效,实际选项根本不可见 |
| **Makefile / `.mk`** | `ifeq/ifneq/ifdef` · `<target>:` | 以为文件参与编译,实际那条 `obj-y` 在未成立的分支里 |
| **DTS / DTSI** | 节点层级 · `status = "disabled"` | 属性归错节点;整个节点被 disable 却当它在跑 |
| **Shell** | `if` · `case` · 函数体 | 分支里的命令当成必然执行 |
| **SELinux `.te`** | `domain` 上下文 | 规则归错域 |

共同点:**块头与被守卫的行,可以相隔任意远**,而且常常长得完全不像 —— 一个 `on property:` 和
一个 `write` 之间没有任何词法关联,grep 任一个都不会带出另一个。

## 5. 可执行检查

```bash
scripts/show_guard_chain.py <file>:<line>                 # 单点
scripts/show_guard_chain.py --grep <pattern> <path>...    # grep + 每个命中都出守卫链
scripts/show_guard_chain.py --selftest                    # 自检(含判别力测试)
```

输出把守卫按 **BUILD-TIME**(预处理)/ **RUNTIME COND**(运行期条件)/ **EVENT TRIGGER**(事件)/
**DEPENDS**(配置依赖)分类,并给每一层的 `file:line`:

```
path/to/init.example.rc:44
   |- [EVENT TRIGGER] :43     on property:sys.example.feature=*
   `- [TARGET       ] :44     write /sys/example/node ${sys.example.feature}
   !! CONDITIONAL: runs only when the above hold. Read them before concluding.
```

退出码:`0` 全部无条件 · `1` 存在守卫(必须人工读条件)· `2` 参数 / IO 错误。

**用法上的要点是把它接在 grep 后面**,而不是"想起来才跑":

```bash
# 别这样
grep -rn "some_node" .

# 这样
scripts/show_guard_chain.py --grep "some_node" .
```

它**不做完整语法解析**(那需要 clang / 真正的 parser)—— 只负责把人该亲自读的那几行定位出来。
机器保证不漏,判断留给人。与 `check_api_change.sh` 同一思路。

## 6. 真实案例

### 案例 A — 事件触发器被当成开机脚本

某 Android BSP 里,一个内核 sysfs 节点由 init 写入:

```
on property:sys.example.feature=*
 write /sys/example/node ${sys.example.feature}
```

grep 只会命中 `write` 那行。据此得出的结论是「init 开机时写一次」——
于是整条链被理解成"开机定型,之后不再变"。

实际上 `on property:<name>=*` 是**属性变化触发器**,init 在这里等于一个常驻的
property→sysfs 转发器,上层每改一次属性它就重写一次。两种理解对应完全不同的架构:
前者要求上层在开机时把值准备好,后者允许运行期随时切换。

**按错误理解去设计,会给一个本来就支持热切换的机制再加一套开机同步逻辑 —— 纯属多余,
而且会掩盖真正的问题。**

### 案例 B — 上游 i2c 探测里的唤醒登记

`drivers/i2c/i2c-core-base.c` 的 `i2c_device_probe()` 里有:

```c
if (client->flags & I2C_CLIENT_WAKE) {
        ...
        device_init_wakeup(&client->dev, true);
        ...
        status = dev_pm_set_wake_irq(dev, client->irq);
}
```

grep `dev_pm_set_wake_irq` 只命中最里面那行。若据此断定"i2c 设备探测时会自动登记唤醒中断",
就漏了 `I2C_CLIENT_WAKE` 这个前提 —— 而该标志需要设备树节点带 `wakeup-source`
才会被置上(`i2c-core-of.c`)。

判据是现成的:节点没有 `wakeup-source` 时,该设备的 sysfs 下**根本不会出现 `power/wakeup` 文件**。
一条 `ls` 就能证伪,却因为"看到调用行就当它执行"而绕了远路。

## 7. 反向的坑 —— 被质疑时,先核对自己的原始产出

上面六节讲怎么不理解错。这一节讲**被人指出"你理解错了"时怎么办**,它的失败后果更重。

对方说"按你说的这样,那不就 XXX 了吗?",此时有两种反应:

```
[错] 立刻认错 → 去查 → 查到一个相关事实 → 宣布「我原来写错了」→ 动手改
[对] 先定位质疑指向的【具体位置】→ 读回自己产出里的【那一处】→ 再判断谁错
```

走错的那条路会**认领一个不存在的错误**,然后去"修"一个没坏的东西 —— 把对的改成错的,
而且此后所有人都相信那是修正过的版本。

原因在于:质疑通常只给出**结论层面的矛盾**("那开关不就是假的了吗"),
不会指明是哪一行、哪张图的问题。而结论矛盾可能来自完全不同的三处:

| 矛盾的真实来源 | 正确反应 |
|---|---|
| 我的产出确实写错了 | 改产出 |
| 我的产出是对的,但**另一处缺失**导致读者推出矛盾 | 补那一处,别动对的部分 |
| 我的产出是对的,读者读的是另一段 | 说明,并想想为什么会引到那段去 |

**三种都表现为"用户说我错了"。不核对原文就分不出来。**

可执行形态(三步,顺序不能换):

```
① 定位:质疑指向哪个具体产出?拿到 file:line / 图元素 / 段落
② 核对:读回自己那一处【实际写了什么】—— 用 grep / Read,不靠回忆
③ 判定:三选一(我错了 / 我对但缺了别的 / 读的不是这段),再决定动不动手
```

第 ② 步不能省。**对自己产出的记忆,和对代码的记忆一样不可靠** ——
"代码事实禁 hedge"那套三档标准(已验证 / 我不知道要查 / 禁含糊)同样适用于
"我到底写了什么",而且长会话里更不可靠,因为早期写的内容已被上下文稀释。

顺带一条:认错时编造具体细节("我把它画成了开机一次性")是**双重伤害** ——
既没解决真问题,又往对话里注入了一个假事实,后面所有推理都可能引用它。
不确定自己写了什么,就说"我去核对一下",不要替过去的自己编动机。

## 8. 与 4 维度分析的关系

`bsp_discipline.md` 要求任何改动过 4 个维度(编译 / 运行路径 / 语义 / 合规)。
执行上下文属于**运行路径维度的入口** —— 连"这行跑不跑"都没确认,后面三个维度都是空谈。

顺序:先 `show_guard_chain.py` 拿到守卫链 → 答完 WHO / WHEN / ELSE → 才进入 4 维度分析。
