# 接口契约变更 — 改之前先枚举所有调用点

> 配套可执行检查:`scripts/check_api_change.sh <函数名> [--tree <代码树>]`
> 相关:`bsp_discipline.md`(改动的 4 个维度)· `dos-and-donts.md`

何时读本文:要改一个**已经有人在调**的函数 —— 改返回值含义、改参数取值空间、
增删副作用、改错误约定。新写的函数不适用(还没有调用者)。

## 1. 什么是"契约"

函数与所有调用者之间的**隐含约定**。类型签名只表达了其中一小部分:

| 契约要素 | 例子 | 类型系统能表达吗 |
|---|---|---|
| 取值空间 | 返回 0/1,或 −1 表示"不适用" | ❌ |
| 特殊值含义 | −1 是错误?是"我不在位"?还是合法状态值? | ❌ |
| 副作用 | 这个 `get_*` 会不会顺手改状态 | ❌ |
| 错误约定 | 负 errno / 返回 −1 / 置全局 errno / 返回 NULL | ❌ |
| 调用上下文 | 能否在原子上下文调用、是否会睡 | ❌ |
| 所有权 | 返回的指针谁来 free | ❌ |

**这些全部只存在于文档和人的脑子里。** 所以改它没有任何自动保障 ——
必须靠人工枚举调用点。

## 2. 没有这条纪律会怎样

改返回值语义时,**类型没变,编译器一声不吭**,所有调用点照样编过,
运行时行为却已经改变。

典型表现是「**功能间歇性失效**」而不是崩溃 —— 这是最难查的一类:
没有 oops、没有 WARN、没有编译错误,只有"有时候不好使"。

## 3. 改动前对每个调用点问三句

```
① 它读返回值吗?
     赋值但不读 = 契约在这里【已经】断了 —— 那多半是个既有 bug,
     顺手记下来,别默认"反正它不看,我随便改"

② 它怎么解释这个值?
     判 == 某个魔数 / 判正负 / 直接存进变量 / 原样传给下一层

③ 新语义下它还对吗?
     特别注意"存进变量"的那些 —— 值会流到你视野之外
```

## 4. 五种高危模式(见到就停下来查)

| 模式 | 为什么危险 |
|---|---|
| **返回值存进全局/静态变量** | 值会流向未知消费者,可能是另一个子系统 |
| **只判 `== 魔数`** | 取值空间一扩大,这类判断静默漏掉新值 |
| **一个值承载多种语义** | 如 int 同时表示"状态"和"我不在位",调用方分不清 |
| **读操作有副作用** | `show` / `get` 改了状态,调用方以为自己只是看一眼 |
| **两条路径实现同一约定却不一致** | 如 read 做了判断、write 没做 —— 其中一条必然是错的 |

## 5. 可执行检查

```bash
scripts/check_api_change.sh <函数名> [--tree <代码树>] [--strict]
```

把调用点按风险模式分四类,逐条给 `file:line`:

```
[忽略返回值] ret = foo(x);  之后 ret 再没被读过
[流入全局]   g_state = foo(x);
[魔数比较]   if (foo(x) == -1)
[已判断]     if (foo(x) < 0) return ret;
```

退出码:`0` 无高危 · `1` 有高危 · `2` 函数没找到。
`--strict` 把 `[魔数比较]` 也算失败。

**它不做完整 C 解析**(那需要 clang)—— 只把人该亲自看的那几行定位出来。
机器负责别漏,判断留给人,与 `check_cpp_arms.py` 同一思路。

## 6. 真实案例

某 BSP 的多驱动分发模块,一个函数被多家驱动实现:

```c
int xxx_mode_control(int mode);
/*   mode: 2=查询, 0/1=设置
 *   返回: -1 = 本驱动未 probe(请问下一家)
 *         0/1 = 实际状态
 *   ⇒ 一个 int 同时装了【元信息】和【状态值】两种语义
 */
```

分发模块把返回值**直接存进静态变量**,而该变量还被**另一个子系统**读去做
电源决策。于是:

- 所有驱动都不在位时,一次 `cat` sysfs 就把变量刷成 −1;
- 那个电源决策跟着变,**关掉了本该保持的一路供电**;
- 两个后果都**没有任何报错**。

同一份约定,读路径做了 `!= -1` 短路判断(正确),写路径把返回值丢掉了 ——
写路径于是"永远成功",上层开关拨得动,底层什么都没发生。

跑本 skill 的检查脚本,这两处**一次就被扫出来**,不需要人通读代码:

```
[流入全局]   .../dispatch.c:62   g_state = xxx_mode_control(2);
[忽略返回值] .../dispatch.c:88   ret = xxx_mode_control(v);
```

**三条教训**:

1. 一个值不要装两种语义 —— 元信息和数据分开(或用负 errno 与合法值区分)
2. 读操作不要有副作用 —— `show` / `get` 只读
3. 值一旦进全局变量,消费者就超出你的视野了 —— 改它之前先查谁在读

## 7. 与 4 维度分析的关系

`bsp_discipline.md` 要求任何改动都过 4 个维度(编译 / 运行路径 / 语义 / 合规)。
契约变更属于**语义维度**里最容易漏的一类 —— 因为它在编译维度是完全干净的。

先跑 `check_api_change.sh` 拿到调用点清单,再逐个过那三句问话,
才算这个维度检查过了。
