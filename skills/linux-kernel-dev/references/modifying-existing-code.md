# 改既有内核代码 — 五步决策流程

> 配套脚本:`scripts/why_this_code.sh`(考古)· `scripts/check_context_safety.sh`(上下文/并发/多核)
> · `scripts/check_api_change.sh`(影响面)· `scripts/show_guard_chain.py`(执行条件)
> 相关:`api-contract-change.md` · `execution-context.md` · `bsp_discipline.md §4`(改动 4 维度)

何时读本文:**要改一段已经在跑的代码** —— 别人写的、没有注释、跑了很久、可能有你不知道的理由。
新写的代码不适用。

## 0. 为什么需要一条【有顺序的】流程

改新代码只要写对。改既有代码要同时满足三件事:

- 不破坏现有行为(除非那正是要修的)
- 不破坏对外接口(UAPI / sysfs 节点 / 属性 / 客户 API)
- 理解原设计的约束 —— 而那些约束**可能已经不成立了**

这三件事靠"仔细一点"办不到。它们互相牵制,必须按顺序解开:不知道原设计的意图,
就判断不了改动破不破坏它;不知道通用做法,就只能在原代码的框架里打转;
不知道运行上下文,方案就可能在中断里睡觉。

**这条流程的核心立场**:原先的代码**不一定是对的**,但先假定它**有理由** ——
先找到那个理由,再决定它今天还成不成立。

## 步骤 1 · 考古:现在为什么是这样

```bash
scripts/why_this_code.sh <file> [symbol]
```

一手证据的优先级:

| 来源 | 可靠性 |
|---|---|
| **原作者的 commit message** | 最高 —— 那是**设计意图**,代码里查不到 |
| 代码注释 | 中 —— 可能过期,可能是从别处抄来没改 |
| 从代码反推 | 最低 —— 只能得到"做了什么",得不到"为什么" |

读完 message,对原设计给出**判断**,三选一,每种都要给理由:

```
a) 对,而且约束仍在        → 别动。方案要绕开它,不是推翻它
b) 对,但当年的约束已消失   → 可以改。说清约束是怎么变的
c) 不对                   → 说清错在哪、当年为什么会这么写
                            (常见:当时看不见的场景,不是水平问题)
```

**c 是最需要克制的一档。** "我觉得这样更好"不是理由;
"这个写法在 X 情况下会 Y,而 X 现在会发生了"才是。

⚠ 常见误判:把**针对性补丁**看成设计失误。很多难看的代码是当年为了修一个具体问题
加上去的,在当时的场景下完全正确 —— 它的缺陷要等到某个新场景出现才暴露。
考古能把这两者分开。

## 步骤 2 · 读规范:内核/安卓本来怎么设计这类东西

在动手设计之前,先建立**参照系**:

- 对应子系统的 `Documentation/<subsys>/` + 本 skill 的 `references/subsys/*.md`
- 上游**有没有现成机制** —— 先找,别造。自己造的机制换个内核版本就要重写
- 用户态那一侧的既定约定(sysfs 属性语义、init 触发器、属性命名…)

没有参照系,就只能在原代码的框架里改,结果往往是"把一个私有做法改成另一个私有做法"。

## 步骤 3 · 摸上下文:这段代码在什么环境里跑

```bash
scripts/check_context_safety.sh <file> <function>
scripts/show_guard_chain.py <file>:<line>
```

五个问题,**一个都不能跳**:

### 3.1 执行条件 — 它什么时候跑

见 `execution-context.md`。守卫链决定了"这行会不会执行",不看就等于假设它总是执行。

### 3.2 调用上下文 — 进程 / 中断 / 原子

能不能睡?判据是**调用方**,不是函数自己:

- 持 spinlock / 在 irq handler / softirq / 原子上下文 → **不能睡**
  (`mutex_lock` / `msleep` / `GFP_KERNEL` 分配 / i2c·spi 传输 全部会睡)
- 进程上下文且没持自旋锁 → 可以睡

一个函数被**多处**调用时,要按**最严格的那处**设计。

### 3.3 并发 — 同时进来会怎样

同一个函数被多个进程/线程同时进入时,它碰的状态是不是共享的?
抢占打断在任意一条指令之间发生 —— "两行代码之间"不是原子的。

### 3.4 多核(SMP)— 最容易漏的一维

前三条在单核上也成立,这一条**只有多核才暴露**,所以最容易被"测了没问题"骗过去。

问三句:

```
① 这个函数会被多个 CPU【同时】执行吗?
     sysfs 的 show/store 会 —— 两个进程分别在两个核上读写同一个节点
     中断处理与进程上下文会 —— 一个核跑 handler,另一个核跑 ioctl
② 它碰的状态是共享的吗?
     static / 全局变量 · 驱动实例结构体字段 · 模块级链表
③ 有保护吗?没有的话,最坏会怎样?
```

**三个常见误判**:

| 误判 | 实际 |
|---|---|
| "`int` 读写是原子的,所以没问题" | 原子 ≠ **有序**。CPU A 写完,CPU B 可能仍读到旧值;而且编译器可以把循环里的读优化成只读一次 —— 需要 `READ_ONCE` / `WRITE_ONCE` 或真正的屏障 |
| "只有一个写者,不用锁" | 单写多读仍需 `WRITE_ONCE`/`READ_ONCE` 防编译器重排与撕裂;若值有多个字段则必须用锁或 RCU |
| "概率很低,测不出来" | 多核下不是概率问题,是**必然发生**,只是频率低。靠测试测不出来,只能靠推理 |

**取舍原则:消除共享状态优于给共享状态加锁。**
能让状态只存在于唯一所有者那里,就不要复制一份到别处再想办法同步 ——
锁能防竞争,防不了"两份状态不一致"。

### 3.5 生命周期 — 调用时对象一定活着吗

指针是否可能为 NULL(未 probe / 已 remove)?
谁负责释放?调用方持有引用吗?

## 步骤 4 · 算影响面

```bash
scripts/check_api_change.sh <function> [--tree <树>]
```

三层都要过:

1. **内部调用点** —— 逐个问 `api-contract-change.md §3` 的三句话
2. **对外接口有没有动** —— UAPI 头 / sysfs 节点名与取值空间 / 属性名 / 客户 API。
   **动了就是另一个量级的事**,需要版本与兼容方案
3. **影响哪些产品与配置** —— 同一份源码可能被多个机型、多个 defconfig 共用。
   判据不是机型名,是:源文件有几份 · 该 `CONFIG` 出现在哪些 defconfig · 历史 commit 怎么标注影响范围

## 步骤 5 · 定方案:优先级是【有序】的

```
1. 不动对外用户接口          能不动就不动
2. 靠拢内核 / 用户态通用设计   用现成机制,不造私有的
3. 好移植、好维护            下一个人不用重新考古一遍
4. 修掉原设计的缺陷          原设计不一定是最好的
```

**顺序不能换。** 为了第 4 条去破坏第 1 条,等于把别人的系统改坏了 ——
哪怕改后的代码"更漂亮"。

每一条设计决策都要写下**理由**,而理由必须能追到步骤 1-4 的产出:

```
决策:把 X 从「记住一个值」改成「用时去问」
理由:步骤1 —— 原做法是为了修 A 问题的补丁,当时手头只有这个值
      步骤3 —— 该值是跨子系统共享的 static,无锁,多核下两条路径会互相覆盖
      步骤4 —— 唯一消费者在 <某文件>,语义变化后三种取值全部更正确
```

没有理由的改动 = 把风险转移给下一个人。

## 6. 一个完整案例(脱敏)

某 BSP 的一个 sysfs 分发节点,读写两路都会写同一个 `static int`,
而那个变量还被**另一个子系统**读去做电源决策。

| 步骤 | 产出 |
|---|---|
| 1 考古 | 该耦合是三年前一笔针对性补丁:「为省电在休眠时切断某路供电,结果把需要它的器件也切了,于是加判断」。**原设计是对的**,约束今天仍在 → 落 a 档,方案要保留它的意图 |
| 2 规范 | 读操作有副作用违反 sysfs 惯例;跨子系统传状态,内核惯常做法是**问所有者**,不是复制一份 |
| 3 上下文 | 消费方在电源关闭路径调用,持 mutex 可睡;各驱动的查询分支实测都是纯内存读,不碰总线 → 实时查询安全。**多核**:读写两路无锁竞争同一个 static,原来靠"值恰好相同"侥幸不出事 |
| 4 影响面 | 该函数全树**唯一 1 个**调用点;对外的 sysfs 节点名与取值空间**不变**;源文件只有一份,被两个机型共用 |
| 5 方案 | 保留原意图(供电决策照旧),**删掉共享状态**改为实时问所有者。对外接口零变化(1),用"问所有者"这个通用做法(2),下一个人不需要理解那个变量(3),顺带修掉读操作的副作用与多核竞争(4) |

**关键在于:第 5 步的每个字都来自前四步,没有一条是"我觉得"。**
