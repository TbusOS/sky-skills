# 改动的边界 — 该改多少 · 不该加什么

> 配套脚本:`scripts/diff_discipline.mjs`(带 `--selftest` 自校准)
> 相关:`modifying-existing-code.md`(动手之前怎么想)· `bsp_discipline.md §4`(改动 4 维度)
> · `api-contract-change.md`(接口契约变更)

何时读本文:**代码写完了、提交之前看 diff 的时候**。`modifying-existing-code.md` 管"动手前先搞清楚",
本文管"动完之后怎么收口"。两份是同一条流程的前后段。

## 0. 为什么单独一份

有两类问题,逐个 hunk 读 diff 时**看不出来** —— 每个 hunk 单看都合理,只有把 diff 当整体看才暴露:

1. **改超了范围**。任务只说改一个函数,diff 里却顺手改了个变量名、重排了 include、
   重新缩进了一段。这些行每一行都要有人评审,并且永久占着 git blame。
2. **加了没人要的东西**。多出一个 module_param、一个 Kconfig 符号、一层只有一个调用点的包装,
   当成"可配置性是免费的"来定价。它不免费:每个选项都是这个驱动余生里都要有人推理的一个状态。

所以本文的检查对象是**整个 diff**,不是单个 hunk。

## 1. 唯一的判据:每一行能不能指回需求

看着你的 diff,逐行问:**能不能指出是哪句需求让这一行成为必要的?**
如果某行的理由是"反正我都进来了顺手…",撤掉它。

四条推论:

- **不该碰的别碰。** 在修 A 函数的 bug 时看到 B 函数变量名难看,留着。看到注释有错别字,留着。
  看到 include 顺序不合你的偏好,留着。你的任务是修 A 函数的那个 bug。
- **匹配既有风格,不是你的偏好。** 这个文件用 `goto err_free` 收尾就跟着用,别因为你更习惯
  多个 return 就改掉它。文件内部一致 > 个人偏好。内核树的整体风格另有硬标准,见 `coding-style.md`。
- **只清理自己造成的垃圾。** 你的改动让某个 include 没用了 → 删掉它。让某个变量没用了 → 删掉它。
  但**本来就存在**的死代码不是你的事,除非有人专门要求清理。
- **不重排版。** 别对一个本来不是这个格式的文件跑格式化工具,别把 4 空格改成 2 空格,
  别把 include 按字母重排。重排版会产生巨大的 diff,把真正的改动淹掉,让评审变成受刑。

机器化形式:

```bash
scripts/diff_discipline.mjs --diff <patch> --scope '<你被要求改的范围>'
scripts/diff_discipline.mjs --git HEAD~1..HEAD --scope 'drivers/i2c/**'
```

`--scope` 就是"这句需求允许碰哪些文件"。不给 `--scope` 时越界检查会被跳过并明示
(报 skipped,不报 clean)—— 因为没有声明范围就无从判断越没越界。

## 2. 四类过度设计 — 翻译成内核形态

原始的四类命名来自 web 语境(见 §4 来源),内核里的形态不一样:

| 类型 | 内核里长什么样 | 机器可判? |
|---|---|---|
| **过早抽象** | 只有一个调用点的 static 包装函数;只有一个实现的 `struct xxx_ops` | 部分:`lone-wrapper`(需 `--tree` 数真实调用点) |
| **臆想式错误处理** | 对本文件静态函数的入参做 NULL 检查;`probe` 里对刚 `kzalloc` 成功的指针再判一次空;为不可能发生的返回值写错误分支 | 否 —— 需要人判断"这个错误真的能发生吗" |
| **不必要的可配置性** | 新增 `module_param` / Kconfig 符号 / sysfs 旋钮,而那个值这辈子不会变 | 是:`speculative-knob` |
| **无用的灵活性** | 只有一个 provider 的 ops 表;只被一种硬件用到的 quirk 位图;单实现的抽象层 | 部分 |

**总判据**:"以防以后需要"**不是需求**,是对未来的猜测,而猜测通常是错的。
检验方式:把代码给一个不熟悉这个项目的人看,如果他问"这里为什么要抽象成这样",
而你的回答是"万一以后要…",那就是过度设计了。

### 内核语境必须补的一条(否则这节会误伤)

**内核本身就有大量通用框架** —— regmap、ops 表、notifier chain、devres、
per-subsystem 的 provider/consumer 模型。**用框架已有的抽象不是过度设计**,那是走正路;
自己在框架旁边**再包一层平行抽象**才是。判断标准不是"有没有抽象",是"这层抽象是内核已有的,
还是你新发明的"。新发明的那层,才拿上面四条去量。

### 反向纠偏

这四条容易被拿来反对一切新增,所以要说清楚合理的形态:

- 调试期的 `module_param`、现场真的需要调的超时值,是合理的
- 面向多颗料的驱动,ops 表当下只有一个实现但第二颗料已经在排期,也是合理的

闸报 `speculative-knob` **不是指控**,它要求的是你能回答两个问题:**谁会去设它?设错了会怎样?**
答得上就留着,答不上就删掉。

## 3. 三个失败模式 — 起了名字才好在评审里指出来

### 3.1 级联改动(Runaway Refactor)

改一处,牵出另一处,那处又牵出下一处。二十分钟后动了 15 个文件,已经说不清最初要干什么了。

- **为什么 BSP 上特别容易踩**:SDK 升级的冲突修复天生是级联的 —— 解开一个冲突点会带出下一个,
  很容易一路解到面目全非,最后一个 commit 里混着三件不相干的事。
- **规则**:**发现改动在级联,就停下来说明现状,拿到确认再继续**,不是闷头改完再解释。
- **机器信号**:`diff_discipline.mjs` 的 `spread`(文件数 / 涉及目录数超阈值)。
  它报 warn 的含义是"停下来确认范围还是不是原来那个",不是"撤销"。
- **落法**:`sdk-migration` / `code-migration-workflow` 里"阶段独立 commit"就是这条的具体形式 ——
  级联到新的一件事,就开新 commit,别混进当前这个。

### 3.2 隐形决策(Invisible Decision)

做了一个难以撤销的架构选择,却没有把它标注成一个**选择**。

- **内核里的形态**:定下 sysfs 节点名、DT binding 的属性名、ioctl 号、放进 UAPI 的结构体布局 ——
  **一旦有用户就改不动了**。这类东西在 diff 里可能只是一行,代价却是永久的。
- **规则**:这类改动的 commit message 里必须写成"我选了 A,没选 B,因为 X",
  而不是只写"新增 xxx 属性"。让评审的人有机会在它固化之前反对。
- **接上**:Forbidden Actions §10(改动 4 维度)· `api-contract-change.md` · Forbidden Actions §4(UAPI)。

### 3.3 错误的抽象(Wrong Abstraction)

**重复远比错误的抽象便宜。抄两遍,再考虑抽象。**

- **内核里的形态**:两颗料的驱动只差三个寄存器,就急着抽一层公共代码;
  抽完之后第三颗料来了,它哪一条都不符合,于是公共层里长出一堆 `if (chip == FOO)`。
  这时候拆回去比当初不抽还贵。
- **判断时机**:第二份重复出现时**不动**,第三份出现时才看有没有真正的共性。
- **接上**:`code-migration-workflow` 的"替代料共存" —— 先各留各的,别急着合。

## 4. 来源与分量(引用时必须一并说明)

本文 §1、§2、§3 的骨架取自一份社区流传的 `CLAUDE.md`,归属署名为 Andrej Karpathy,
但**该归属从未被独立证实**,本人未公开回应,Anthropic 也没有发布过任何官方版本。
它的实际性质是"一份写得不错的社区文档",不是权威规范。

采用它是因为两点具体价值:四类过度设计的**命名**好用(命名之后才能在评审里指名道姓),
以及"以防以后需要不是需求"这个**判据**足够锋利。不是因为出处权威。

原文本身有转录错误,例如 "Add null checks only on values that are never null"
把工程结论**说反了**(应为"只对可能为 NULL 的值加检查")。因此本文是按内核语境**重写**的,
不是翻译,也没有照抄。原文全部例子都是 web 技术栈(EmailService、JWT、REST、prettier),
与内核无关的部分(依赖管理那节讲 npm 包)整节未采用。
