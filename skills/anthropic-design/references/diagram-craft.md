# Diagram Craft — 手工 SVG 图示工艺（anthropic-design）

> **本文约束的是什么**——三层分清楚：
> ① **审美**（色彩语义、暖系调色板、编辑式克制）——不可变,这是 skill 的身份;
> ② **工艺质量**（可读性、字号、留白、不发灰、不满铺）——机器闸强制,这是底线不是风格;
> ③ **图型与结构**——**自由定制**。模板和 §15 图型谱系是审美起点和设计思想的载体,不是强制规格。
> 内容长什么样,图就该长什么样:可以变体、混搭(波形里嵌位域、架构图里嵌 mock)、自创新图型——
> 只要 ①② 仍然成立。"必须配图"约束的是**有没有图**,从不约束**图长成哪样**。

> 适用：架构图 / 流程图 / 层级图 / 时间线 / git graph / 一切"工程类"图示。
> 时序图另有专文 `sequence-diagrams.md`；抽象插画见 `imagery.md`（两者不受本文"工程图"规则约束的条目会单独标注）。
> 模板：`templates/diagrams/`（architecture / flow / hierarchy / timeline / sequence / state-machine / deployment + 内核七件 function-flowchart / algorithm-ringbuffer / register-bitfield / soc-block / hw-timing-waveform / build-pipeline / sched-timeline + 互连拓扑 interconnect-map + 协议分层 protocol-stack + 地址映射 address-map + 芯片与代码七件 system-topology / die-floorplan / datapath / packet-encap / terminal-annotated / struct-graph / bus-fabric + 调用与时序六件 call-graph / call-stack / runtime-timeline / frame-pipeline / multicore-calls / power-sequence,共 **30 件**,全部按本文标准实现;另有 §17 的 glyphs.svg 构件片段集,不计入图型谱系）。案例库：`demos/anthropic-design/diagrams.html`（36 张图 × 工程 / 内核硬件 / 芯片与代码 / 调用与时序 / 产品展示 / 演讲汇报六类场合，每张带 Copy SVG）。

## 0. 第一原则：颜色做语义，不做填充——但必须在场

颜色的职责是**编码类别和焦点**，不是涂满面积。同时颜色必须**看得见**：把一切都压成 8% tint + 灰线的图读作"没做完"。

- 大面积（分组容器、面板底）只允许 white / cream / **16-20% tint**（§1 容器 tint 列，2026-06-11 起加深一档——旧 8-12% 档实践证明发白）
- **纯色满填只允许 ≤ 56×56 的元素**（icon tile、徽章、色点、图例 chip、提交圆）——而且这些小元素**必须**用纯色满填，不准用空心环替代（§1）
- 单图饱和色覆盖率目标 **4-14%**：>15% 走向色块（saturated-band 上限闸，known-bugs §1.27）；<3% 发灰（diagram-monochrome 下限闸抓 0 饱和 hue，known-bugs §1.30）
- **反向红线：工程图不允许发灰**——0 个饱和 hue（全靠灰阶 + 白卡）的工程图读作 wireframe。每张工程图 ≥ 2 个语义 hue（§1）；单系列图表（data-display 默认单蓝合法）、纯插画、apple skill 不受此条约束
- 反面教材：三条满宽橙/蓝/绿色带的旧 architecture.svg（2026-06-10 已重写）——"PowerPoint SmartArt 感"的最大来源；以及全图白卡灰线的"幽灵图"（2026-06-11 加下限闸）

|---|---|---|---|---|---|

| 蓝 | `#6a9bcc` | `#e2ecf5` | `#d6e3f0` | `#4a7bab` | 表现层 · 数据 · 搜索类 |
| 橄榄绿 | `#788c5d` | `#e5e9dd` | `#e0e5d4` | `#5d7045` | 成功 · 分析类 · 领域层 |
| 金 | `#c9913f` | `#f0e4d8` | `#ecdcc8` | `#8a5a2a` | 暂存 · 镜像 · 次要类别 |
| 墨 | `#141413` | `#e7e4d9` | — | `#141413` | 基础设施 · 中性骨架 |

> 2026-06-11 起 tint 整体加深一档（旧值 `#fbeee7 / #eef3f9 / #eef1e8 / #f6efe3 / #edebe3` 退役）。
> 全部新 tint 明度 l ≥ 0.85，不触 saturated-band 闸，也不计入 hue 数——色彩在场感来自下面三条。
> 金主色同日从 `#c49464` 改为 `#c9913f`：旧值就是 ember 的签名金，在 anthropic 页里会触 cross-skill-smell（§K，RGB 距离 < 22 判串味）。新值距 ember 金 37.5，距橙 38.8，不串。

用法：**多色彩是允许且推荐的**（一层一个 hue / 一类 agent 一个 hue），但每个 hue 只以"容器 tint + 4px 色条 + 色点 + 彩色连线 + label 深色"出现，不以满填色块出现。焦点元素（主路径、协调者卡）固定用橙。三条硬规则：

1. **实心饱和小元素**：色点、编号徽章、git 提交圆、图例 chip、状态 dot 一律**主色实心填充**（`fill="#d97757"` 等）。**禁止空心环**（`fill="none" stroke=主色`）替代——空心环只允许表达 "未完成 / upcoming" 语义,且同图必须有实心态对照。这是 v2 工艺发白的主要原因之一。
2. **每图 ≥ 2 hue 合约（工程图）**：分层 / 分类各占一个 hue，焦点固定橙。单 hue 工程图（全橙或全蓝到底）按反模式处理（§14）。hue 按色板四主色计（橙 / 蓝 / 绿 / 金），窗口 mock 红绿灯不算语义 hue。单系列图表、纯插画不受约束。机器闸只抓 0 hue（diagram-monochrome,known-bugs §1.30）——存量合法单 hue 图（git graph / timeline）不受影响，但新图按 ≥ 2 hue 写。
3. **彩色连线**：主干线不只是橙——次类别的主干线用该类 hue 1.8px 实线，灰 `#a8a496` 只留给次要虚线关系。

辅助灰阶：连线 `#a8a496`、次级文字 `#6b6a5f`、弱标签 `#8c8a7d`、卡边 `#d8d4c8` / `#e3e0d4`、分组边 `#d9d5c7`、面板边 `#eceadf`。

## 2. 结构：嵌套分组

层次靠"包含关系"表达，不靠色带：

```
面板（white / cream 渐变 + dot-grid）
└─ 分组容器：tint 底 + 1px 边（同 hue 浅色，虚线 4 3 或实线）+ rx 10-12
   ├─ 左侧 4px 色条（rx 2，full hue）
   ├─ 标签：4px 色点 + 10.5-11px UPPERCASE letter-spacing 0.08em-1.2 label 深色
   ├─ 右侧可选注释：10px italic #8c8a7d，text-anchor="end"
   └─ 节点白卡若干
```

## 3. 节点卡

- 白底 `#ffffff` + 1px 边 + rx 8-10 + 微投影 `feDropShadow dx=0 dy=1 stdDeviation=2 flood-opacity=0.06`
- 两行排版：**主名 12.5-14px Poppins 600 `#141413`** + **副说明 9.5-11px `#6b6a5f`**——单行居中大字是 SmartArt 感的另一半来源
- 类别标记二选一：
  - 简洁版：主名前 3.5px 色点（适合密集行，见 architecture.svg）
  - 完整版：左侧 32-40px icon tile（tint 底 rx 8-10 + hue 深色线性 icon，见 hierarchy.svg / flow.svg）
- 焦点卡（全图最多 1-2 张）：橙 tint 底 `#fbeee7` + 橙 1.5px 边 + 橙 icon（旧 `#fdf6f2` 太接近白，焦点立不住）

## 4. 连线工艺

1. **圆角正交折线**，不用斜线直穿：`M x1,y1 V ym Q x1,ym x1±8,ym H x2∓8 Q x2,ym x2,ym+8 V y2`（拐角 8px quadratic）
2. **从节点边缘锚点出发**，不从盒子中心穿出；同一边多条线用偏移锚点（如卡底 380/420/460/500 四个锚位）
3. 主路径 1.8px 实线（橙）；次要关系 1.2px 虚线 `stroke-dasharray="4 3"`（灰 `#a8a496` 或类别色）
4. 箭头统一 7px 小实心三角 marker，颜色同线：
   ```svg
   <marker id="arr" viewBox="0 0 8 8" refX="7" refY="4" markerWidth="7" markerHeight="7" orient="auto-start-reverse">
     <path d="M0,0.5 L7.5,4 L0,7.5 Z" fill="#d97757"/>
   </marker>
   ```
5. 回流/失败路径走图形下方，灰虚线 + 11px 标签（如 `fail · retry`）

6. **同类线 ≥ 2 条时,每条压一颗药丸写清它是什么**(rx = 高/2,墨 tint `#e7e4d9` 底 + `#cfccc0` 边 + 10.5-11px 600 `#141413`)。
   药丸内容 = **名字 + 一个关键指标或位宽**(`AXI4 · 128-bit` / `PCIe Gen4 ×8` / `MD[63:0]` / `DDR5 · 8 ch`);
   只写 `bus`、`link` 这种类别词等于没写。
   **为什么是"压在线上"而不是"写在线旁"**:线会拐弯、会交叉,写在旁边时归属由距离决定 —— 两条线靠近的地方,
   标签属于谁没有唯一解;压在线上归属由位置唯一确定,药丸的不透明底色顺带切断了交叉处的视觉打架。
   **为什么门槛是 2 条**:只有一条线时,"这根线是什么"由图题回答;出现第二条,读者的默认假设立刻变成"这两根是一回事",
   而它们往往不是 —— 不写名字就等于宣布它们等价。
   **例外**:流程图的线表达的是"下一步",步骤号由编号徽章(§5)承担,不再压药丸;真正只有一条线的图不受此条约束。
7. **两类箭头,分工写死**——这是让一张结构图能被后面每一节复用的前提:
   - **中性实线 = 一直在那儿的结构**:物理连线、总线、层级归属。它描述的是硬件/代码的静态事实,换一节内容也不变。
   - **彩色虚线 = 本节正在讲的这一次**:一次访存、一次 DMA、一次中断、一次调用。它描述的是一个时刻。
   **没有这条分工会怎样**:两种线画成同一种,结构和事件被压成同一个平面 —— 读者无法判断
   "这根箭头是硬件上真有一根线,还是这次刚好走了这条路"。把 DMA 路径画成黑实线箭头,
   读者会读成"这里多了一根物理通道",这是这类图最常见的误读。
   **配额**:一张图**最多一条**彩虚线路径(§1 橙色预算)。要讲第二次不同的访问就再出一张 —— 那正是 §16 图族。

## 5. 编号徽章

主路径和流程步骤加叙事编号：r=9-10 橙色圆 + 11px 600 白字。位置：流程卡左上角压角（圆心 = 卡角坐标 +4）、路径中段（避开箭头和文字，横段放编号、留 4px 以上间隙）。

**徽章画了就必须在字里被点名。** figcaption 或紧邻正文至少引用一次(正文写成「③ 处调用 `dma_map_single()`」这样);
一个都不引用的编号是纯装饰,读者不知道该按什么顺序读,而"顺序"正是加编号的唯一理由。
**编号必须是连续的 1..N**(或 `A`..`N`)—— 跳号的那一组不是编号,是标记,别放进圆圈里,
不然读者会去找不存在的那一步。步骤超过 10 步时改用大写字母 ——
两位数字挤进 r=10 的圆里会掉到 9px 以下,触 `diagram-tiny-text`。
机器闸 `badge-not-referenced` 在看这条,**5 个徽章起查**:3-4 步时箭头本身就把顺序说完了,
编号只是复述;5 步以上顺序才撑不住,必须靠字锚一个。

## 8. 先定尺寸再画：选档表 + 布局公式

**内容多的图必须画大,不准把元素缩小塞进固定画布**。读者体验第一:看不清的图等于没画。

### 8.1 选档（画第一笔之前算）

先预估三个数：列数 C、最宽节点的字符数、`<text>` 元素总数 T。

```
viewBox 宽 = max(720, C × (节点宽 + 24) + 2 × 24)     # 节点宽公式见 §8.2
scale = 容器内可用宽 / viewBox 宽
合格线：scale ≥ 0.82（11px 源字号 → 渲染 ≥ 9px）
```

| 容器档位 | 可用宽 | 适用 | viewBox 宽 |
|---|---|---|---|
| 720 正文列（prose 流内） | ~660 | T ≤ 10 且 C ≤ 2 的小图 | ≤ 760 |
| 960 标准（`anth-container`） | ~880 | T ≤ 18 | 880-1040 |
| 1200 wide（`anth-container anth-container--wide`） | ~1130 | **T ≥ 20 或 C ≥ 4 必须用** | 1080-1280 |

- scale < 0.82 → 升一档；1200 档还不够 → **拆成两张图**，不准缩字号
- **breakout（对齐让位于可读性）**：图的宽度由内容密度定档，**不由上文列宽定**——"为了和上面文字对齐把图压小"是用户点名反馈的坑（known-bugs §1.44），图看不清等于没画。prose 流中需要大图时，结束当前容器，单独开一段 `<div class="anth-container anth-container--wide"><figure>…</figure></div>`，图后再回窄列；**grid 单元格里禁放 ≥20 label 的密图**（要么 `grid-column: 1 / -1` 独占全行，要么拆图）
- **viewBox 紧贴内容**：内容 bbox 距 viewBox 边 ≤ 24px。viewBox 写大、内容挤中间 = 两侧死空间逼所有标签变小
- 机器闸：`svg-letterbox`（内容 < 72% 渲染宽,known-bugs §1.28）、`dense-diagram-cramped`（≥ 20 text 渲染 < 760px,§1.29）、`diagram-tiny-text`（任何 figure 图渲染 < 9px,不再限 hero）

### 8.2 布局公式（防文字溢出 / 防挤）

- **节点宽度 = max(160, 英文字符数 × 9, CJK 字符数 × 18)**——主名+副说明取较长者
- 架构图列间距 ≥ 14（卡间）/ 行高 = 卡高 + 28（标签区）；流程图卡间走线段 ≥ 32
- 分组容器 padding ≥ 16；面板 viewBox 四周 padding ≥ 24
- **所有坐标和尺寸落在 4px 网格上**；圆角全图统一（卡 8-10、容器 10-12、面板 14-16）
- SVG `<text>` font-size ≥ 11（audit 红线：渲染 < 9px 告警），副说明最低 9.5px 只允许出现在 ≥1000px 宽的 hero 图里
- 文字 bbox 互不相交 ≥ 4px（known-bugs §1.25）；写完先渲染再交付

## 9. icon 语法（lucide 风，4 条）

1. 24×24 设计坐标（`transform="translate(tileX+8, tileY+8)"` 放进 40px tile，32px tile 用 +6）
2. `stroke-width 1.5-1.6`，`stroke-linecap="round" stroke-linejoin="round"`
3. **不填充**（`fill="none"`；实心小点除外）
4. 颜色 = 类别 label 深色（中性 `#6b6a5f`）

常用现成 path 见 `templates/diagrams/` 内：chat 气泡 / code 尖括号 / globe / cpu / sliders / database / drive / sparkle / list / magnifier / bars / download / shield-check / send。

## 12. 图密度合约（何时必须配图）

页面写作时遵守：

| 内容形态 | 必须的视觉化 |
|---|---|
| ≥ 3 步的流程 / 启动链 / 数据流 | 流程图或时序图 |
| 数字对比 / 统计 | stat callout 或图表（`data-display.md`），不准纯文字段落罗列 |
| 系统结构 / 分层 / 依赖 | 架构图 |
| 时间演进 / 版本 / 里程碑 | 时间线 |
| 产品 / UI 描述 | 窗口 mock |
| 函数控制流 / 错误处理路径 | 函数流程图（§15.1） |
| 数据结构 / 算法机制 | 算法原理图（§15.2） |
| 寄存器 / 位域 / 协议帧格式 | 位域图（§15.3） |
| 芯片 / SoC / 板级硬件结构 | SoC 框图（§15.4） |
| 多 die / 多插槽互连 · 两侧地址空间不同一套编号 | 互连拓扑 + 地址空间映射图（§15.8） |
| 硬件信号 / 总线协议时序 | 波形时序图（§15.5） |
| 编译 / 构建 / 打包链 | 编译流程图（§15.6） |
| 多核调度 / 抢占 / 时间片 | 调度时间线（§15.7） |
| 连续纯文字 > 2 屏 | 插入至少 1 个视觉元素（图/表/stat/pull-quote） |

节奏目标：每 1.5 屏高度（≈1300px @1440 视口）至少 1 个 SVG / figure / stat 元素。

**表里的图型是默认映射,不是唯一解**:它回答"这类内容值得一张什么样的图作起点",
实际结构按内容定制——拆图、合图、混搭、自创形态都允许,合约只在两件事上是硬的:
该有图的地方要有图(text-desert 闸),以及图本身的工艺质量(§0-§9 + 各闸)。

## 13. figure 语义规范

每张内容图示包 `<figure>` + 真实 `<figcaption>`（audit known-bugs §1.18：SVG aria-label 和内部 `<text>` 不能替代 figcaption）。SVG 本体必带 `role="img"` + `aria-label`；纯装饰 SVG 用 `aria-hidden="true"`。

## 15. 内核 / 嵌入式工程图谱系（23 个图型的专属工艺）

> 每个图型有现成模板（`templates/diagrams/` 同名 .svg），复制改内容比从零画稳得多——
> 但模板是**起点不是规格**:它示范这个图型的审美和常见坑的解法,结构、节点数、布局、信息密度
> 全部按你的实际内容重新设计;内容超出谱系时直接自创图型,套用 §0-§9 的工艺即可。
> 通用规则（§0-§9）全部适用；本节只写每个图型**额外**的工艺决定。案例见 `demos/anthropic-design/diagrams.html`。

### 15.1 函数流程图（function-flowchart）

- 纵向主路径（happy path 橙 1.8px + 编号徽章），**错误处理走右侧独立车道**：gold 1.2px 虚线逐级下汇到共享出口（`return -errno`）——错误路径穿插在主路径里是最常见的可读性灾难
- 菱形只给真判断（`ret < 0?`），用强调 tint `#f4d9cd`；cleanup 步骤（`iounmap` / `kfree`）是普通卡，不是菱形
- 入口/出口用胶囊（rx = 高/2）；成功出口绿色点缀，错误出口 gold
- 内容必须真实：真函数名、真 errno,不写 step1/step2

**竖着画还是横着画** —— 这是这个图型唯一需要提前决定的事,决定错了后面全是补丁：

| | 竖版（主路径由上到下,错误车道在右） | 横版（主路径从左到右,错误车道在下） |
|---|---|---|
| 适合 | 步骤 ≤ 3、每步文字长、错误处理各自独立 | 步骤 ≥ 3、**错误处理是一条解绑梯**(每级失败跳进不同标签再依次落下) |
| 高度 | 步距 ~104px × 步数 + 出入口 ≈ 很快过 640 | 一条主路径 + 一条车道,恒定 ~420 |
| 讲得清的事 | "每一步失败各回各家" | **"倒着解绑"** —— 车道的箭头与主路径反向,这个反向本身就是结论 |

- **横版的排布公式**：`入口胶囊 + N×(步骤卡 + 菱形) + 出口胶囊` 一行排完,
  菱形的 `yes` 分支**垂直落下**进下方车道,`no` 走水平线继续。
  垂直落下是硬要求 —— 斜着落会跟相邻的落线交叉,一交叉就分不清哪一级失败去了哪一级标签。
- **车道里的顺序要反着排**：最右边放最晚获得的资源(`err_unmap`),最左边放共享出口(`err_out`)。
  这样三条落线都是竖直的、互不交叉;而车道内部的"继续落下"箭头自然朝左,与主路径反向。
  **顺着排会让三条落线全部交叉** —— 这是横版最容易翻车的一处。
- **车道里的卡片写 `标签:` + `调用`两行**(`err_unmap:` / `iounmap(base)`),
  不要写成 `ret = -ENOMEM` 这类赋值 —— 那是数值不是动作,读者看不出它在解绑什么。
- 例子看 `demos/anthropic-design/diagrams.html` 的 `mydev_probe()` 那张(viewBox `1080 × 420`)。
  它用 `kzalloc` 而不是 `devm_kzalloc` 是刻意的：**用了 `devm_` 这把梯子就不存在了**,
  这张图也就没有画的必要 —— 图里那句脚注就是替读者把这层挑明。

### 15.2 算法原理图（algorithm-*，模板示例 ring buffer）

- 数据结构 = 单元格阵列（cell ~56×48 rx 6）：**占用 = tint 填充,空闲 = 白底**,状态一眼可分
- 指针/游标 = 实心 hue 三角 + 标签（in/out、head/tail），不同指针不同 hue
- 机制性注释（`smp_wmb()` / `idx & (size-1)`）≤ 2 行,放阵列侧边或下方,12px;不要把伪码整段塞进图
- 环形结构优先画直线阵列 + wrap-around 圆角箭头,真画圆环文字会全歪

### 15.3 寄存器位域图（register-bitfield）

- 32 位拆两行（31..16 / 15..0），位格 56-60px 宽、44px 高,4px 网格;bit 号 10.5-11px 在格顶
- 字段 = 合并格 + 字段 hue tint + **4px 顶色条** + 居中字段名;焦点字段（EN 位类）用橙;reserved = 白底 + 灰 `—`
- 标题行必含三件套:寄存器名 14px 600 + `offset 0x..` + `reset 0x..`(11px 灰)
- 图下方 3-4 行字段说明:实心色点 + `字段 · RW/RO · 语义`(11.5px),访问权限用 ≤56px 实心 chip

### 15.4 SoC / 芯片框图（soc-block）

- 子系统 = tint zone(CPU 橙焦点 / 内存绿 / 高速外设蓝 / 低速外设金 / 时钟复位墨),zone 内连线用 zone hue
- **互连(NoC / AXI / AHB 总线)= 中性细长卡**(白或墨 tint `#e7e4d9`),绝不允许画成饱和满宽色带(saturated-band 闸);APB 桥单独一张小卡喂低速 zone
- 唯一的主数据路径(CPU→NoC→DDR)橙 1.8px + 徽章;其余 zone 连线 1.2px
- 每张 IP 卡两行:IP 名 + 关键参数(`DDR4 ctrl + PHY` / `Cortex-A55 ×2 (L1 32K)`)
- **边界**:这一节画的是**一颗芯片内部**,只有一套物理地址空间。跨 die / 跨插槽、两侧各有一套编号的,是 §15.8 的图型 —— 别在 SoC 框图里塞第二套地址

### 15.5 硬件波形时序图（hw-timing-waveform）

- 一信号一 lane,左侧 12px 600 标签;波形线 1.8px;**焦点信号(CS / 触发 / 使能)用橙,其余 lane 各 hue 区分**(SCLK 墨 / MOSI 蓝 / MISO 绿)
- 数据段画成 tint cell + 居中 hex 值(`0x9F`);high-Z 用灰短划
- 采样点 = 浅灰虚线竖线(每个有效沿);时序参数(tSU/tH/tCSS)= 双箭头 + 11px 标注,**离波形线 ≥ 8px**
- 底部时间轴 t0..tn(10.5-11px);面板内放协议小标题 chip(`SPI mode 0 · CPOL=0 CPHA=0`)

### 15.6 编译流程图（build-pipeline）

- 工具步骤(橙点卡)和产物(蓝点卡)**交替**出现,主链橙 1.8px + 编号;产物卡副行写格式(`ELF + symbols`)
- 并行分支(dts→dtc→dtb)走 gold 1.2px,在打包步骤(mkimage FIT)圆角汇入
- 最终交付物(boot.itb / Image.gz)用焦点卡 `#fbeee7` + 橙边
- 图例:橙点=工具 · 蓝点=产物 · 金=分支

### 15.7 调度时间线（sched-timeline）

- 一 CPU 一 lane(左标签 `CPU 0/1/2`),底部统一时间轴 + ticks(ms)
- 任务块 = tint 块 + **4px 左色边** + 任务名 11.5px;同一任务跨 CPU 保持同 hue;idle = 白底灰虚线边
- IRQ/抢占 = 竖线 + 实心橙徽章 + 事件标签(`IRQ · eth0 rx`);任务迁移 = 灰虚线圆角箭头 + `migrate` 标注
- 图例必须有(任务数 ≥ 2 即多色);此图型天然 ≥ 3 hue,注意橙只给一个焦点事件/任务

### 15.8 互连拓扑 + 地址空间映射图（interconnect-map）

**这张图只回答一个问题:一次访存落在谁的编号上、字节走哪根线。**

拓扑单独画,读者知道"两块 die 之间有一根线",但不知道那根线意味着 `*p = 1` 直接写到对面,
还是必须 `dma_map_single()` 再让设备自己搬 —— 这两条路的驱动代码没有一行相同。
地址空间条单独画,读者知道有一段窗口,却不知道这段窗口的字节走哪根线、跨不跨一致性域。
**把两半缝在一起的那条虚线就是这个图型存在的全部理由**:它落在地址带的哪一段上,
就是在说"这一段能用一条普通访存指令读到"。分成两张图,这一步要读者自己在脑子里把两半对上 ——
而这一步对不上,正是异构内存最常见的误解来源(把"传指针"和"拷一份"当成两种等价写法)。

结构自上而下三层,三层都在同一个 viewBox 里,**不许拆成上下两张 figure**——一拆就回到了上面说的那个坑。

**① 拓扑层 —— 谁和谁之间有线**

- **节点分组容器**:一个插槽 / 一颗超级芯片 / 一块加速卡 = 一个 §2 分组(tint 底 + 虚线边 `4 3` + rx 10-12)。
  **框的边界必须正好落在私有域的边界上** —— 框存在的理由是画出"框内私有、框外要过互连"这条界,
  不是好看的分区。为了让边界排得整齐,把一块共享内存圈进某个框,这张图就开始说假话了。
- **芯片卡两行**(§3):die 名 + 关键参数(`Grace CPU · 72 core` / `H100 · 80 GB HBM3`)。
  同一 node 内的私有内存(DDR / HBM)**也是卡**,不是背景色块 —— 它是这张图里被寻址的对象之一。
- **互连线 = 线 + 药丸**。每条线的中段压一颗胶囊(rx = 高/2,墨 tint `#e7e4d9` 底 + 10.5-11px 600 `#141413`),
  写**协议名 + 一个关键指标**(`NVLink-C2C · 900 GB/s`)。这是本图型的签名动作,理由是几何的:
  线会拐弯、会交叉,标签写在线**旁**归属有歧义;压在线**上**归属由位置唯一确定,
  药丸底色顺带切断了交叉处的视觉打架。
- **方向即语义**:对等双向 = 两端箭头;主从单向 = 单端箭头;多方共享一个交换 = 全部汇聚到一张
  **中性交换卡**(白底或墨 tint,**不是**饱和色带 —— 同 §15.4 对互连的规定,saturated-band 闸也在看)。
  **一条线只表达一种关系**:"能互访"和"经由谁"是两件事,合成一根线就都读不出来了。

**② 地址空间层 —— 程序看到的编号**

- **一个视角一条水平条带**,条带贴 label chip 写清是谁的视角(`HOST PHYSICAL` / `DEVICE PHYSICAL` / `PCIe BUS`)。
  **两条带永不合并**:合并等于宣布两边编号是同一套,而"同一块 DRAM 在 CPU 眼里是 `0x8000_0000`、
  在设备眼里是 `0x0`"恰恰是这类系统最贵的坑。
- 条带内 1px 虚线分段,每段一个名字 + 起始地址(11px)。段宽**粗略**按容量成比例;
  比例做不准时在 figcaption 里说一句"宽度不按比例" —— 不说,读者会拿宽度去估容量。
- **窗口用斜纹,不换色相**。某段是从另一个空间开进来的窗(BAR / Export / EGM / DMA 区),
  在该段上叠 45° hatch(`#6a9bcc`,`opacity 0.35`,间距 6),底下的类别 tint 保持不变。
  斜纹和色相是**正交的两个通道**:色相说"这是哪类内存",斜纹说"这块地不是本地的"。
  给窗口换个鲜艳色相,就是把两件事挤进一个通道,读者只能二选一地理解。
- **跨空间映射线走条带下方**:从条带 A 的那一段拉 1.2px 虚线到条带 B 的那一段,中段压药丸写映射机制
  (`NVLink-C2C` / `IOMMU` / `BAR0`)。**一条映射线只连两段**;多对多的关系拆成两张图,别在一张里织网。

**③ 缝合层 —— 谁能直接访问**

- 一到两颗**执行体胶囊**(`CPU core · ld/st` / `GPU SM · ld/st`),各拉一条橙 1.2px 虚线箭头,
  **精确落在条带的某一段上**,不是落在整条带上。这条线是全图焦点,§1 的橙色预算(一图 1-2 处)优先给它。
- **figcaption 必须把这条线的结论写成一句话**:"GPU 的 SM 能用一条 `ld` 指令读到 host 的这一段,不走 memcpy"。
  图上有线、字上没有结论 = 读者仍然不知道能不能直接传指针,那这张图白画了。

**尺寸**:天然 T ≥ 30,**一律 1200 wide 档**(`anth-container--wide` + `grid-column: 1 / -1`),viewBox 宽 1200-1280。
高度是它最容易翻车的地方 —— 三层叠起来很容易冲过 `diagram-oversized` 的 640px 渲染线。
反解上限:`viewBox 高 ≤ 640 × viewBox 宽 / 渲染宽`,1240 宽进 wide 档(渲染 ~1130)算得 **702 单位**,工作值取 ≤620。
**node 超过 2 个就把地址层拆成第二张图**,不要靠压行高硬塞。

| ❌ 别画 | 它教错了什么 |
|---|---|
| 只画拓扑,地址范围当一行小字写在框里 | 地址是每个视角一套编号;写进同一个框等于宣布只有一套 |
| 两条地址带画成一条长带、中间竖线隔开 | 同上,而且竖线读作"同一空间的两段",意思正好反了 |
| 窗口段换一个鲜艳颜色 | 色相已经在编码内存类别;抢通道的结果是两件事都读不出 |
| 互连线的名字写在线旁边 | 线一交叉归属就不明;药丸压线是这个图型的立身之本 |
| 交换 / fabric 画成满宽饱和色带 | 互连是中性细长卡(§15.4 同款规定);色带会触 saturated-band 闸 |
| Load/Store 箭头落在整条带上 | 那句话退化成"CPU 能访问内存",等于没说;必须落到某一段才有信息 |
| 一张塞 4 个以上 node + 全部地址空间 | 高度冲线、标签压到 9px 以下 —— 拆图,别缩字号 |

### 15.9 协议分层对等图（protocol-stack）

**这张图只回答一个问题:同层之间那条"对话",到底有没有一根线。**

分层协议的教材写法是"传输层和对方的传输层通信"。读者据此形成的图像是两个传输层之间有一条通道 ——
于是他去查"传输层的线在哪"、去问"为什么抓不到 DLLP 的物理信号"。真相是:
**横向那条线一根都不存在,字节全程只走纵向**,唯一真实的横向连接在最底下那一层。
把"协议上的对等"和"物理上的连通"同时画出来而不混,就是这个图型存在的全部理由。

**结构**

- **两侧镜像栈,层数相同、层高相同、同名层的 y 坐标严格相同。** 坐标一致本身就是"对等"的几何表达;
  两侧错开半格,"对等"这个词在图上就失去依据了,读者只能从文字里接受它。
- 每层 = §2 分组容器(tint 底 + 虚线边 `4 3` + rx 10-12),**层名做成骑在容器上沿的标签片**
  (rect 高 22 + rx 11,压在容器 top 边上,50% 出框),**不是容器内的第一行文字** ——
  放进容器里它会被读成"这一层的第一个部件"。
- **层内必须放真实部件卡**(`TLP` / `Flow control` / `DLLP` / `Link manager` / `TX · RX`),
  不是空层。写着"应用层"的空框等于说这层什么都不做。

**两类横线,和纵向线一共三类,不许混**

| 线 | 画法 | 说的是 |
|---|---|---|
| 纵向 | 彩虚线(本节这一次)或中性实线,**逐层穿过,严禁跳层** | 字节真实走的路 |
| 横向 · 上面各层 | 灰 1.2px `4 3` 虚线 + 中段药丸(`Logical` / `TLP end-to-end`) | 这一层的协议约定作用在这两个对等实体之间 —— **没有线** |
| 横向 · 最底层 | **全图唯一一条横向实线**,1.8px | 真实介质。它是"横向只有这一根是真的"的证据 |

- 横向虚线**两端必须落在同一层的容器上**;落到相邻层就是在画一件不存在的事。
- 差分对 / 介质细节(AC 耦合电容画成线上两道 8px 短竖线、`D+` `D-` 微药丸)放在最底层下方,
  它们是"这一根才是真的"这句话的物证,值得画细。
- **figcaption 必须把结论写成一句话**:"上面三层的横线都是虚的 —— 字节从发送侧一路下到最底层,
  过一次线,再一路上到接收侧同一层。" 图上有三类线、字上没有这句,读者仍会以为传输层之间有通道。

**尺寸**:`viewBox="0 0 1240 560"`,`anth-container--wide` + `grid-column: 1 / -1`。
四层 × 层高 92 + 三个间隙 24 = 440,加 header 56 + 介质区 64 = 560。渲染 560 × 1130 / 1240 = **510px**,
离 640 线有 130px 余量。层数到 5 就换 `1240 640`(渲染 583px),**到 6 层拆图**,别压层高 ——
层高不等会被读成"这层更重要 / 更慢"。

| ❌ 别画 | 它教错了什么 |
|---|---|
| 横向线画成实线 | 直接宣布同层之间真有一根线 —— 这正是这张图要纠正的那个误解 |
| 只画一侧的栈 | 对等关系没地方画,图退化成 §15.4 的分层框图,失去全部价值 |
| 纵向箭头跳层(传输层直接到物理层) | 分层的全部意义就是不许跳;跳一次,读者就学会了可以跳 |
| 层内放空框只写层名 | 层名已经在骑边标签上了;空框在说这层不做事 |
| 两侧层高不等或 y 不对齐 | "对等"失去几何依据,只剩文字断言 |
| 最底层也画成虚线 | 那就没有任何一条真实连接了,整个系统读起来不通电 |

### 15.10 纵向地址映射图（address-map）

**这张图只回答一个问题:某个地址落在哪一段上,以及这一段在另一个视角里叫什么号。**

它和 §15.8 的分工很清楚:§15.8 画的是**拓扑 + 地址**缝在一起,回答"字节走哪根线";
这一张不画拓扑,**只画编号本身**,回答"这个数落在哪儿"。BSP 里最常要画、也最容易画错的就是它。

**结构**

- **纵向条,低地址在下、往上递增**(与 §15.4 同向),每段一个名字 + 容量。方向要在 figcaption 里说一句 ——
  高地址在下的画法同样通行,所以"递增"本身不构成信息。
- **引线指边界线,不指区域。** 这是本图型的签名动作,理由是语义的:
  **边界是一个地址,区域是一段范围**。把 `4 GiB` 写在某段的中间,读者无法判断它指的是这段的起点、
  终点还是大小 —— 三种读法都讲得通,而只有一种是对的。引线从边界 y 处水平拉 1.2px 灰虚线到左栏,
  末端压药丸。段名 + 容量写在段内居中,和边界标签在**不同的栏**里,谁也不占谁的位置。
- **两档药丸,分开两种东西**:
  - **符号名**(`TOLUD` / `Reclaim Limit` / `DRAM_END`)→ 墨 tint `#e7e4d9` 药丸,11px 600
  - **字面常量**(`0xFEC0_0000` / `4 GiB`)→ 橙 tint `#fbeee7` + 橙边药丸,11px mono
  **为什么必须分档**:符号名说的是"这个边界叫什么、由谁写进去",常量说的是"它这一次等于多少"。
  同一个 `TOLUD` 换一块板就是另一个数。混成一档,读者会把这次的数当成定义,
  照抄进另一块板的代码里 —— 这是这张图能造成的最贵的误读。
- **一个视角一条条带,两条并列。** 左边系统物理地址、右边 DIMM 物理地址(或 CPU 视角 vs 设备视角)。
  两条之间用**映射线 + 药丸写机制**(`Direct` / `Reclaim` / `IOMMU` / `BAR0`)连起对应的段,
  一条映射线只连两段。**两条永不合并成一条长带中间加粗线** —— 那读作"同一空间的两段",意思正好反了。
- **hole / reserved / 不可用段用 45° 斜纹**(`#6a9bcc` opacity 0.35 间距 6),底下的类别 tint 不变(同 §15.8)。
- 段高按容量**粗略**成比例;比例做不准时 figcaption 说一句"高度不按比例" —— 不说,读者会拿高度估容量。

**尺寸**:`viewBox="0 0 1240 600"`,`anth-container--wide`。渲染 600 × 1130 / 1240 = **547px**。
横向四栏:边界标签栏 0-232 · 条带 A 232-560 · 映射线区 560-800 · 条带 B 800-1128 · 右侧标签栏 1128-1240。
段数超过 8 段就合并相邻的同类段(连续三段 reserved 合成一段写 `reserved ×3`),别压段高 ——
段高低于 34 单位时段内两行文字必然掉到 9px 以下。

| ❌ 别画 | 它教错了什么 |
|---|---|
| 地址标签写在段的中间 | 起点 / 终点 / 大小三种读法都成立,读者只能猜 |
| 只标每段起始、不标最后一段的终止 | 顶上那条边界没有地址,整条带的量程就是开放的 |
| 符号名和字面常量同一档药丸 | 把"这个边界叫什么"和"它这次是多少"混成一件事,读者会把板级常量当定义 |
| 两个视角画成一条长带 + 中间一条粗线 | 粗线读作同一空间内的分段,而这里是两套编号 |
| 高地址在下但 caption 不声明 | 方向是这张图的隐含坐标系,不声明等于让读者按自己的习惯读 |
| 段高严格等分,却不说不按比例 | 等分本身在说"这些段一样大",而它们通常差几个数量级 |

### 15.11 板级系统拓扑 + 同框地址条（system-topology）

**这是什么**：一张图同时画两样东西 —— 上半是**器件怎么连**（SoC / 桥 / switch / 叶子设备），
下半是**这些器件在物理地址空间里各占哪一段**，中间用引线把设备卡和它自己的那段地址钉在一起。

**没有它会怎样**：拓扑图和地址图分成两张，读者得自己在脑子里把两张叠起来。
「BAR 分配失败」这类问题恰恰只在两张图**叠起来**时才看得见 ——
设备在树上活得好好的，它的窗口在地址条上却没位置。分开画，这个结论画不出来。

**为什么这么设计**：替代方案是画两张图再用文字说「见上图」。不选它的理由是几何的 ——
引线一旦要跨图，就只能靠编号，而编号读者要来回翻。同框之后引线是**一条线**，
眼睛一次就能走完。代价是图变宽变挤，所以地址条**必须允许不按比例**（图里写明 `not to scale`），
否则 16 KiB 的 BAR 在 4 GiB 的条上是 0 个像素。

**什么场景会用到**：新板子第一次跑通枚举、PCIe/CXL 设备加不进来、
firmware 把窗口切小了、要跟硬件同事对「这块地址到底归谁」。

**机制细节**
- **每根线上必须有药丸**，写链路类型 + 编号（`Gen4 x4 · BUS 01`）。理由同 §4.6：线一交叉归属就不明。
- **叶子画成设备卡**：图标 + 名字 + 第二行写 `BDF · BAR0 大小`。BAR 大小是把卡和地址段接上的那把钥匙。
- **地址段的左右顺序必须跟上面设备卡的左右顺序一致**，引线才不会互相穿过。
  顺序对不上时先重排设备卡，不要让引线交叉 —— 交叉的引线等于没画。
- 地址条**只写名字**（`nvme` / `accel`），尺寸留在设备卡上。40 px 宽的段塞不下 `BAR0 256 MiB`。
- 空洞用斜纹填充（`未分配`），不要用留白 —— 留白会被读成「图没画完」。

### 15.12 片内布局图（die-floorplan）

**这是什么**：一颗 die 内部的**瓦片阵列**：每块瓦片是一个核加它自己那一片末级缓存，
瓦片之间跑互连轨，轨的每个交叉点画一个**站点**，四周是 IO 瓦片和内存控制器。

**没有它会怎样**：只画「CPU → 缓存 → 内存」三个方块，就解释不了
「为什么访问同一个地址、不同核的延迟不一样」。延迟差来自**跳了几站**，
而跳数只有在瓦片阵列上才数得出来。

**为什么这么设计**：为什么站点画在**轨的交叉点**而不是画在瓦片边上？
因为瓦片不是「连到轨上」，它是**挂在自己那个站点上**；请求先进站，再沿轨走。
把站点画在瓦片边框上，读者会以为瓦片之间能直连 —— 那是另一种拓扑（crossbar），结论完全不同。
图里那句 `a tile joins the mesh at its ring stop` 就是为了堵这个误读。

**什么场景会用到**：讲 NUMA / sub-NUMA、讲 LLC 切片的地址哈希、讲为什么绑核会影响带宽、
讲 IO die 和 compute die 的关系。

**机制细节**
- 瓦片 = 上下两块：上块窄（缓存切片，带容量），下块宽（核，带编号）。上下两块**不要留缝**。
- 轨走**瓦片之间的空档**，不要压在瓦片上。空档宽度就是版式里的 gap，先定 gap 再定轨。
- IO 瓦片沿上边缘排一行，**每块头上写速率**（`Gen5 · 32 GT/s`）—— 这是外人最先想知道的数字。
- 内存控制器画在左右两侧、die 边框**外面**，后面接 DIMM 梳齿。画在里面会跟瓦片抢地方。
- **一条被追踪的请求**用 §4.7 的「本次运行」箭头，配 3 个编号徽章：进站 / 命中哪片切片 / 出到哪个控制器。
  编号写进 `aria-label`，图注里逐条对上。

### 15.13 数据通路图（datapath）

**这是什么**：把一次查找画成**器件级**的通路 —— 地址拆成字段、译码器选中一行、
比较器逐路比 tag、匹配线一边进或门出 `HIT`、一边当多路选择器的选择端。

**没有它会怎样**：只画「查 cache → 命中 / 未命中」这个框图，就答不出
「四路组相联为什么需要四个比较器」「valid 位到底参与什么」。
这些问题的答案就是通路的形状本身。

**为什么这么设计**：为什么用梯形画多路选择器、三角画比较器、盾形画或门，而不是统统画方块？
因为这套形状是**读者已经会的词汇**（教科书和数据手册里几十年就是这么画的），
换成方块就得每个都写标签，图立刻变吵。代价是这套形状只在硬件语境里成立 ——
画软件流程时不要用，那里方块才是通用词汇。

**什么场景会用到**：讲 cache / TLB 组织、讲仲裁器、讲流水线转发、
讲一个寄存器读出来为什么要走那么多级。

**机制细节**
- 顶上先画**地址字段条**，位号标在条的上沿两端（`47`…`12`），字段名写在条里。
- 比较器有两个输入：一路来自阵列里存的 tag，一路来自地址。
  **两路必须从不同的边或不同的高度进**，否则读者分不清谁是谁。
- 多路选择器画成**左宽右窄**的梯形，数据从宽边进、结果从窄边出、选择端从底边进。方向反了就是错的。
- 总线画一根线，宽度用**斜杠 + 数字**标（`/4`）。这是行业记法，比画四根线省地方且更准。
- 一定要留一句反例说明（图里的 `way 1 is invalid, so its comparator can never assert`）——
  数据通路图最容易被当成「所有路都一样」，写死一路失效才讲清 valid 位干什么。

### 15.14 报文逐层封装 + 字节标尺（packet-encap）

**这是什么**：同一个报文在协议栈里往下走，每一层加自己的头尾，**画在同一把字节标尺上**，
所以每根条的长度就是它的字节数，下一层比上一层长出来的那截就是这层加的东西。

**没有它会怎样**：用「层 1 → 层 2 → 层 3」的方块图，读者知道有封装，
但不知道**加了多少、加在哪一头**。开销算不出来，抓包时也对不上偏移。

**为什么这么设计**：关键是两条**贯穿上下的虚线**，钉住第一层那段的左右边界。
有了它，「下层只在外面加、绝不动里面」这件事是**看出来的**，不是读出来的。
替代方案是每层各画一张、旁边写字节数；不选是因为读者得自己做减法，而减法正是这张图要替他做的。

**什么场景会用到**：讲协议栈开销、讲 DMA 描述符 / 环形队列的每项布局、
讲为什么小包效率低、讲 MTU 怎么算。

**机制细节**
- 先定 **px / byte**（模板用 8），图里明写。定了之后所有条的宽度都由字节数算出来，不许手调。
- 窄字段（1–4 字节 = 8–32 px）**塞不下文字**：用括线引到条外写，别缩字号。这是本图型最常见的翻车点。
- 标尺刻度按 8 字节一格画在条的下沿，别画满每字节 —— 密到一定程度就成噪点。
- 最后一层可以接**按 lane 分发**：n 条 lane 列，第 n 个字节进第 `n mod lanes` 列。
  这一段是竖的，跟上面横的条形成对比，正好当图的收尾。

### 15.15 终端实录标注图（terminal-annotated）

**这是什么**：把**真实的**串口 / dmesg / lspci 输出原样放进一张深色终端卡，
在具体的行上钉编号徽章，右边一列写这行为什么重要，再用半透明色块盖住行里最关键的那几个字。

**没有它会怎样**：把 log 贴进 `<pre>` 里，读者面对二十行等宽字，不知道该看哪一行；
或者把 log 改写成「大意是……」，那就丢掉了唯一能跟现场逐字对上的东西。

**为什么这么设计**：为什么不重画一张示意图？因为这张图的**全部说服力来自它没被改过**。
读者要能拿自己机器上的输出跟它对，一改就对不上了。
所以规矩是**只加不改**：徽章、色块、右栏注释都在原文之外，原文一个字符不动。
（跟全局约定「原始日志一律不脱敏」同一条理由。）

**什么场景会用到**：交付调试结论、写踩坑记录、教别人怎么读一段 log、
给协作方说明「我们看到的现象长这样」。

**机制细节**
- 终端卡用等宽字体，并给每行加 `textLength` + `lengthAdjust="spacing"`。
  **这是色块能画准的唯一办法**：字符步进 = `textLength / 字符数`，
  于是色块的 x 可以从字符下标算出来，换字体也不跑位。不加 `textLength`，
  色块就得靠目测，改一次文字就错一次。
- 色块画在文字**下面**（先画 rect 再画 text），透明度 0.26 左右；盖在上面会糊掉字。
- 徽章钉在行的右端、卡片内侧，引线走到右栏。**徽章编号顺序必须跟行号顺序一致**，
  引线才不会交叉。
- 右栏每条注释：一行标题（这行说明什么）+ 二到三行正文（为什么它重要）。别复述 log 原文。
- **留一段"正常的"在图里**。全是报错的 log 读者会怀疑整个环境坏了；
  留几行成功的，才说明「log 本身是好的，坏的是这一处」。

### 15.16 结构体指针图（struct-graph）

**这是什么**：把几个结构体画成带字段行的卡片，**指针箭头从持有它的那一行出发**，
落到目标卡片的标题栏上。

**没有它会怎样**：常见画法是「结构体 A → 结构体 B」两个方块一根箭头。
读代码时真正要回答的是「**哪个字段**指过去的」——因为改的就是那个字段。
方块级的箭头答不了，读者还得回去翻头文件。

**为什么这么设计**：箭头**起点在字段行、终点在标题栏**是不对称的，这是有意的：
起点精确到字段（那是一个具体的地址），终点是整个对象（指针指向对象，不指向对象的某个字段）。
反过来画（从卡片边出发、指到某个字段）就把语义说反了。

**什么场景会用到**：读一个陌生子系统、讲生命周期和引用计数、
讲某个字段为什么必须单独存在、给新人讲一条数据结构链。

**机制细节**
- 指针字段的行尾画一个**实心点**，那就是箭头的起点。非指针字段没有点。
- 右列写类型或当前取值，写哪个都行，但一张图里统一。取值更适合讲一次具体的运行。
- **同类兄弟对象只详画一个**，其余只留区分它们的那几行（模板里三个 VMA，只有第一个是全的）。
  三张一模一样的卡片是浪费版面，也让读者以为它们有区别。
- 卡片标题用等宽字体写 `struct xxx`，行内字段名也用等宽 —— 它们是代码里的标识符，
  跟散文字体混排会读成散文。
- 字段名和顺序**必须跟真头文件对得上**，并在图脚注明版本（`v6.6`）与
  「行序是阅读顺序、不是结构体偏移顺序」。不写这句，读者会拿它当内存布局用。

### 15.17 总线挂载框图（bus-fabric）

**这是什么**：把互连画成**几条横轨**，主设备挂在轨上方、从设备挂在下方，
每条引下线标自己的位宽，轨上写跑在它上面的通道名，再叠一次被追踪的读事务。

**没有它会怎样**：换成「主 → 互连方块 → 从」的画法，就看不出
「谁和谁共享带宽」「桥后面那一段窄在哪里」。共享和分层是横轨这个形状自己说出来的。

**为什么这么设计**：真实的 AXI NoC 是交换式的，不是一根共享总线 —— 这张图明知如此还画成轨，
是因为**要讲的是挂载关系和位宽变化，不是仲裁实现**。所以图脚必须写明
`rails are a drawing, not a topology claim`。不写这句，图就变成了一个错误的技术论断。

**什么场景会用到**：讲 SoC 内部分层（高速轨 / 低速轨）、讲某个外设为什么只能到 32 位、
讲桥两侧的位宽和时钟域、讲一次读事务经过哪些部件。

**机制细节**
- 轨用 4–6 px 的深色圆角矩形，比任何连线都粗 —— 粗细本身就是「这是一条总线」的信号。
- 仲裁器画成**骑在轨上**的小卡片（盖住一小段轨），不要画在轨旁边。骑上去表示事务从它身上过。
- 被追踪的事务走**两条平行线**：去程实线在轨上方、回程虚线在轨下方，各带一个箭头。
  两条线离轨至少 12 px，否则跟轨糊在一起（实测：8 px 时看不出来）。
- 每条引下线标位宽（斜杠 + 数字）。位宽在桥两侧变化，正是这张图最该被看见的地方。
- 低速轨比高速轨**短**，左右都不要对齐 —— 长度差本身就说明它只服务一部分设备。

### 15.18 调用关系图（call-graph）

**这是什么**：把几个模块画成容器，函数画成卡片，**每条边按"是哪一种调用"分别画**：
直接调用 / 经 ops 表的间接调用 / 异步交接 / 硬件事件进入 / 完成通知回来。

**没有它会怎样**：所有边长一个样，读者只知道 A 到 B 有关系，不知道
**A 调用 B 的时候还在不在同一个栈上**。而"在不在同一个栈上"决定了几乎所有事：
能不能拿锁、能不能睡、出错了栈上还有没有 A、改 B 会不会影响 A 的时序。

**为什么这么设计**：替代方案是所有边一样画、在旁边写字说明。不选是因为**边的种类是要被扫视的**，
不是被逐条阅读的 —— 读者第一眼要看出"这张图里有几处换了上下文"。
颜色和箭头形状能一眼扫完，文字不能。
代价是要先定死一套边的词汇表并放进图例，而且**图例必须在图的最上面**：
这类图的图例不是附属说明，它就是这张图的读法。

**什么场景会用到**：读陌生子系统、讲一个功能牵扯几个驱动、排查"改了 A 为什么 B 坏"、
交接一块代码给别人。

**机制细节**
- 五种边的固定画法（anthropic 版）：
  | 边 | 线 | 箭头 | 标什么 |
  |---|---|---|---|
  | 直接调用 | 实线 1.6 深墨 | 实心 | 不标 |
  | **经 ops 表** | 实线 1.6 蓝 | **空心** | 成员名 `.atomic_flush` |
  | **异步交接** | **虚线** 金 | 实心 | **交接原语** `queue_work()` |
  | 硬件事件 | 折线闪电 橙 | 实心 | 中断源 |
  | 完成通知 | **点线** 绿 | 实心 | `complete(&x)` |
- **容器 = 谁编译进哪个模块**，不是"谁在架构上属于谁"。跨容器的边才是要小心的边。
- 函数卡右上角挂**上下文徽章**（`process` / `kworker` / `hardirq`）。
  两张卡的徽章不一样 = 它们之间那条边一定换了上下文，画成虚线才对。
- 允许一条边**飞过中间的容器**（模板里 `.prepare` 就是这样）——
  那不是画得难看，那是事实：core 通过 `drm_panel` 直接够到面板，不经过显示驱动。
- 图脚写一句**这张图跟 grep 的关系**：`grep 只找得到黑色实线那几条`。
  这句话是读者把图收进脑子的钩子。

### 15.19 调用栈快照（call-stack）

**这是什么**：一份真实 backtrace 画成叠起来的帧，**外加一条断层线**，
标出"从这里往下，上一帧不再是调用者"。

**没有它会怎样**：把 backtrace 贴成一列文字，读者会**默认整列都是调用链** ——
于是花半天去看 `process_one_work` 为什么调用 `commit_tail`。它不为什么，
它调用的是队列里排到的任何东西。

**为什么这么设计**：断层线是这张图存在的全部理由。替代方案是在文字旁边加注释说明；
不选是因为注释会被跳过，而**一条横穿整张图的线跳不过去**。
断层之下画成"骨架"、断层之上画成"这次的活"，是把一个抽象概念变成版面分区。

**什么场景会用到**：讲 oops 怎么读、教新人认异步边界、写踩坑记录、
跟人解释"你要找的调用者不在这张栈上"。

**机制细节**
- 帧**贴着叠**（间隙 4px），别当成卡片列表排开 —— 栈就该看着像栈。
- 每帧三段：`#序号` · 函数名（等宽）· `+偏移/大小`（等宽，右对齐）。
  偏移那一段要留着，图注解释它是喂给 `addr2line` 的东西。
- 外部模块帧挂 `[module]` 徽章。**bug 几乎总在带徽章那一侧** —— 这句写进图注。
- 断层线右端接一张**虚线幽灵卡**，写真正的调用者和"它不在这张栈上"。
  幽灵卡必须是虚线，跟实线的帧区分开：它不是这次栈上的东西。
- 右栏留一条注释专门教**认骨架帧**：`process_one_work`/`worker_thread`（工作队列）·
  `call_timer_fn`（定时器）· `rcu_do_batch`（RCU）· `el0_svc_common`（系统调用入口）。
  每一个都标着一道同样的断层。

### 15.20 运行时泳道时间线（runtime-timeline）

**这是什么**：几个执行上下文各占一条泳道，共用一根时间轴，
函数执行画成块，交接画成跨泳道的箭头，**关键的等待画成轴下面的括线**。

**没有它会怎样**：只画"中断 → 软中断 → 工作队列 → 线程"这个链，
就答不出最要紧的问题：**每一跳等了多久**。而延迟问题全部住在跳与跳之间。

**为什么这么设计**：**画间隙，不画箭头**。箭头只说"然后发生了这个"，
只有间隙说得出"什么时候"。所以这类图里箭头是次要元素，
**轴下面那几条带数字的括线才是主角**。
代价是必须有真实测量（`trace_printk` / ftrace），编不出来 —— 这是好事。

**什么场景会用到**：讲为什么 tasklet 和 workqueue 不能互换、
定位卡顿、跟人解释"你加的这个 `queue_work` 让路径长了 60 µs"。

**机制细节**
- 泳道**按"能不能睡"排序**，不按调用顺序：hardirq → softirq → 线程。
  副标题写清每条泳道的约束（`irq disabled · must not sleep`）。
- 块窄于约 100px 时标签放**块的上方**，不要缩字号（同 §15.14 的窄字段规矩）。
- **等待也是内容**：线程在等的那一段画成斜纹条，不要留白。留白读作"没这回事"。
- 至少画三条括线：一条正常的、一条正常的、一条**离谱的**，让离谱那条有参照。
  离谱那条上金色加粗。
- 轴的单位写在轴左端（`µs`），别只写在标题里。

### 15.21 一帧的数据通路（frame-pipeline）

**这是什么**：一条硬件通路上的每一级各占一条泳道，共用一个帧周期的时间轴，
**下面同轴画出 vsync / TE 这些信号**，再用贯穿所有泳道的竖线标出触发点。

**没有它会怎样**：把 GPU → DDR → DMA → DSI → 屏画成一串方块，
就看不出**它们是同时在跑的**，也看不出这一帧的 deadline 在哪。
掉帧不是"某一级慢"，是"某一级越过了那条竖线"。

**为什么这么设计**：两个决定。
① **共享内存那一级要拆成两条小条** —— 一条 GPU 在写后台缓冲，一条扫描输出在读前台缓冲。
   合成一条就看不见争用，而 GPU 一忙扫描输出就 underrun 正是争用的结果。
② **deadline 画成一条 vsync 边，不是一个数字**。
   画成边之后 slack 会自己量出来，读者不用做减法。

**什么场景会用到**：讲掉帧、讲 double/triple buffering 为什么这么排、
讲 TE 信号干什么用、跟屏厂对时序。

**机制细节**
- 触发点用**编号徽章 + 贯穿所有泳道的虚线**。徽章编号必须在图注里逐个点名（§5）。
- 相邻两个触发点靠得太近时**把其中一个的时刻挪开一点**，别把徽章叠在一起 ——
  实测两个徽章相距不足 40px 就会糊成一坨。
- 信号行（vsync / TE）跟泳道**共用同一根轴**，不要另起一张图。
  同轴是这张图一半的价值。
- 最后画一条 slack 括线，配一句"越过它会怎样"。没有这句，前面画的全是描述，不是结论。

### 15.22 跨核调用（multicore-calls）

**这是什么**：几个 CPU 各占一条泳道，共用时间轴，画出 IPI 的扇出、
各核的**应答**、以及一把自旋锁上的等待。

**没有它会怎样**：`smp_call_function_many()` 画成一个扇出箭头，
读作"广播完就走"。实际上它**要等每一个核都应答**，
于是最慢的那个核决定了发起方阻塞多久 —— 扇出图完全表达不了这件事。

**为什么这么设计**：**必须把应答箭头也画出来**。只画扇出读作 fire-and-forget；
应答画上去，这件事才变成一次等待。这是这张图跟普通"多核架构图"的唯一区别，
也是它存在的理由。

**什么场景会用到**：讲为什么长时间关中断是**系统属性不是局部属性**、
讲自旋锁的真实代价、讲 per-CPU 变量为什么能省掉这一整套。

**机制细节**
- **自旋画成斜纹条**，并在标签里写明"烧 CPU，不是睡"。这是自旋锁最常见的误解。
- 每条泳道的副标题写它**为什么是这个样子**（`irqs off in a long section`），
  不要只写核号。图的结论就藏在这些副标题里。
- 画两条括线：发起方阻塞多久、等锁方自旋多久。前者配一句
  "由最慢的应答者决定，不是平均值"。
- 图脚补一句 per-CPU 的对照 —— 有对照，读者才知道这一整套开销是可以不付的。

### 15.23 上电时序（power-sequence）

**这是什么**：电源轨、时钟、复位、链路状态、初始化命令、背光各占一行，
按**事件**（不是按线性时间）排开，中间用括线标出 datasheet 的约束，
上方用横条标出**每一段归哪个驱动回调管**。

**没有它会怎样**：上电顺序写成一串文字步骤，读者照着写代码，
但**约束（要等多久）和归属（写在哪个回调里）全丢了** ——
而屏点不亮的原因几乎总是这两样之一。

**为什么这么设计**：为什么不按线性时间画？因为约束跨了四个数量级
（复位低电平 10 µs，睡眠退出到背光 120 ms）。按真实比例画，10 µs 那段是 0 像素。
所以**按事件排、图上明写 `not to scale`、真实数字全部交给括线**。
这是 datasheet 几十年的画法，读者已经会读。

**什么场景会用到**：新屏点亮、跟屏厂对上电时序、代码评审时核对
`.prepare` / `.enable` 的分工、查开机白闪。

**机制细节**
- 顶上那条**回调归属横条**是这张图比 datasheet 多出来的东西：
  datasheet 只讲硬件，这条把它接到代码上。
- 关键事件画**贯穿全图的浅虚线**，括线才有依附，不然括线像浮在空中。
- 每条约束标 `t1 ≥ 10 ms` 这种形式（**带不等号**）——
  它是下限不是精确值，写成 `10 ms` 会被人当成延时函数的参数照抄。
- **必须写下电顺序**：严格逆序，每一步都要，包括那些等待。
  只反转电源轨、不管命令顺序，屏上会留电荷。
- 图脚给**每条约束对应的现场症状**（t1 不够 → 屏根本不应答；
  t4 不够 → 每次开机白闪）。有症状，这张图才能拿去查问题，而不只是拿去抄。

### 15.24 物理数据通路（soc-dataflow）

**这是什么**：画"哪个硬件真的发出了这次读请求，走的是哪根线"。
外框是封装边界，**框外的东西是板子上另一颗芯片**（DDR 在一边，屏在另一边）。
框内按数据实际流动的方向排：内存 → 内存控制器多端口 → 片上互连 → 各个主设备 → 像素接口 → 屏。

**没有它会怎样**：讲显示通路时最常见的画法是一排方块加一串箭头，
读者会得到"数据像水一样从左流到右"的印象，于是**把配置和数据当成同一件事**。
真正要纠正的误解——"设置帧缓冲 = 把图搬过去"——正好被这种画法固化。

**为什么这么设计**：为什么把配置路和数据路画成两种线？
因为整张图的论点就是这两条线**量级差六个数量级、方向相反、物理上不是同一根线**：
一边每帧 4 个字节的寄存器写，另一边每帧 8.3 MB 的总线读。
用同一种箭头画，这个区别就没了，图也就不值得画。
替代方案是给箭头标数字——试过，读者会跳过数字只看形状。**形状本身必须带信息。**

**什么场景会用到**：跟人解释"帧缓冲到底是什么"、新人问"图是怎么到屏上的"、
排查撕裂时判断该看带宽还是看面板时序、代码评审时确认 DMA 属于哪个 IP。

**机制细节**
- **两种线**：配置路金色虚线（APB / I2C 这类低速寄存器总线），
  数据路橙色实线（AXI 这类高带宽总线）。图例必须画出来，否则读者以为是随手配色。
- **数据线要落在具体端口上**，不能随便找块地方插进内存框。
  画在 `p2` 上并在旁边写清"这个口的优先级最高、扫描输出等不了"，
  才把"内存控制器为什么要有优先级"这件事一并讲了。
- **封装边界用虚线，并且在线上写一句**"这条线以外是另一颗芯片"。
  不写这句，读者不知道虚线是分组还是封装。
- 编号徽章沿数据方向串一遍，图脚一行一句展开——**徽章负责顺序，图脚负责因果**。
- ⚠ **图脚字数要算**：一行文字装不下会被 viewBox 裁掉，而且不报错、不换行（§20）。
  生成脚本里直接写死断言，例如 `assert len(line) * 6.4 < 1056`，踩线就炸，
  不要靠"记得有这条规矩"。

### 15.25 GPU 的数据流向（gpu-dataflow）

**这是什么**：回答"GPU 参与之后数据去了哪"。中间横着一条**共享的内存地址条**，
上面按地址排开几个租户（命令缓冲 / 页表 / 纹理 / 前台缓冲 / 后台缓冲），
CPU 和 GPU 在上方、显示侧在下方，**所有箭头都终止在这条地址条上**。

**没有它会怎样**：不画这张图，"上传到 GPU"这个说法就永远纠正不过来。
读者会以为 GPU 是一个数据的**目的地**，于是去找"上传耗时"、
去优化一个根本不存在的拷贝，或者在没有显存的芯片上套用显卡的性能模型。

**为什么这么设计**：为什么把 GPU 画成敞开的、把内部每块存储的容量都标出来？
因为**论点要靠读者自己算出来**才成立：tile buffer 2 KiB、L2 256 KiB，
而一帧 8.3 MB——数字摆在一起，"里面放不下"是读者得出的结论，不是图作者宣布的。
画成一个不透明的方块，读者只能选择信或不信。

为什么七个箭头全部落在同一条条上？因为**"东西没有移动"是一个否定命题**，
否定命题没法用箭头直接画。能画的是它的反面：**每一次访问的终点都是同一块内存**。
读者数完七个终点，自己就得出"没搬过"。

**什么场景会用到**：解释"上传纹理"在手机芯片上到底发生了什么、
讲双缓冲为什么不需要拷贝、说明为什么 GPU 一忙显示就抖、
纠正把独立显卡那一套理解直接套到集成 GPU 上的方案。

**机制细节**
- **前台 / 后台两块缓冲要分开画并各给地址**，且让显示侧的箭头落在前台、
  GPU 的箭头落在后台。翻页是换地址，图上要看得出来。
- **GPU 的页表也画在地址条上**。这一笔很值：它顺带说明了 GPU 的 MMU
  跟 CPU 的 MMU 是两套，而两套页表都住在同一块 DDR 里。
- **必须留一块"例外说明"**：独立显卡有自己的显存，那边的"上传"是真拷贝。
  不写这块，读者会觉得图作者不知道显卡是怎么回事，整张图的可信度一起掉。
  这也是"上传"这个词的来历——**讲清词从哪来，比说"这个说法不对"有用得多**。
- 缓存一致性单独标一句（"要么刷缓存，要么 GPU 读到还留在缓存里的旧字节"）。
  它不是数据流的一环，但是这条路上最常见的一类 bug，图上不提就没人想起来。
- 地址写成 `0x8321_0000` 这种**带下划线分组**的形式，比裸十六进制好读一个量级。

### 15.26 有独立显存时的数据搬运（vram-dataflow）

**这是什么**：§15.25 的对照图。台式机显卡自带显存，于是图上有**两条地址条**，
中间只有一根 PCIe。左半是主机内存，画成上下两排装着**同一批物理页**：
上排是普通页面（显卡够不着），下排是同一批页面被锁住并通过 GART 映射之后的样子。
右半是显卡：它自己的 die（搬运引擎、着色器阵列、L2、显示引擎）加它自己的显存。

**没有它会怎样**：只画集成的那张，读者会以为"数据从来不用搬"是普遍真理。
可"上传"这个词有真实来源，不讲清来源就只是断言别人错了。
更要紧的是,**读者真正想知道的是有显存那种情况下字节到底怎么过去的**——
只写一句"独立显卡是例外"等于把最该画的一步留给了文字。

**为什么这么设计**：为什么要跟 §15.25 用同一套地形和配色，只改地址条的数量？
因为这两张图的差别**必须落在一处**，读者才看得出是哪一处。
一张一条地址条、所有箭头终止在上面；另一张两条地址条、中间一根线——
把别的都保持不变，"多了一块内存"这件事自己会跳出来。
如果第二张换个构图重画，读者得先重认地形，差别就淹掉了（§16 同一道理）。

为什么左边要画成**上下两排同一批页面**，而不是画一个"内存"方块？
因为这张图第二重要的结论是：**锁住页面 + 建映射，一个字节都没搬**。
画成一个方块就说不出这件事；画成两排、并在中间的箭头旁写上函数名，
读者自己看得出这一步的产物是一条表项不是一次拷贝。

**什么场景会用到**：讲"上传纹理"到底发生了什么、解释为什么显存不够会突然变慢
（数据被挤回主机内存、每次访问都过 PCIe）、说明为什么要一次上传反复用、
以及跟人区分集成与独立显卡的性能模型。

**机制细节**
- **搬运引擎要单独画成一个框并高亮**。整张图的关键就是"发起这次拷贝的是显卡，不是 CPU"——
  这跟集成那张的规则是同一条（谁要数据谁发读请求）。画成一条无主的箭头，这条规则就丢了。
- **die 一行和显存一行都按故事顺序从左往右排**（搬运引擎 → 着色器 → L2 → 显示引擎；
  纹理 → 后台缓冲 → 前台缓冲）。排对了，每条箭头都是短的竖线，不用横穿别的框。
  这是最省事的防重叠办法：**先排好顺序，再画箭头**，比画完再挪省十倍力气。
- **CPU 能看见的那个窗口要画出来**，并写清它通常远小于显存。
  这解释了为什么驱动宁可用引擎搬也不让 CPU 直接写。
- 符号名全部用主线内核里的真名（`TTM_PL_SYSTEM` / `AMDGPU_GEM_DOMAIN_GTT` /
  `dma_map_sgtable` / SDMA）。**编一个像模像样的名字，读者就没法验证；
  用真名，读者一搜就能对上。**
- ⚠ 右边贴边的竖箭头会跟显存条下面那句说明**撞在一起**。落法跟 §15.24 一样：
  在生成脚本里给那句话写死宽度断言（`538 + 字数 × 5.75 < 箭头的 x`），撞了当场炸。

### 15.27 平台框图（platform-block）

**这是什么**：画**这块板子**上，芯片跟外面的器件怎么连、走的是哪种接口。
中间一颗 SoC，外设按「归谁管」分组围一圈，每条连线上骑一个黑药丸写接口名。

**没有它会怎样**：`soc-block` 画片内、`system-topology` 画机器之间，中间这一层没人画。
于是「屏是怎么接上去的」「内存条插在哪」这类问题只能靠读原理图，
而原理图给的是网络表，不是给人看的拓扑。

**为什么这么设计**：为什么器件要画外形，不画标签框？
因为**标签框要先读才认得出**。绿色带金手指和缺口的一条 = 内存条，不用读字；
写着「DDR4 SDRAM」的圆角矩形，得读完才知道。
读者扫一眼图的时候认的是形状，不是文字。

为什么每条线上都要挂接口名？因为**线本身不带信息**。两个框之间画一根线，
只说了「有关系」；写上 `MIPI DSI x4`，才说清是哪种关系、多宽、能跑多快。
一张图上如果有五根线而只有两个名字，那三根就是装饰。

**什么场景会用到**：给新人讲板子结构、跟硬件对接口、排查「这个器件到底挂在哪条总线上」、
写移植文档时说明新板子跟旧板子差在哪。

**机制细节**
- **分组名骑在没有线穿过的那条边上**。上边有线就挂下边。跟线抢位置的结果是两个都看不清。
- **线要比药丸长得多**。第一版左右各留 82px 间隙、药丸 85px，
  结果药丸把线整条压在下面，看起来根本没连。**留 130px 以上**，两头各露 20px 才读得出是一根线。
- 编号只给「像素真正走的那几根线」，把它们跟只走引导代码 / 控制字节的线分开。
  一张平台图上线很多，不分类等于没画。

### 15.28 多地址空间对照（address-spaces）

**这是什么**：几条地址空间条纵向叠放，同一块内容在每层的位置用竖虚线上下连起来，
两层之间放一个翻译盒写清是谁做的翻译。

**没有它会怎样**：「设备看到的地址跟 CPU 看到的不是一回事」这句话，
在一条地址条上**画不出来**。不画，读者就会拿着一个物理地址去问设备为什么读不到。

**为什么这么设计**：为什么要叠起来而不是并排？
因为要表达的是**同一块内容的三个身份**，叠起来才能用竖线一条条连上；
并排放，读者得自己在两张图之间找对应，那正是这张图想省掉的力气。

为什么斜纹带要跟实心段区别对待？因为**它不是存储**。
一段实心色表示「这里有字节」，斜纹表示「往这儿读会落到别处」。
两者用同一种画法，读者会以为设备上真有那么大一块内存。

**什么场景会用到**：讲 DMA 为什么要传物理地址、讲 IOMMU 挡住了什么、
讲显存和主机内存为什么不能互相解引用、排查「地址对但读到垃圾」。

**机制细节**
- **边界值用黑药丸挂在条外，虚线指到那条边界线上**。值属于边界，不属于哪一段——
  写在段里，读者会以为那是段的起点还是终点都说不准。
- 药丸挂上边还是下边，看那一侧有没有别的东西。挂下边正好撞上翻译盒是第一版踩的坑。
- **图脚要收在一句能带走的话上**：「光有一个指针永远不够，它只有连同所属空间一起说才有意义」。
  图讲完机制，图脚讲能用的判断依据。

### 15.29 拷贝与共享对照（copy-vs-share）

**这是什么**：同一张底图画两遍，上下两半用**完全相同的坐标**，差别只有一处——
中间有没有那个橙色 COPY 块。

**没有它会怎样**：「到底搬没搬」这件事，**文字定不了**。
「交给它」「发过去」「上传」「传进去」对两种情况都说得通。
不画出来，团队里两个人可以用同一句话指两件完全不同的事，还以为在说同一件。

**为什么这么设计**：为什么两半要用一模一样的坐标？
因为读者的注意力应该全部落在那**唯一一处**差别上。
换个构图重画，读者得先重认一遍地形，差别就淹掉了（跟 §16 同一道理）。

为什么橙色只给那个块？因为橙是焦点色。这张图的焦点就是「有没有这一块」，
别处再出现橙色就是在分散那唯一要看的地方。

**什么场景会用到**：讲零拷贝、讲共享内存与消息传递的差别、
纠正「上传到 GPU」这类说法、评审里判断某个方案到底省没省一次拷贝。

**机制细节**
- **两个使用方指向同一段 = 没搬**；中间插一个橙块 = 搬了。就这两种画法，不要有第三种。
- 橙块上写清**搬了多少**（`8.3 MB`）。没有量的拷贝块只是个标记，有量才有代价。
- 使用方盒子跟地址条之间**要留出画箭头的空间**。第一版只留 6px，箭头几乎看不见。
  上下各留 38px 以上。
- 图脚给一条能带走的判断依据：**没有橙块，就没有拷贝**——读者拿这条去看别人的图。

### 15.30 会动的数据通路（dataflow-animated）

**这是什么**：仓里唯一一张会动的图。线用虚线画，让 `stroke-dashoffset` 循环变化，
虚线段就沿着线走起来。**流动的线 = 硬件一直在走的通路；静止的线 = 发生一次就完了。**

**没有它会怎样**：静态图说不出「这条一直在跑，那条一帧只发生一次」——
两者都是一根带箭头的线，读者只能靠读字分辨，而字是最容易被跳过的。

**为什么这么设计**：为什么允许这张图动，别的都不动？
因为**这里的动作带着一条信息**。动画一旦是装饰，读者的眼睛就被拉去看没有信息的地方，
整张图的信噪比反而降了。判断依据只有一条：**去掉动画会不会丢掉一条说不出来的事实**？
答不上来就别动。

为什么用 CSS 不用 SMIL？因为**只有 CSS 认 `prefers-reduced-motion`**。
截图检查是以「关闭动效」跑的（`screenshot.mjs` 用 `reducedMotion:'reduce'`），
SMIL 动画不理这条，于是每次截图停在不同帧，检查就没法比对，
而且要求减少动效的读者会被强迫看动画。

**什么场景会用到**：讲连续通路与一次性配置的区别、讲扫描输出为什么等不了、
任何「这条路一直在跑」是重点的场合。

**机制细节**
- 做法：`stroke-dasharray: 13 9` + `@keyframes` 把 `stroke-dashoffset` 推到 `-44`
  （必须是「虚线段 + 间隔」的整数倍，否则循环处会跳一下）。
- **三条关闭动效的口子照 glass 现成的约定**（`skills/glass-design/assets/glass.js:12-13`）：
  `prefers-reduced-motion: reduce` · `html[data-motion-freeze]` · 页面 hash 含 `freeze`。
- **类名和 keyframes 名必须加前缀**。图被内联进图集之后，这段 CSS 是全文档生效的，
  裸的 `.flow` 会串到别的图上。
- ⚠ **动画要实测,别假定**。做法:不关动效连拍两张比 md5，应当**不同**；
  开 `reduce` 再连拍两张，应当**相同**。两条都验过才算这动画是可控的。
  只看一眼「好像在动」不算——停不住的动画会让截图检查每次结果都不一样。

### 15.31 带方向的流动线（三张图共用的画法）

**这是什么**：把连线画成会流动的虚线，虚线段朝数据走的方向走。
两头都传的那种连线**画成上下两条各流各的**，不画一条双箭头线。
`page-flip` / `gpu-memory-flow` / `vram-copy-flow` 三张都用这套。

**没有它会怎样**：静态图上，「谁读谁」只能靠读字。
而读者扫图的时候不读字 —— 于是「上传到 GPU」「把帧交给显示控制器」
这类说法就一直纠正不过来，因为图从来没反驳过它们。

**为什么这么设计**：为什么双向不画一条双箭头线？
因为**一条线上的虚线只能朝一个方向走**。画成双箭头，动的方向就跟其中一个箭头相反，
读者要么忽略动画，要么被误导。两条各流各的，读者一眼看出哪边在往哪边送 ——
也就一眼看出**是谁在拉、谁在推**。

为什么不是所有线都动？因为**动本身就是在说一句话**：这条通路一直在跑。
一帧只发生一次的事（写一个寄存器）画成静止的，两者摆在一起才有对比。
全都动等于什么都没说。

**什么场景会用到**：讲数据通路、讲拷贝与共享、讲 DMA 由谁发起、
任何「方向」本身就是答案的图。

**机制细节**
- 做法见 §15.30：`stroke-dasharray` + `@keyframes` 推 `stroke-dashoffset`，
  推的距离必须是「虚线段 + 间隔」的整数倍。反向就是把终值取正。
- **箭头方向必须跟流向一致**。不一致比不画箭头还糟。
- **流动线比静态线抢眼得多**，所以更容易压住文字。这三张图各踩了一次：
  一句说明被竖线穿过、一个徽章压在线上、一个徽章落进了 COPY 块里。
  落法：先排线，再放字；放完**渲染出来看一眼**，机器检查抓不全这类。
- ⚠ **动画必须实测**，别看一眼「好像在动」就算：不关动效连拍两张比 md5 应当**不同**，
  开 `reduce` 再拍两张应当**相同**。`page-flip` 第一版就是忘了改成流动线，
  探针一跑立刻现形 —— 肉眼当时完全没看出来。

## 16. 同底递进图族(一套地形,讲清好几件事)

一张图讲不完的内容,默认做法是画一张更满的图。**这是错的方向** ——
读者的注意力先花在"认地形"(CPU 在哪、内存在哪、线怎么走),再花在"读新信息"。
一张更满的图把两笔开销叠在同一个时刻;每节重画一张构图不同的新图更糟,读者每次都要重新认一遍地形。

**图族的做法**:同一 viewBox、同一节点坐标、同一配色的 N 张图,
**第 k 张 = 第 k-1 张 + 恰好一层**。地形零成本复用,注意力全部落到新增那一层。

### 什么内容适合做成图族

判据只有一条:**同一张地形上先后发生好几件事**。典型三类 ——

| 内容 | 底图(不变的地形) | 逐张叠加的层 |
|---|---|---|
| 一次外设访问的全过程 | SoC 拓扑 | ① 拓扑 → ② + 地址空间条 → ③ + 这次访存的落点 → ④ + DMA 回程 |
| 启动阶段 | 存储介质 + 各级镜像的位置 | 每张点亮一级(BootROM → SPL → U-Boot → kernel),已跑完的置灰 |
| 协议分层 | 两侧镜像栈(§15.9) | ① 层次 → ② + 真实数据通路 → ③ + 对等虚线 |

不适合:两张图的**结论**不同(不是同一张地形上的两件事,而是两个话题)——那是两张独立的图,别硬凑。

### 五条硬规矩

1. **底不许动。** 节点坐标 / 尺寸 / 配色 / 标签,一个像素一个字都不改。
   要改就回头把整族一起改 —— 族里有一张对不上,复用的前提就没了,读者会以为地形真的变了。
2. **一张只加一层。** 加两层就没人知道哪一层解释的是哪一段话。
   忍不住想合并,通常说明这两层其实是同一件事,那就合并成一层、少画一张。
3. **caption 第一句写"这张比上一张多了什么"**,不重复描述整张图。
   第二句才是这一张的结论。重复描述全图 = 读者又被迫认一遍地形,图族白做。
4. **viewBox 全族完全一致,高度也是。** 新层放不下就把底图整体上移 —— **这是违规**,
   一移全族就对不上了。正确做法:**一开始就按最后一张的高度定 viewBox**,前几张下方留白。
   留白比错位便宜得多,而且留白本身在告诉读者"下面还有东西要来"。
5. **族 ≥ 3 张给编号**(`图 3-1 / 3-2 / 3-3`),正文按编号引用。

### 工程落法

底图存成一份 `templates/diagrams/<name>.svg`;族里每一张 = 这份底图 + 一个 `<g id="layer-N">` 覆盖层。
覆盖层里只放新增元素,**绝不修改底图的任何节点** —— 想强调底图里某个已有元素,
用叠加的方式(在它上面盖一个橙边 rect / 一颗徽章),不要回去改它本身的 fill。
这样"底不许动"从一条自律变成结构上做不到违反。

机器闸 `series-viewbox-drift` 检查同一页里连续 figure 的 viewBox 是否一致。

### 反模式

| ❌ 别做 | 它教错了什么 |
|---|---|
| 每节一张构图不同的新图 | 读者每节重新认地形,新信息反而被认地形的开销盖住 |
| 一张图把四层全画上,靠 caption 分段解释 | 图上四层同时在场,读者无法知道读到第二段时该看哪一层 |
| 族里某张为了放下新层把底图挪了 | 挪了就不是同一张地形,图族唯一的好处当场消失 |
| caption 每张都完整描述一遍全图 | 等于宣布这几张之间没有承接关系 |
| 用图族凑数(同一张图改个标题算两张) | 图密度合约(§12)看的是信息量,不是 figure 标签数 |

## 17. 构件字形库（glyphs.svg）

`templates/diagrams/glyphs.svg` 是一份**片段集**,不是一张图 —— 里面每个 `<g id="…">` 可以整段复制进任何工程图。
它解决的是同一个问题:**一个圆角矩形能代表任何东西,所以它什么都没说**。
硬件图里"队列""字节流""插槽""端口"各有通行画法,用对了读者一眼认出;
用一个方框加一行字,则必须读字才知道这是什么。

| glyph | 画法 | 表示 | **不要拿它表示** |
|---|---|---|---|
| `g-queue` | 矩形 + 内部等距竖线(梳齿,间距 10-12) | **有容量上限、按序进出**的东西:FIFO、ring buffer、credit 池、请求队列 | 一般的缓冲区 / 一块内存 —— 梳齿在承诺"格子数就是深度",没有深度概念就别画格子 |
| `g-bytestream` | 长条 + 底沿刻度(长短刻度交替,像尺子) | **被序列化的字节流**:报文、TLP、帧。刻度在说"这是按字节量的" | 地址空间条(那是 §15.10;刻度会被读成地址刻度) |
| `g-slots` | 一排等距小竖圆角条(4-6 条)+ 下方药丸写名字 | **可插拔的位置**:PCIe 槽、DIMM 槽、SFP 笼 | 焊死的器件 —— 槽在说"这里可以空着,也可以插别的" |
| `g-porttab` | 骑在父框边界上的小墨色标签(竖排字或 ≤4 字符) | **属于这块芯片的接口**:IMC、RP、PHY | 独立的部件 —— 贴边 = 从属;要表达"另一颗芯片"就画独立卡 |
| `g-devcard` | 白卡 + 顶部墨色边条(高 14)+ 边条上一颗白点 + 卡内型号文字 | **一块可插拔的板卡 / 模块**:NIC、SSD、加速卡 | 芯片内部的 IP 核 —— 边条模拟的是挡板,片内没有挡板 |
| `g-accoupling` | 线上两道 8px 短竖线(间距 4) | **AC 耦合电容**,画在差分对上 | 任何"断开 / 隔离"的泛化含义 —— 它是一个具体元件 |
| `g-sync` | 线穿过域边界处的小方块 + `sync` 标注 | **跨时钟域同步器** | 跨任何别的边界 —— 只给时钟域 |

**通用规矩**

- **厂商 logo 一律不进 SVG。** 器件卡里写型号文字(`200 GbE NIC · 2×QSFP56`),不嵌 logo:
  一是版权,二是 logo 一旦是位图,这张图就改不动了 —— 而模板存在的前提就是能改。
- **glyph 的外形是中性的,但它身上的颜色仍归 §1 管。** 形状(梳齿 / 刻度 / 槽 / 贴边)用墨色;
  要上色时只上**真语义**的那种:队列的读写指针 = 实心 hue 三角(§15.2 同款)、已插卡的槽 = 实心 hue、
  link 起来的 LED = 实心 hue 点。**橙色不给 glyph** —— 橙是焦点色,焦点该留给那条彩虚线(§4.7)。
  纯墨色到底的一张 glyph 表会触 `diagram-monochrome`(known-bugs 1.30),
  而这条闸是对的:一张什么色都没有的工程图读起来像没画完。
- **glyph 是名词,不是装饰。** 图里画了梳齿,就意味着这里真有一个深度有限的队列;
  没有队列却画梳齿,是在图上写一句假话 —— 比画个方框糟得多。

## 18. 超深调用链:唯一允许的 ASCII 图

`references/sequence-diagrams.md` 禁止用 `<pre>` ASCII art 画时序图,理由是**字符宽度**:
中文 2 格、emoji 1.5-2 格、ASCII 1 格,混在一起必然错位。
这条禁令的边界正好落在"有没有非 ASCII 字符"上 —— 于是有一个场景合法:

**内核调用链。** 30 层以上、每层都是纯 ASCII 的 C 函数名。画成 SVG 流程图必然不可读:
30 个节点的纵向流程图高度冲破 640px 线好几倍,压到能放下则字号掉到 6px。
这种内容 ASCII 树反而是最优解 —— 缩进天然表达深度,没有布局约束,而且可以直接复制去 grep。

**格式**

```
sys_read
  -> ksys_read
     -> vfs_read
        -> file->f_op->read_iter: ext4_file_read_iter
           |
           | EXT4
           V
           -> generic_file_read_iter
              -> filemap_read
                 -> folio_wait_bit             (blocks here)
                 |<---------------------------- resumes at this depth
                 -> copy_folio_to_iter
```

- **深度只用缩进表达**,每层 3 空格;`->` 表示调用。
- **跨子系统处插三行** `|` / `| 子系统名` / `V` —— 这是全图唯一的分层信号,它替代了流程图里的泳道。
- **返回 / 唤醒用 `<---` 横线**,画在它真正落回的那一层的缩进位置上。
  横线的**长度没有意义,落点的缩进有意义** —— 这是读者唯一能据以判断"回到哪一层"的东西。
- 函数名后可跟 `: 实际实现`(`file->f_op->read_iter: ext4_file_read_iter`):
  写出间接调用这一跳最终落到谁身上,是这类图最值钱的信息,也是流程图最难画的部分。

**硬红线**

| 规则 | 为什么 |
|---|---|
| **树体里一个非 ASCII 字符都不许有** | 中文一进来宽度就乱,整棵树错位 —— 这正是 sequence-diagrams.md 那条禁令的成因。中文注释写在树**外面**的 figcaption 里 |
| 必须包 `<pre><code>` + 容器 `overflow-x: auto` | 深树天然超宽,不给横向滚动容器会把整页顶宽(`page-overflow-x` 闸) |
| 超过 60 行折叠进 `<details>` | 首屏只留前 15 行 + 结论 |
| 只用于调用链 | 时序、状态机、架构一律走 SVG。ASCII 的优势只在"深度 + 纯标识符"这一种形状上成立 |

## 19. 一张图要同时活在三家 gallery：安全尺寸档

**这是什么**：同一份 SVG 会被 anthropic / apple / glass 三家的 gallery 各嵌一次，
而三家的图位渲染宽度差很远。**渲染字号 = 源字号 × 渲染宽 / viewBox 宽**，
所以同一份源在最窄那家会掉到 9 px 以下。这一节给出一个三家都过的档位。

**没有它会怎样**：在 anthropic 画好、看着舒服，搬进 apple 当场触
`dense-diagram-labels-small`（known-bugs §1.50）。每搬一次改一次字号，
三份文件的字号从此对不上，以后谁也不敢动。

**为什么是这个档**：2026-08-26 实测的三家图位宽度是 1086 / 946 / 1230 px。
取 viewBox 宽 **1120**，缩放分别是 0.970 / 0.845 / 1.098；
把最小标签定在 **12 px**，三家分别渲染成 11.6 / 10.1 / 13.2 px，
都在语料下限 9.96 px 之上。高度取 **≤ 560**，最放大的那家（glass 1.098）
渲染成 615 px，仍在 `diagram-oversized` 的 640 px 天花板之下。

| | anthropic | apple | glass |
|---|---|---|---|
| 图位渲染宽 | 1086 | **946**（最窄） | 1230（最宽） |
| viewBox 1120 时的缩放 | 0.970 | 0.845 | **1.098** |
| 12 px 源字号渲染成 | 11.6 | 10.1 | 13.2 |
| 560 高渲染成 | 543 | 473 | **615**（离 640 只剩 25） |

**什么场景会用到**：任何打算三家都放的图型模板。只给一家画的图不受这条约束。

**机制细节**
- **viewBox `0 0 1120 560`，最小 `font-size="12"`。** 记住约束来自两头：
  宽度被 apple 卡（字太小），高度被 glass 卡（图太高）。
- apple 那一份可以整体提到 12.5 / 13.5 —— 那是 apple 自己的字号台阶，不是为了过闸。
- 高度真的不够用时，**先砍内容再动 viewBox**。把 560 加到 620，glass 那份就是 681 px，直接超顶。
- 三家宽度是量出来的，会随各家版式改动而变。**改过 gallery 版式就要重量一次**，
  别拿这张表当常数用。

### 15.32 讲清一条硬件通路：九张图怎么分工

2026-09-01 用户看了当时那版显示通路页,原话:「**你觉得人们有理解了吗**……
一帧、前台、后台,这都是啥……**图你再想想看怎么画清楚尽可能所有的硬件细节**」。
当时那页有四张图、每道机械检查全绿。问题不在版式,在**一张图想说太多件事**。

拆法不是按硬件顺序切,是**按读者的下一个问题切**。每张图只回答一问,
而下一张图的题目就是上一张必然引出的那个问题:

| 图 | 回答的问题 | 上一张为什么会引出它 |
|---|---|---|
| `arm64-display-path` | 经过哪些硬件、走哪根总线 | 起点 |
| `what-is-a-frame` | 一帧多大,为什么片上放不下 | 全景图里两个盒子标着"装不下",凭什么 |
| `gpu-tile-render` | 装不下那 GPU 怎么画出来的 | 上一张刚证明装不下 |
| `display-controller-inside` | 屏上四层图是谁合起来的 | 全景图里显示控制器是个黑盒 |
| `buffer-roles` | 前缓冲后缓冲到底是啥 | 前一张出现了这两个词 |
| `dsi-panel-inside` | 像素怎么出芯片、屏里怎么点亮 | 前面所有图都停在芯片边界 |
| `bus-tenants` | 共用一块内存的代价 | 前面每张都在夸共用是对的 |
| `display-vocabulary` | 每个词落在通路哪一段 | 术语表是十六个孤立句子 |
| `display-triage` | 出问题时先查哪一站 | 学完了,它值多少钱 |

**判断依据:一张图讲不完的标志,是你得在图注里补一句"另外……"。**
补的那一句就是下一张图的题目。

三条排版纪律,都是这一轮踩出来的:

- **总线名挂盒子下方,不挂盒子之间的缝。** 缝通常只有 26px,药丸 90px,
  挂上去就压住下一个盒子的编号徽章。
- **画竖直的流动线前,先看沿途有没有别的盒子。** 第一版的写入线从内存控制器
  直着往下走,正好穿过 CPU 盒,药丸落在盒子里面。
- **同一个东西在多列里重复出现时,标注只写一次,写在行首。**
  `buffer-roles` 第一版每列都标地址,结果第一列的标注跑到画布外被裁掉;
  改成行首标一次之后,**「三列画的是同两块内存」这个论点反而自己立住了** ——
  少写的那两遍,比写出来更能说明问题。

### 15.33 借第一张图例表里的四个构件（`glyphs.svg`）

`glyphs-memory.svg` 那八个构件(地址条 / 窗口带 / 页帧阵列 / COPY 块 / 内存条 /
屏 / 连接药丸 / 署名卡)一直在用,但**第一张图例表那八个几乎没人碰**。
这一轮把其中四个用起来了,各有各的不可替代:

| 构件 | 画什么 | 为什么不能用普通盒子代替 |
|---|---|---|
| `g-queue` | 深度有限、按顺序 | 盒子表达不出"还剩几格"。DDR 控制器的请求队列、AXI 未完成事务 |
| `g-bytestream` | 串行化的**字节**,不是地址 | 跟地址条形状必须不同,否则读者以为 lane 上跑的是地址 |
| `g-porttab` | 信号在这里离开硅片 | 梯形骑在边框上,一眼看出"这是对外接口"而不是内部模块 |
| `g-sync` | 时间上的一个刻度 | vsync / TE 既不是数据也不是地址,画成盒子就错了 |

**`g-bytestream` 有个坑**:多条并排时,每条下面的刻度会顶到下一条,
四条 lane 挤成一片阴影。刻度长度要能调 —— 并排画时给 7px,单独画时 12px。

**最有用的一条是 `g-sync` 带出来的**:它逼你区分「东西在哪」和「什么时候发生」。
`display-vocabulary` 那张图把 vsync / 翻页 / 撕裂 / 欠载 单独归一组,
就是因为**它们不在任何一个盒子里**。前一版页面把时刻和地点混在一起讲,
是读者绕不出来的一个原因 —— 在框图上找一个时刻,能把人困住很久。

### 15.34 剖面图（cross-section）

**答的问题**:谁挨着谁、中间隔着什么、各层多厚。框图答不了 ——
"A 连 B" 说不出 "A 压在 B 上,中间有 150 µm 的胶"。

- **必须配平面图 + 剖切线**。一张没说"从哪儿切"的剖面图是有歧义的:同一个模组横着切和竖着切
  完全是两张图。平面图上画一条点划线 `stroke-dasharray="10 4 3 4"`,两端各一个 `A`,
  再各画一个箭头 —— **箭头说明你朝哪个方向看**,没有箭头,读者不知道左右是哪边。
- **被切开的实体填 45° 斜线**(`pattern` + `patternTransform="rotate(45)"`,opacity 0.20-0.26)。
  不同材料换 hue 不换角度 —— 换角度读者会以为是两种剖法。空气隙 / 未填充区用白底虚线框,不打斜线。
- **薄层的名字一律引到外面**。带子高度 < 20px 就塞不下 11.5px 的字。
  引线水平出到一个**右对齐的标签列**(`text-anchor="end"`),标签之间中心距 ≥ 17px。
  往 14px 的带子里塞字是这类图翻车的头号原因。
- **厚度只画相对比例,并在图脚写明**。真按 0.55 mm 比 3.5 µm 画,液晶层就是 0 像素。
  写了"相对比例"读者才不会拿图去量。
- 反模式:剖面图上画箭头解释("如图 A 处")—— 剖面的价值就是不用解释;
  层数超过 14 层还硬画在一张里(拆成"整体 + 局部放大")。

**局部放大(detail callout)是剖面图的固定搭档**:整体图上画一个虚线小框,
**用两条线**连到放大面板的两个角。为什么是两条:一条线读起来是"指向某处的箭头",
两条才读成"这一块,放大"。放大倍数写在放大面板的标题里(`AT 40×`)。

### 15.35 爆炸视图（exploded-view）

**答的问题**:先装哪个、后装哪个、哪些还拆得下来。这两问剖面图一个都答不了,
而它们决定一块板子能不能修 —— 所以爆炸图不是剖面图的"立体版",是另一张图。

- **一根直轴,所有件的中心落在轴上**。轴用点划线画出来。这根线是读者判断
  "这些件怎么合回去"的唯一线索;件不对齐,图就退化成一列矩形。
- **间距必须相等**。不等距会被读成真实距离 —— 于是两个只是碰巧相邻的件看起来有关系。
- **编号走装配顺序,不走从上到下**。这正是这张图存在的理由:基板先、中介层后、
  die 再后、最后整颗上板。编号如果跟着位置走,这张图就白画了。
- **边框区分可逆性**:实线 = 装完还拆得开;虚线 = 固化 / 回流之后回不去。
  一眼看出"从哪一层往下就没有返修的机会了"。
- **圆形元素 = 接合处,不是零件**(焊球、铜柱)。方的是件,圆的是缝,读者不会数错零件数。
- **左上角配一张成品缩略图**,虚线箭头指向爆炸列。没有它,读者不知道这堆件合起来长什么样。
- **正视图拆开是默认**;要画成等距轴测的立体爆炸图也可以,但要走 §24 那四条硬约束,
  而且只有在「几件东西在一个平面上怎么摆」也需要说清时才值得 —— 只讲顺序的话,正视图更清楚;
  把接合处也编号(那会让"五步装配"变成"九步")。

### 15.36 命令贴在架构图上（debug-map）

**答的问题**:"系统卡了,我该敲哪条命令"。工具清单答不了,因为读者不知道
自己的问题落在哪一层;架构图也答不了,因为它只说结构不说怎么看。这张把两者合成一张。

- **每张节点卡下面挂一条 mono 药丸**,写**具体路径或命令**,不写"看日志"这种类别词。
  卡和药丸同宽、贴在一起,归属才唯一。
- **药丸按后果上色,不按类别上色**:绿边 = 只读,随便敲;金边 = 会改硬件或内核状态。
  右端再压一个 `read` / `writes` 小字。**这个区别在凌晨两点、在别人的板子上最要命** ——
  颜色是给"手比脑子快"的那一刻准备的。
- **左边一列从现象进入,不从架构进入**。没有人是捧着框图进调试现场的,
  进来时手里拿的是"背光亮但屏黑"。每张现象卡末尾用橙色写"→ 从哪块开始"。
- **图脚必须写清前提**:`/sys/kernel/debug/...` 只在挂了 debugfs 且编了对应内核选项时存在。
  **少一个文件不等于那一块没在工作** —— 不写这句,这张图会制造错误结论。
- 命令必须是真的。写进图里的每条路径都要能在内核树里找到出处,
  查不到的宁可不写(受"代码事实禁 hedge"约束)。

### 15.37 对数刻度数量级尺（magnitude-ruler）

**答的问题**:一批跨好几个数量级的量(延迟 / 容量 / 带宽 / 频率),
它们之间到底差多远。线性刻度画不下 —— 1 ns 和 150 ms 差 1.5 亿倍,
放在同一条线性轴上,前十一个点会叠在同一个位置。

- **必须在图上写明"等距 = 十倍"**。这是对数轴唯一的义务。漏了这句,
  读者会不出声地把每一段都读小十倍,而且不会察觉自己读错了。
- **配一条线性刻度的对照小图**,把同一批点放上去,让"叠成一个点"这件事被看见。
  这比任何一句解释都有效,而且它顺手回答了"为什么这张图要用对数轴"。
- **十进制刻度之间补 2..9 的次级刻度**(短、浅灰)。没有次级刻度,读者无法估读中间值。
- **标签用交错的多行 + 竖直细杆连回轴上**。密集处三行,别互相压。
- **配一列"换成人类尺度"的卡**(若 1 ns = 1 秒:L1 = 1 秒,一帧 = 193 天)。
  这一列才是让尺子变成论据的东西:"慢十万倍"是一句话,"一秒对一百九十三天"是一张图。
- **写明这是典型数量级不是实测值**,并让读者去测自己的板子。
- 反模式:把数量级尺画成柱状图(柱长在对数轴上没有意义);
  只标 10 的幂而不放具体事件(那是一把没量东西的尺)。

### 15.38 引脚 / 连接器图（pinout）

**答的问题**:这个连接器每一根是什么、怎么跟手里的实物对上。

- **物理排布 + 信号表,两样都要**。只有表,没法拿实物核对;只有排布图,不知道每根是什么。
  排布按**实物真实排法**画(单排 FPC 就画一排,别为了省地方画成两列)。
- **1 脚必须有标记**,并写清实物上靠什么认(丝印三角 / 切角)。
- **必须写"从哪一面看"**。从元件面看和从焊盘面看是**镜像**的 ——
  不写这句的引脚图不能用,这是这类图唯一会造成硬件损坏的错误。
- **差分对用括号括起来**,不要只做并排两行表格。一对被读成两根独立的脚,
  就会被当成两根独立的脚去布线,然后在长 FPC 的远端出问题。
- **对间的地不是备用地,是屏蔽**。图脚要写明,否则会被人挪去接别的信号,
  顺带改掉旁边那对的阻抗。
- 类别配色四档就够:地(墨)/ 电源(金)/ 差分(蓝)/ 控制(绿),橙色留给标注和警告框。
- 反模式:表里写型号当权威 —— 图脚必须写"以屏的规格书为准,这只是示例排法"。

### 15.39 逐级抽象阶梯（abstraction-ladder）

**答的问题**:这个符号里面装的是什么,以及它值多少钱。

- **每一格先画"里面是什么",再折成符号**,两者之间用一条虚线连着。
  下一格打开的,正是上一格折起来的那个符号。
- **符号上必须标成本**(晶体管数 / 周期数 / 字节数)。抽象最擅长藏的就是这个数字,
  而它恰恰决定了这东西会被用一百万次还是根本不会被用。
- **三级是上限**。再多读者就跟丢了"谁装着谁"。内容需要更多级时拆成两张图,
  让第二张的第一级等于第一张的最后一级 —— 这样它从一个已经懂了的东西开始。
- **没有它会怎样**:读者遇到的符号一上来就是关着的,他会正确地照抄,但没法对它推理;
  在遇到第一个变体之前一切正常,之后就完全卡住,因为他没有可以退回去的模型。
- 反模式:只画符号不画里面(那是参考卡不是解释图);把成本写在图注里而不是符号上
  (图注和图之间要来回找,而这个数字必须跟着符号走)。

### 15.40 同坐标状态三联图（state-triptych）

**答的问题**:同一个东西在几个状态下分别是什么样,以及**到底哪里变了**。

- **几格共用每一个坐标,一格都不许挪**。眼睛不需要重新解析,唯一还在动的就是那个差别。
  这一条是全部效果的来源:只要有一格为了排得好看被挪了一下,效果就没了。
- **颜色含义对整张图只定义一次**,写在读者会看的地方。
  **在几格之间会变的图例,比没有图例更糟** —— 读者会学会不信任颜色,转去读标签,
  于是这张图退化成一张慢吞吞的表格。
- **状态排成序列,不排成清单**(存着 0 → 写入 1 → 读出 1)。排序不花任何代价,
  却给了这张图一个方向,读者知道为什么是这个次序。
- **每格底下写一句"这一格跟左边那格差在哪"**。差别看得见,不等于说得出。
- 反模式:每个状态重画一张(读者会把电路重新找 N 遍,而且不会注意到哪里变了);
  用颜色同时表达状态和类别(一个颜色只能有一个职责)。

### 15.41 同一个零件的工序序列（process-steps）

**答的问题**:这东西是怎么一步步造出来的,以及**从哪一步起就没有退路了**。

- **同一个零件画 N 次,坐标全部锁死**。六张独立的图会让读者在每格里重新找一次零件,
  到第三格他已经不再对比了。锁死坐标,这一排就不再是图片:眼睛不动,变化在动。
- **只把这一步新增的东西描成焦点色**,已经存在的部分一律弱色。
  没有这一条,读者必须对比两格才知道这一步干了什么 —— 而**对比比看贵得多**。
- **每格底下写"到这一步还救得回来吗"**。这是工序图通常会省掉的一行,
  也是排期真正取决于的那一行。答案从"能"变成"不能"的位置,用一条竖虚线明确标出来。
- 反模式:几格画得不一样大(读者同时在比"变了什么"和"现在多大",后者一定看错);
  什么都上色(等于什么都没上色)。

### 15.42 放大链（scale-ladder）

**答的问题**:这几样东西是同一个东西的不同尺度,而不是几件不相干的东西。

- **每一跳三样东西,缺一不可**:① 虚线框说明下一格看的是哪一块 ② **两条**线把框带进下一格
  ③ 每格标真实尺寸和放大倍数。
- **两条线,永远不是一条**。一条读起来是"通向某处",两条才读成"这一块,打开"。
  这跟剖面图挂放大面板用的是同一对线(§15.34)—— 读者认过一次,下次不用再学。
- **底下配一把对数尺,把几个尺度标上去**。几格在页面上是等距排开的,
  在现实里往往差几个数量级;**没有这把尺子,排版本身就在宣称一个错误的比例**,
  而读者没有任何办法察觉。
- 反模式:不标尺寸(读者分不清放大三倍和放大五十倍);把虚线框放在离出口最远的角上
  (引线要横穿整格,压住格里所有内容)。

## 21. 两种视觉模式,分工写死

一张图讲**物理位置**,和一张图讲**逻辑关系**,是两件事。混着画,两边都讲不清。

| | 物理模式 | 逻辑模式 |
|---|---|---|
| 回答 | 它在哪儿、挨着谁、多大 | 谁连谁、什么条件下走哪条路 |
| 画法 | 剖面 / 爆炸 / 放大链 / 板级布局,按真实比例和真实排布 | 框图 / 电路 / 流程 / 状态,按逻辑排布,不管真实位置 |
| 尺寸 | 必须标真实尺寸 | 不标尺寸,标的是位宽 / 周期 / 条件 |
| 什么时候用 | 读者要拿图去对实物 | 读者要顺着图做推理 |

**一张图只能属于一种模式。** 想同时说清位置和逻辑,出两张,并且让它们共用同一批名字。

**为什么**:两种模式对"距离"的含义要求相反。物理图里两块挨着 = 它们真的挨着;
逻辑图里两块挨着只是排版方便。混在一起,读者无法判断某一次相邻是事实还是巧合 ——
而他不会问,他会默认是事实。

## 22. 数值贴在物体上,不进图例

能写在物体上的数值(位宽、电压、容量、尺寸、间距),就写在那个物体旁边,
不要收进图例或图注。

- **为什么**:图例和图之间有一次视线往返。一个数字往返一次不算什么,
  一张图有十个数字,读者就在两个区域之间来回十次,而每次回来都要重新定位。
- **图例留给"看不出来的东西"**:颜色语义、线型语义、单位约定。这些没法贴在物体上。
- **边界**:数值多到贴不下时,不是把它们塞进图例,而是这张图画大了 —— 拆图(§8.1)。

## 23. 抽象层和物理层同框

波形画在**那根导线的正上方**,不要单独出一张波形图;算式浮在它描述的那个部件上;
逻辑符号和它对应的物理结构并排放。

- **为什么**:分成两张图,读者要自己建立"这条波形属于那根线"的对应关系,
  而这个对应关系恰恰是这段内容的全部内容。分开画等于把要讲的东西删掉了。
- **落法**:物理层用实物比例画,抽象层用半透明底或浮层压在上面,两者之间**不画箭头**
  —— 位置本身就是对应关系。
- **反模式**:一张实物图 + 一张波形图 + 一句"上图中的 CLK 对应下图的第二条曲线"。
  那句话就是这条规则存在的理由。

### 15.43 三种看内部的画法并置（see-inside）

**答的问题**:"把里面画出来"到底该用哪一种。它有三种,答的问题不同,代价也不同。

| 画法 | 答什么 | 代价 |
|---|---|---|
| 切开(剖面) | 谁挨着谁、多厚 | 只看得到那一刀所在的那个平面 |
| 透视(半透明) | 里面有几个、怎么摆 | 重叠的地方会糊成一个本来不存在的形状 |
| 拆开(爆炸) | 什么顺序、还拆不拆得开 | 真实的相邻关系没了 |

- **透视是最该少用的一种**,因为**它的失败是安静的**:两个重叠的件合成一个新形状,
  页面上没有任何东西提示读者。另外两种失败时至少看得出来。
- **一张图不要同时答三个问题**。剖面长出幽灵轮廓、透视图长出一根装配轴,
  都是这件事的征兆,而读者的反应是不再相信这张图里的任何一部分。
- 三种都是平面画法,都不需要透视。要同时说清"怎么摆"和"多厚"才轮到等距(§24)。

### 15.44 只点亮当前那一块（highlight-in-place）

**答的问题**:一张很密的图,怎么分几步讲,而不让读者每一步都重新找一遍。

- **底图只画一次,几格共用每一个坐标**,把当前讨论的那一块上色,其余保持中性。
  密图每格重画,读者到第三格就已经不再仔细看了。
- **中性是选择,不是剩下的**。不属于这一步的东西要刻意画安静,
  上色的那一块才有"从什么里面站出来"的东西。
- **抽象名词第一次出现时,用虚线框钉在物理结构上**(在阵列上圈出"一页")。
  只在正文里说,它就一直是个读者点头但没落地的词。
- **高亮最多两层**(一行 + 一列)。第三种颜色一上,等于什么都没高亮 ——
  那正是内容该拆成第二张图的信号。

### 15.45 宽度有量纲（flame-graph）

**答的问题**:时间/资源到底花在哪。

- 一个方块有两个维度,大多数图只用了一个。**让宽度带上单位**(采样占比、字节数、预算),
  另一维才不算白给。
- **横轴不是时间**。相邻两块没有先后关系,它们按名字排序 —— 这是这类图第一号误读,
  必须写在图上。
- **纵轴是栈深不是时长**。又高又细的塔是很深但几乎不花时间的调用链,
  而它恰恰是眼睛最先被吸引过去的东西。
- **颜色别随机**。随机配色是这类图的常见做法,它把一整个维度花在了零信息上;
  按代码归属(应用 / 库 / 内核)分组更有用。
- **没有宽平顶不是图坏了**,是它在说"开销摊得很平,没有单独一件事可修"。

### 15.46 语法铁路图（railroad）

**答的问题**:哪些部分可选、能不能重复、要在几个里挑一个。

- **唯一的规则**:从起点环走到终点环,走得通的路径就是合法的。写在图上。
- **只有三种形状**:上方绕过 = 可省略;下方回环 = 可重复;并排分支 = 三选一。
  文法记号里这三件事全靠方括号 / 花括号 / 竖线区分,长得都一样。
- **铁路图里没有决策**,所以不许出现菱形、每段一个箭头、或者条件标签。
  加了就变成一张碰巧画错的流程图。
- **它输在递归**:记号一行就能说清 term 里面含 expr,图只能指回上面那条轨。
  文法以递归为主时,留着记号。

### 15.47 队列压力曲线（queue-pressure）

**答的问题**:越忙会怎样。

- **只画排队的图不够**。读者看见队列,默认"忙一点 = 按比例慢一点",
  而真实关系是 ρ/(1−ρ):50% 到 80% 是四倍,80% 到 95% 又是五倍。
  **那条曲线才是这张图存在的理由**,排队的小方块只是入口。
- **在曲线上标出膝点**(约 80%),并且写清"轴是线性的,体验不是"。
- **说明这条形状的前提**(单服务台、随机到达)。真实系统有突发,弯得更早更狠 ——
  把曲线当坏消息的下限,不是估计值。

### 15.48 单幅速查图（cheatsheet）

**答的问题**:这张图被人截图发走之后,还成不成立。

- 一张要独自旅行的图,得自带页面平时替它提供的四样东西:
  **① 标题说它是什么 ② 一句话说它答什么 ③ 出处和日期 ④ 它的边界(什么它不管)**。
- **检验方法很简单**:截图,发给一个没读过这个页面的人,看他能不能据此做事。
  我们大部分图过不了这一关,而这就是过得了的那个形状。
- 边界那一条最容易省,也最要紧:说清"这张卡只说画哪种图,不说怎么画",
  读者才不会拿它当完整答案。

### 15.49 可拨的步进图（stepper）

**答的问题**:几步的过程,让读者自己控制看到第几步。

- **这是 HTML,不是 SVG**。模板是 `templates/diagrams/stepper.html`,
  一个 `<figure>` 里放控件 + N 个 `[data-step]` 面板 + 一小段脚本。
- **必须有一个可截图的默认状态**,而且这是机器检查的:
  `visual-audit` 的 `interactive-figure-blank-default`。
  - 点击之前**恰好一个**面板可见(其余 `hidden`)
  - 对应的那个控件带 `aria-current`
  - 两条都不满足时,截图门拍到的是一个空盒子,而四道检查全绿 ——
    **坏的方向是"放过",这正是最贵的那个方向**。
- **默认那一格本身要是一张完整的图**。脚本没跑(禁用 JS、抓取器、打印)时,
  页面显示的就是它。
- 各步共用每一个坐标,只让高亮移动(§15.44 的规矩在这里同样适用)。
- **先做步进按钮,不做连续滑块**。滑块的中间状态无穷多,截图和像素对比都失去意义;
  离散几步则每一步都可复现。

## 24. 等距轴测:允许,但有四条硬约束

**先分清两种立体。** 一种是**装饰性立体** —— 投影阴影、透视缩放、给方块加一圈假厚度、
用渐变冒充打光。这种一律禁:它不增加任何信息,只让工程图看起来像演示软件里的现成图形,
而且透视会让"两条边是不是等长"变得不可判断。

另一种是**等距轴测**(isometric / axonometric)。它是技术插画的标准手法,而且**保持可测量**:
三根轴上的长度按同一比例读,平行线仍然平行。仓里 `apple-design` 一直在用它画信息图 ——
所以 §14 那条一刀切的禁令本来就跟仓内实践对不上,2026-09-02 改成现在这样。

**什么时候值得用等距**:当"几件东西在一个平面上怎么摆"和"它们各自多厚"**都要说**的时候。
只讲厚度和相邻 → 剖面(§15.34);只讲顺序和可逆 → 正视爆炸(§15.35);
两样都要 → 才轮到等距。它不是更好看的爆炸图,是回答第三个问题的图。

**四条硬约束,缺一条就退回平面画法:**

1. **用真正的等距变换,不要随手画斜边。**
   `sx = (x - y) * 0.866`,`sy = (x + y) * 0.5 - z`。手画的斜边角度不一致,
   读者会以为那是形状差异。
2. **文字一律保持正立,不跟着面倾斜。** 倾斜的字既难读,渲染后的有效字号也会掉,
   会触 `diagram-tiny-text`。文字放在物体外面用引线接,或者压在正立的药丸里。
3. **三个面用同一 hue 的三档 tint,不用渐变、不用阴影。** 顶面最浅、左面中、右面最深,
   全图统一。这样"立体"仍然是颜色语义的一部分,而不是假光照 —— 也保住了 §0。
4. **必须有一条尺寸线或一个比例说明。** 等距最容易骗人的地方就是尺寸:
   两个看起来一样大的面,在轴上可能差一倍。没有尺寸线,这张图只能当示意。

**还有一条不是硬约束但值得记**:等距图里**被遮住的东西就是没了**。要同时看见前后两件,
要么拆开(加间距),要么用 §15.43 的半透明,别指望读者脑补。

## 20. 文字不能越过 viewBox 边界

`<text>` 超出 viewBox 不会报错、不会换行，**它就是被裁掉**，而且只有在缩放后的
那一家才看得出来。2026-08-28 实测：`datapath` 里一句
`x="956"` 的说明在 anthropic 恰好放得下，搬到 glass 就成了 `…staying lo`。

- 落法：**贴右边的文字一律 `text-anchor="end"` 钉在右边距上**（模板用 `x="1088"`），
  别用 `text-anchor="start"` 加一个"估计够"的 x。左边同理，用 `x="32"` 起。
- 居中的长句用 `text-anchor="middle"` 并保证 `x ± 半宽` 落在边距内。
- 字体换了宽度就变（Poppins → Inter → SF Pro 逐个变宽），所以**靠估算 x 的写法迟早会裁**。
  锚点写在边距上是唯一不受字体宽度影响的写法。
